# Storage Service 学习分析 — Seata 最简参与者(RM)

> 库存服务:整条链路里**最简单的参与者**——收请求、扣库存、返回。
> 但"简单"恰恰是 Seata AT 的卖点:**参与方一行事务代码都没写,却自动获得了回滚能力**。
> 本篇就借它这条 UPDATE 语句,把 AT 一阶段(undo_log)的机器拆开给你看。

## 1. 项目定位:库存,链路第一站

```
business(/seata/feign)
   │ ①第一个被调用
   ▼
storage-service (18082)  ← 本项目
   库表: storage_tbl (commodity_code 唯一键, count 库存)
   动作: count = count - 2
```

| 维度 | 说明 |
|---|---|
| 角色 | **RM**(资源管理器):管 storage_tbl + 自己的 undo_log |
| 事务注解 | **零!** 没有 @GlobalTransactional 也没有 @Transactional |
| 包结构 | 本模块开始用 `controller/`、`config/` 子包(比 business 规范一点) |

## 3. 核心代码:一行业务 SQL 的"隐形事务"

```java
@RestController
public class StorageController {

    @GetMapping(value = "/storage/{commodityCode}/{count}", produces = "application/json")
    public String echo(@PathVariable String commodityCode, @PathVariable int count) {
        LOGGER.info("Storage Service Begin ... xid: " + RootContext.getXID());   // ★ 打印全局事务ID

        int result = jdbcTemplate.update(
                "update storage_tbl set count = count - ? where commodity_code = ?",
                new Object[] { count, commodityCode });                          // ★ 全部业务就这一句

        LOGGER.info("Storage Service End ... ");
        return result == 1 ? SUCCESS : FAIL;
    }
}
```

三个观察点:

1. **`RootContext.getXID()`**——这就是上一讲说的"从头里取出的 XID 绑到上下文"后的读取口。
   成功链路里,这行日志会打出 business 开启的同一个 XID,**这就是"我已入伙"的证据**。
2. **没有任何事务注解**——Seata 的魔法在**数据源代理**层(starter 自动把 DataSource 包装成代理),
   只要"当前线程绑定了 XID + 执行了 SQL",分支事务就自动发生。
3. **update 返回影响行数**,0 行(商品不存在)→ 返回 FAIL → business 检查后抛异常 → 全局回滚。

## 4. 深挖:这条 UPDATE 在 Seata眼里发生了什么(必看)

以库存 100、买 2 件为例,`update storage_tbl set count=count-2 where commodity_code='C00321'`:

```
线程绑定 XID=192.168.1.5:8091:8888
   │
   ▼ jdbcTemplate.update(...)
┌──────────────────────────────────────────────────────────────┐
│ Seata 数据源代理(自动织入,业务无感)                            │
│                                                              │
│ ① 解析 SQL:目标表 storage_tbl,条件 commodity_code='C00321'   │
│    → 定位主键 id=1(所以业务表必须有主键!)                     │
│                                                              │
│ ② 查"修改前"镜像:                                            │
│    SELECT id,commodity_code,count FROM storage_tbl           │
│      WHERE commodity_code='C00321' FOR UPDATE                │
│    → beforeImage: {id:1, code:C00321, count:100}             │
│                                                              │
│ ③ 开本地事务,执行业务 UPDATE(count 100→98)                   │
│                                                              │
│ ④ 查"修改后"镜像:                                            │
│    → afterImage: {id:1, code:C00321, count:98}               │
│                                                              │
│ ⑤ 组装 undo_log 写入【同一个本地事务】里:                      │
│    INSERT INTO undo_log(branch_id, xid, rollback_info...)    │
│    rollback_info = 序列化(before|after|SQL解析信息)           │
│                                                              │
│ ⑥ 向 TC 注册分支事务 + 申请行级全局锁                          │
│    (resource_id=jdbc:mysql.../seata, lock_key=storage_tbl:1) │
│                                                              │
│ ⑦ ★ 提交本地事务(不等全局事务!)                              │
│    → 业务数据 98 已落库、undo_log 也已落库(原子)               │
└──────────────────────────────────────────────────────────────┘
```

**之后二阶段分两种命运:**

```
全局成功(TM 提交)                全局失败(TM 回滚)
   │                                │
   ▼                                ▼
TC 异步通知分支提交                TC 通知分支回滚
   │                                │
DELETE FROM undo_log               ① 校验:当前行 == afterImage(98)?
WHERE xid=... branch_id=...           (没人偷偷改过 → 数据可信)
   │                                ② 用 beforeImage 生成反向补偿:
   ▼                                   UPDATE storage_tbl SET count=100
完成(纯异步,极快)                      WHERE id=1
                                      ③ 删 undo_log、释放全局锁
                                      → 库存看起来从未被扣过
```

**两个灵魂问答:**

- *为什么一阶段就敢提交本地事务?*——undo_log 与业务数据在**同一本地事务**里原子落库,后悔药已经存好。
- *回滚时凭什么敢直接改回去?*——先校验当前数据 == afterImage,确认没有"别人绕过 Seata 改过这行",再补偿。

## 5. 启动造数据的 hack:DatabaseConfiguration

```java
@Configuration
public class DatabaseConfiguration {

    @Bean
    public JdbcTemplate jdbcTemplate(DataSource dataSource) {
        JdbcTemplate jdbcTemplate = new JdbcTemplate(dataSource);
        // 在"创建 Bean 的方法"里顺手重置测试数据:
        jdbcTemplate.update("delete from storage_tbl where commodity_code = 'C00321'");
        jdbcTemplate.update("insert into storage_tbl(commodity_code, count) values ('C00321', 100)");
        return jdbcTemplate;
    }
}
```

**这是什么?**——demo 的"数据重置器":每次重启,库存回到 100。
**为什么被注释掉的还有 Druid?**——注释写着 GraalVM 不支持(和 nacos 家族 UrlCleaner 被注释同一个原因)。

工程评价:
- ✅ 好处:实验可重复(刷爆了重启即可复位)
- ❌ 坏处:配置类里藏业务 SQL,违反单一职责;生产代码绝不能这么写(等价于每次发版清库)
- 被注释的 `@ConfigurationProperties("spring.datasource")` + DruidDataSource 写法,是**企业里多数据源的标准姿势**,值得看一眼记下来

## 6. 配置拆解:与 business 的差异

seata 段几乎一样(`tx-service-group` 变成 `storage-service-tx-group`),差异在**多了数据源**:

```yaml
base:
  config:
    mdb: {hostname: 127.0.0.1, dbname: seata, port: 3306, username: 'root', password: 'root'}
          # 自定义占位符,把 DB 连接集中一处,下面 ${base.config.mdb.xxx} 引用——值得学的组织方式

spring:
  datasource:
    driver-class-name: com.mysql.cj.jdbc.Driver
    url: jdbc:mysql://${base.config.mdb.hostname}:${base.config.mdb.port}/${base.config.mdb.dbname}?...
    username/password: ${base.config.mdb.*}
  main:
    allow-bean-definition-overriding: true     # ★ 为什么需要?(见坑3)
```

别忘了它的库里还有一张 `undo_log`(all.sql 建的)——**它才是 RM 身份的"硬件基础"**。

## 7. 企业里怎么用?

### 7.1 参与方的接入清单(企业落地最小集)
1. 引 `spring-cloud-starter-alibaba-seata`
2. yml 配 `tx-service-group` + registry/config(Nacos)
3. **业务库建 `undo_log` 表**(每个数据源一张)
4. 完了。不需要写任何事务代码——这就是 AT"0 侵入"的含义

### 7.2 库存场景的真实演化(重点)
本示例"扣库存"直接 UPDATE 同一行——**恰是 AT 模式的软肋**:

```
热点行:爆款商品 storage_tbl 里只有一行,行级全局锁串行化所有全局事务
   → 秒杀场景吞吐被锁等待拖垮
企业对策:
   ① 库存分桶:一件商品拆 N 行(库位/分片),下单随机/轮询挑一行扣 → 锁竞争分散
   ② 热点商品走 Redis 预扣 + 异步落库(脱离全局事务,消息最终一致)
   ③ 极端性能场景改 TCC(自己控制资源,不靠行锁)
```

### 7.3 与消息队列的配合
扣库存成功后要发"库存已扣"事件 → **事务外发消息**(否则回滚了消息却发出去了)。
企业常用:Seata 全局事务内只做 DB 操作,事务提交后的钩子/本地消息表再保证事件可靠投递。

### 7.4 多数据源参与方
若 storage 有两个库,每个库各自要 undo_log,且要配 `seata.datasource` 相关的代理策略(默认自动代理所有 DataSource)。

## 8. ⚠️ 注意事项与坑

### 坑 0:parent 链断裂(同全家族)→ 见总览坑 0

### 坑 1:undo_log 缺失 = 回滚失败
storage 库没建 undo_log(或建错库)时:**一阶段照常跑**(业务能成功),
但**回滚时无药可救**,TC 反复重试,只能人工修数据。症状:`BranchRollbackFailed`。
→ 接入清单第 3 条不是可选项。

### 坑 2:业务表没主键
undo/锁都按主键定位行。`storage_tbl` 有 `id` 主键没问题;**无主键表**在 AT 里直接不支持
(报 `Could not found any index in the table` 类错误)。给老表加主键是接入 Seata 的前置改造。

### 坑 3:`allow-bean-definition-overriding: true` 的真相
seata starter 会向容器注册 DataSource 代理等 Bean,可能与你自己的定义**同名冲突**。
demo 用"允许覆盖"暴力解决。企业里更优雅:优先用 starter 的自动代理,自定义 Bean 换名字。

### 坑 4:update 影响行数 ≠ 1 时要敏感
`return result == 1 ? SUCCESS : FAIL`:若 commodity_code 重复(表有唯一键,此处安全)或不存在,result=0 → FAIL → 上游抛异常回滚。
**企业代码要区分"0 行是业务失败还是并发更新丢失"**,必要时乐观锁兜底。

### 坑 5:共库错觉
本示例 4 个服务连同一个 `seata` 库 → 新手误以为"分布式事务是同一个库的事"。
真实世界:**跨库/跨实例才是常态**,AT 的所有机制(undo_log 按库、全局锁跨库)都是为此设计。
做实验时可以把 3 张业务表拆到 3 个库验证(记得每库一张 undo_log)。

### 坑 6:日志没打 xid?
`RootContext.getXID()` 打印 null = XID 没传到。排查:
① business 是否真在 @GlobalTransactional 里发起调用;② 本服务是否引了 seata starter(拦截器在);
③ 调用链中间是否经过网关/代理**剥掉了请求头**(TX_XID 丢失)。

### 坑 7:接口语义
`GET /storage/{code}/{count}` 用 GET 做"扣减"写操作——违反 REST 语义,URL 被爬虫/预加载误触发就惨了。
demo 图方便,**生产写操作必须 POST/PUT**。

## 9. 动手练习

1. **看穿一阶段**:给 storage 也开 `io.seata: debug`,成功链路跑一次,在日志里按顺序找到:
   `xid` 绑定 → SQL 解析 → 分支注册 → 全局锁申请 → 本地提交
2. **肉眼看 undo_log**:在二阶段提交**之前**打断点(或把 business 的提交故意放慢),SELECT undo_log 表,
   观察 rollback_info 里的 before/after 镜像(二进制,可看到字段名)
3. **亲眼见回滚**:连续刷 `/seata/feign` 直到 order/account 的骰子爆炸,立刻查 storage_tbl——count 已回到 100,
   而 undo_log 已被清理(回滚完即删)
4. **删掉 undo_log 表再试**:drop 掉后触发回滚,观察 `BranchRollbackFailed` 报错,体会坑 1
5. **无主键实验**:给 storage_tbl 复制一张无主键的表并改 SQL 指向它,看 Seata 拒绝工作
6. **进阶**:写一个"绕过 Seata 的直连 UPDATE"(新开一个不带 XID 的请求路径改库存),
   然后触发全局回滚——观察 afterImage 校验失败、回滚受阻,理解"为什么参与方所有写都要走 Seata 体系"

### 一句话总结

> storage-service 用最少的代码证明了 AT 的核心承诺:**参与方零注解、零感知**——
> 一条普通 UPDATE 背后,Seata 数据源代理悄悄完成了"前后镜像 + undo_log + 分支注册 + 全局锁 + 本地提交",
> 把"后悔药"和业务数据原子地存进同一个库。回滚时靠镜像反向补偿,提交时只需删日志——这就是 AT 高性能的全部秘密。
