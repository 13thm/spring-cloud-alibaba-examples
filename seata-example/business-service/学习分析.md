# Business Service 学习分析 — Seata 事务发起者(TM)

> 它是整个分布式事务的**发起者/总指挥**:自己没有数据库,却掌握全局事务的生死。
> 一切从一个注解开始:`@GlobalTransactional`。
> 本篇讲透:注解背后的机制、两种远程调用(rest/feign)、XID 传播原理、企业实践与坑。

## 1. 项目定位:TM 事务管理器

```
                    business-service (18081)
                    ┌─────────────────────────────┐
   用户请求 ──────► │  @GlobalTransactional        │ ← 全局事务边界在这里!
                    │  1. Feign→storage 扣库存      │
                    │  2. Feign→order   建订单      │
                    └─────────────────────────────┘
                      无数据库 → 它是纯 TM(只开/提交/回滚,不管数据)
```

| 维度 | 说明 |
|---|---|
| 角色 | **TM**(Transaction Manager):开启全局事务、最终 commit/rollback 的决策者 |
| 端口 | 18081 |
| 数据库 | **没有**(纯发起方;若它也写库,则同时是 RM) |
| 注册 Nacos? | 否(`autoRegister = false`,又是那个"纯客户端不注册"的老朋友) |

## 3. 启动类精读:一个类干四件事

```java
@SpringBootApplication
@EnableFeignClients                                    // ① 开 Feign(声明式调用 storage/order)
@EnableDiscoveryClient(autoRegister = false)           // ② 借 Nacos 发现别人,不注册自己
@LoadBalancerClients({
        @LoadBalancerClient("storage-service"),        // ③ 为三个服务声明负载均衡(空配置,老问题)
        @LoadBalancerClient("order-service"),
        @LoadBalancerClient("service-provider")
})
public class BusinessApplication {

    @Bean
    public RestTemplate restTemplate() {               // ④ 裸 RestTemplate(无 @LoadBalanced!)
        return new RestTemplate();
    }

    // ★ Feign 接口直接定义在启动类内部(内部接口,语法合法但不推荐,见坑5)
    @FeignClient("storage-service")
    public interface StorageService {
        @GetMapping(path = "/storage/{commodityCode}/{count}")
        String storage(@PathVariable("commodityCode") String commodityCode,
                @PathVariable("count") int count);
    }

    @FeignClient("order-service")
    public interface OrderService {
        @PostMapping(path = "/order")
        String order(@RequestParam("userId") String userId,
                @RequestParam("commodityCode") String commodityCode,
                @RequestParam("orderCount") int orderCount);
    }
}
```

看点:
- ③ 的 `@LoadBalancerClient` 三连又是**没带 configuration 的空配置**(不影响运行,默认轮询即可;正确姿势见 sclb 项目文档)
- ④ 的 RestTemplate **故意不加 `@LoadBalanced`**——因为 HomeController 的 rest() 版本用的是写死的 `http://127.0.0.1:18082` 直连地址,不需要负载均衡,但仍能传播 XID(证明 Seata 与 LB 无关)

## 4. 核心:HomeController 与 @GlobalTransactional

### 4.1 事务入口(feign 版,推荐先看)

```java
@GlobalTransactional(timeoutMills = 300000, name = "spring-cloud-demo-tx")
@GetMapping(value = "/seata/feign", produces = "application/json")
public String feign() {

    String result = storageService.storage(COMMODITY_CODE, ORDER_COUNT); // ① 扣库存
    if (!SUCCESS.equals(result)) {
        throw new RuntimeException();                                    // ② 失败必须抛异常!
    }

    result = orderService.order(USER_ID, COMMODITY_CODE, ORDER_COUNT);   // ③ 建订单(内部再扣钱)
    if (!SUCCESS.equals(result)) {
        throw new RuntimeException();
    }

    return SUCCESS;                                                      // ④ 全部成功 → TM 通知 TC 提交
}
```

### 4.2 @GlobalTransactional 注解拆解

这个注解 = 分布式版的 `@Transactional`,AOP 代理后方法被包裹成:

```java
// 伪代码:Seata 全局代理干的事
public String feign() {
    String xid = TM.begin(300000, "spring-cloud-demo-tx");  // ① 向 TC 开全局事务,拿 XID
    RootContext.bind(xid);                                   // ② XID 绑到当前线程上下文
    try {
        // ...原方法体:所有下游调用自动携带 XID ...
        TM.commit(xid);                                      // ③ 全成功 → 通知 TC 全局提交
        return SUCCESS;
    } catch (Throwable t) {
        TM.rollback(xid);                                    // ④ 任何异常 → 通知 TC 全局回滚!
        throw t;
    } finally {
        RootContext.unbind();                                // ⑤ 清理线程上下文
    }
}
```

| 属性 | 本例值 | 说明 |
|------|--------|------|
| `timeoutMills` | 300000(5分钟) | 全局事务超时;默认 60s。demo 给得很宽裕 |
| `name` | spring-cloud-demo-tx | 事务名,用于监控/日志识别(仅标识,不参与路由) |

**记住一句话:注解方法内抛出未捕获异常 → 全局回滚;正常返回 → 全局提交。**
所以示例里两处 `throw new RuntimeException()` 不是多余代码,是**触发回滚的机关**。

### 4.3 rest 版:证明 XID 传播不依赖 Feign

```java
@GlobalTransactional(timeoutMills = 300000, name = "spring-cloud-demo-tx")
@GetMapping(value = "/seata/rest", produces = "application/json")
public String rest() {
    // 裸 RestTemplate 直连 IP:端口(不走注册中心、不走LB)
    String result = restTemplate.getForObject(
            "http://127.0.0.1:18082/storage/" + COMMODITY_CODE + "/" + ORDER_COUNT, String.class);
    ...
    response = restTemplate.postForEntity("http://127.0.0.1:18083/order", request, String.class);
    ...
}
```

**XID 照样能传过去!** 因为 `spring-cloud-starter-alibaba-seata` 对 RestTemplate 和 Feign 都做了自动织入(见下节)。两个入口的业务逻辑完全一样,只是调用风格不同——**企业里按团队技术栈二选一即可,事务行为一致**。

## 5. XID 是怎么"飞"到下游的?(原理)

这是本模块最重要的知识点。SCA 的 seata starter 提供了两个"自动织入":

```
TM 侧(business)
  RootContext(XID 存在 ThreadLocal)
        │
        ▼  发起 HTTP 调用时,starter 自动把 XID 塞进请求头:
┌─ Feign 路径 ──────────────────────────────┐  ┌─ RestTemplate 路径 ─────────────┐
│ SeataFeignClient(包装你的FeignClient)    │  │ SeataRestTemplateInterceptor     │
│ 请求头: TX_XID = 192.168.x.x:8091:666   │  │ 请求头: TX_XID = ...(同一个key)   │
└──────────────────────────────────────────┘  └─────────────────────────────────┘
        │                                              │
        ▼                                              ▼
RM 侧(storage/order/account)
  Seata 处理器(自动注册的拦截器/过滤器)收到请求:
  从头里取 TX_XID → RootContext.bind(xid)   ← 参与方从此知道自己属于哪个全局事务
        │
        ▼
  执行业务 SQL 时,数据源代理发现"有 XID" → 向 TC 注册分支 → 写 undo_log → ...
```

三个推论(面试可用):
1. **XID 靠 HTTP 头传播,与调用工具无关**——Feign、RestTemplate、甚至手写 HttpClient(自己带头)都能传
2. **异步/线程池会断链**——XID 在 ThreadLocal 里,新线程不会自动继承;`@Async`、消息队列消费等场景要手动透传(或用 Seata 提供的工具)
3. **入口即分支**——参与方收到带 XID 的请求那一刻就"入伙"了,**不需要也不应该**再写 `@GlobalTransactional`(见坑 4)

## 6. seata 客户端配置精读

`application.yml` 的 seata 段(4 个服务长得几乎一样,以 business 为例):

```yaml
seata:
  enabled: true
  application-id: ${spring.application.name}        # ① 本应用在 Seata 里的身份
  tx-service-group: ${spring.application.name}-tx-group   # ② ★ 事务组:business-service-tx-group
  config:
    type: nacos                                     # ③ 客户端配置中心=Nacos
    nacos:
      serverAddr: 127.0.0.1:8848
      dataId: "seata.properties"                    #    从 Nacos 读 seata.properties
      username/password: nacos
  registry:
    type: nacos                                     # ④ 注册中心=Nacos(用来找 TC)
    nacos:
      application: seata-server                     #    在 Nacos 里找名为 seata-server 的服务
      server-addr: 127.0.0.1:8848
```

**两条独立的"寻址"要分清(新手最容易混):**

| 配置 | 回答的问题 |
|------|-----------|
| `registry.type=nacos` | **去哪找 TC?** → Nacos 上服务名叫 `seata-server` 的实例 |
| `config.type=nacos` | **去哪读参数?** → Nacos 上 `seata.properties`(里面有关键的 vgroupMapping) |

`tx-service-group` 的三级对照链(对不上就是经典报错 `can not get cluster name for registry`):

```
yml:      tx-service-group: business-service-tx-group
                        ↓ 对应
Nacos配置: service.vgroupMapping.business-service-tx-group=default
                        ↓ 对应
server端:  集群名 default(即 seata-server 注册时所属 cluster)
```

其余配置:

```yaml
feign.client.config.default: {connectTimeout: 10000, readTimeout: 10000}
# Feign 超时 10s:全局事务里任何一环卡死都会拖垮整体,超时兜底必要

logging.level.io.seata: debug
# ★ 学习神器:能看到 xid 传播、分支注册、全局提交/回滚全过程,强烈建议 4 个服务都开
```

## 7. 企业里怎么用?

### 7.1 发起方的标准姿势
- `@GlobalTransactional` 只加在**编排层**(facade/controller/service 入口),一个业务动作一个边界
- 边界内**只做编排**,不做耗时操作(外部 HTTP、大文件、sleep 都会拉长全局锁持有时间)
- 返回值用统一 Result/异常体系,**失败必抛异常**,别学 demo 的魔法字符串判断(见坑 6)

### 7.2 超时与重试的工程参数
- `timeoutMills` 按下游最长链路评估(demo 的 5 分钟是给手工实验留的,**生产别照抄**;过长会让死事务长时间占着全局锁)
- 幂等:全局重试期间参与方可能收到重复的 commit/rollback 指令,业务侧保证幂等(undo_log 本身有防重能力)

### 7.3 无库发起方很常见
像"交易编排服务/BFF"这种只调度不落库的角色,本模块就是模板:引 starter、配事务组、加注解,完事。

### 7.4 可观测性
- 事务名(`name`)用有业务含义的命名,接 Seata 控制台/Prometheus 监控**全局回滚率**——回滚率飙升=某个下游在劣化
- debug 日志只在排障时开,量大

## 8. ⚠️ 注意事项与坑

### 坑 0:parent 链断裂(同全家族)
详见总览坑 0。

### 坑 1:注解方法必须是"可代理"的
`@GlobalTransactional` 靠 AOP 生效:
- **同类内部自调用失效**(this.feign() 绕过代理)——和 `@Transactional` 同款坑
- `private`/`final` 方法不生效
- 排查:日志里没有 `Begin new global transaction` 字样 = 代理没生效

### 坑 2:异常被 try-catch 吞掉 = 不回滚
```java
try { orderService.order(...); } catch (Exception e) { log.error(...); }  // ❌ 吞了 → 照常提交!
```
必须让异常冒出注解方法,或手动 `GlobalTransactionContext.reload(xid).rollback()`。

### 坑 3:rest 版写死了 127.0.0.1
换机器/容器部署直接失效。demo 为了简化;**生产用 Feign+服务名**,顺带享受负载均衡。

### 坑 4:误以为下游也要加 @GlobalTransactional
参与者靠 XID 入伙,**加了反而制造嵌套全局事务**(下游开新事务,回滚互不联动)。

### 坑 5:Feign 接口定义在启动类内部
`StorageService`/`OrderService` 是 `BusinessApplication` 的**内部接口**——语法没问题,但工程上应放独立包
(参照 nacos 家族 consumer 的 `feign/` 目录)。内部接口 + `@EnableFeignClients` 默认扫描启动类所在包,能扫到才 work。

### 坑 6:魔法字符串判断失败
`if (!SUCCESS.equals(result)) throw ...` 依赖下游**返回 FAIL 字符串**且**上游记得检查**;
生产应让下游直接抛异常/返回错误码并由 Feign 解码器转异常,减少"忘了检查"的人祸。

### 坑 7:yml 的 `enabled:true` 缺空格(语法错误)
```yaml
loadbalancer:
  ribbon:
    enabled:true    # ❌ 冒号后无空格,不是布尔配置,是个废键
```
本例无实际影响,但抄配置会传染。

### 坑 8:autoRegister=false 的连带效果
business 不注册进 Nacos——**它自己不能被别的服务 Feign 调用**(找不到实例)。如果哪天要给别人提供服务,记得改回。

## 9. 动手练习

1. **跑通成功链路**:`curl localhost:18081/seata/feign`,连续刷到 SUCCESS;开着 `io.seata: debug` 日志,把 `xid` 出现的每一行抄下来,画出传播路径
2. **触发回滚**:一直刷,直到骰子爆出异常;观察 business 日志的 rollback 指令 + 查 3 张业务表数据是否复原
3. **对比两种入口**:`/seata/rest` 与 `/seata/feign` 各刷几次,用 Wireshark/日志确认两者请求头里都有 `TX_XID`
4. **亲手制造坑 2**:把 `feign()` 里两段 if-throw 删掉,再等骰子爆炸——亲眼看"吞掉失败"导致数据不一致(库存被扣但事务提交),体会这个坑的可怕
5. **改超时做实验**:`timeoutMills` 改成 1000,在 order 的 sleep 场景下观察超时回滚行为(可临时给 storage 加 Thread.sleep)
6. **进阶**:把 Feign 接口挪到独立包;给 storage 再起一个实例,验证 XID 经负载均衡后依然正确传播到任意实例

### 一句话总结

> business-service 是全局事务的**大脑**:`@GlobalTransactional` 划出边界、开事务拿 XID、
> 把 XID 随每次 HTTP 调用播种到下游、按"异常与否"对 TC 下达全局提交/回滚令。
> 它证明了两件事:**Seata 对发起方的侵入只有一个注解**;**XID 传播靠 HTTP 头,与 Feign/RestTemplate 之争无关**。
