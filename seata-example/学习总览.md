## 1. 一句话理解这个示例

> 用户买 2 件商品:**扣库存**(storage)→ **创建订单**(order)→ **扣账户余额**(account),
> 三步分散在 3 个服务、(理想中)3 个数据库里。任何一步失败,前面已提交的必须**全部撤销**——
> Seata 用一个 `@GlobalTransactional` 注解 + undo_log 回滚日志,让这一切像本地事务一样简单。

业务数据流(示例固定值:用户 `U100001`,商品 `C00321`,买 2 件,单价 2):

```
storage_tbl: count 100 → 98
order_tbl:   新增一行 (U100001, C00321, 2, 4)
account_tbl: money 10000 → 9996
```

**示例故意内置了"骰子"**:order 和 account 里都有 `random.nextBoolean()` 抛异常(各 50% 概率)。
多刷几次接口,必然触发全局回滚——这就是本示例最核心的实验!

## 2. 问题:为什么本地事务救不了微服务?

### 2.1 单体时代

```java
@Transactional   // 一个数据库连接,一个本地事务,ACID 由数据库保证
public void purchase() {
    storageDao.deduct(...);   // 同库
    orderDao.insert(...);     // 同库
    accountDao.deduct(...);   // 同库
}   // 要么全成,要么全滚
```

### 2.2 微服务时代(本示例的处境)

```
business-service (无库)          ← 发起方
   │ HTTP
   ├──► storage-service (库存库)  ← 自己的本地事务,update 完就提交了
   └──► order-service  (订单库)   ← 自己的本地事务
            │ HTTP
            └──► account-service (账户库) ← 自己的本地事务
```

致命点:**每个服务的 `@Transactional` 只管自己那一小段**。第三步扣余额失败时,
第一步的库存扣减**早已在 storage 库提交**,没人能撤销它 → **数据不一致**:
库存少了 2 件,钱却一分没扣。

### 2.3 理论背景(面试必背)

- **CAP**:网络分区(P)必然存在时,一致性(C)与可用性(A)二选一。
- **BASE**:大多数互联网业务选择**最终一致性**——基本可用、软状态、最终一致。
- Seata AT 就是"**最终一致**"路线:一阶段就提交本地事务(可用性高),靠回滚日志保证出问题时能补偿回去。

## 3. Seata 是什么:三个角色

Seata(开源分布式事务中间件,源自阿里 GTS)由三部分组成:

```
                        ┌────────────────────────┐
                        │      TC  协调者         │
                        │   seata-server(独立部署)│
                        │  管全局事务/分支/全局锁    │
                        └─────▲──────────▲───────┘
              注册/上报/请求   │          │  注册/上报/请求
              ( begin/commit │          │ branch register
                /rollback )  │          │ /lock/undo 状态)
┌───────────────────┐        │          │      ┌────────────────────┐
│ TM 事务管理器       │────────┘          └──────│ RM 资源管理器        │
│ business-service   │                        │ storage/order/account│
│ 开全局事务的那个进程  │   XID 通过 HTTP 头传播 ► │ 管自己的库+undo_log   │
└───────────────────┘                        └────────────────────┘
```

| 角色 | 谁来当 | 职责 |
|------|--------|------|
| **TC** (Transaction Coordinator) | 独立部署的 `seata-server` | 维护全局事务/分支事务状态,指挥提交或回滚,管全局锁 |
| **TM** (Transaction Manager) | **business-service**(发起方) | 定义全局事务边界:begin / commit / rollback(就是 `@GlobalTransactional` 干的事) |
| **RM** (Resource Manager) | storage / order / account | 管理本地资源:注册分支、记录 undo_log、执行 TC 下发的提交/回滚 |

> 💡 **XID(全局事务ID)是串起一切的线**:TM 开启全局事务时从 TC 拿到 XID,
> 每一次跨服务 HTTP 调用都把 XID 塞进请求头带过去,参与方取出并绑定到自己的事务上下文——
> 于是 TC 能知道"这些分支同属一个全局事务"。你在代码里看到的 `RootContext.getXID()` 打印的就是它。

## 4. AT 模式核心原理(本示例用的模式)

### 4.1 两阶段流程

```
【一阶段:每个参与者各自执行,执行完就提交本地事务】

业务SQL: update storage_tbl set count = count - 2 where commodity_code='C00321'
   ↓ Seata 的数据源代理解截获
① 解析 SQL,查出修改前的行 → before image(镜像)
② 执行业务 SQL
③ 查出修改后的行 → after image
④ 把 before/after 写进同库的 undo_log 表
⑤ 向 TC 注册分支 + 申请该行的【全局锁】
⑥ 提交本地事务(不等全局事务!)  ← 这就是"高可用"的来源

【二阶段-提交】(全局事务成功,TC 异步通知)
   直接删 undo_log —— 秒完,性能极好

【二阶段-回滚】(任一分支失败,TC 通知所有分支)
   校验 after image 与当前数据一致(没被别人改过)
   → 用 before image 生成反向 SQL 自动补偿
   → undo_log: count=98 → 恢复成 100
   → 释放全局锁
```

### 4.2 关键设计点

- **为什么敢一阶段就提交?** 因为 undo_log 里有"后悔药"(before image),回滚时反向补偿即可。
- **全局锁的作用**:防止两个全局事务同时改同一行,导致补偿时数据对不上。
  事务A持有行锁期间,事务B要改同一行会**重试等待**,超时则回退。
- **隔离级别**:默认全局"读未提交"(一阶段提交后别人就能读到);需要强读隔离时用 `@GlobalLock` + `SELECT ... FOR UPDATE`。
- **0 侵入的代价**:undo_log 表 + 数据源被代理 + 行级全局锁的热点问题(后面企业节细说)。

### 4.3 Seata 四种模式对比(知道 AT 不是唯一选择)

| 模式 | 侵入性 | 一致性 | 场景 |
|------|--------|--------|------|
| **AT**(本示例) | 无(自动补偿) | 最终一致 | **绝大多数业务,企业默认选择** |
| TCC | 高(手写 Try/Confirm/Cancel) | 最终一致 | 性能敏感/非关系库(需要自己控制资源) |
| Saga | 中(写补偿服务) | 最终一致 | 长事务、跨企业调用 |
| XA | 无 | **强一致** | 传统数据库两阶段提交,性能差 |

## 5. 模块地图与调用链

```
nacos-example 风格回顾:消费者/提供者;seata-example 换成"事务角色"视角:

business-service  TM+RM(无库)  18081  autoRegister=false,不注册自己
storage-service   RM            18082  库:storage_tbl + undo_log
order-service     RM(还调下游)   18083  库:order_tbl   + undo_log
account-service   RM            18084  库:account_tbl + undo_log
```

`/seata/feign` 的完整调用链(推荐入口):

```
浏览器 → business /seata/feign   @GlobalTransactional 开启(XID=192.168.x.x:8091:123456)
  ├─Feign→ storage /storage/C00321/2   扣库存(请求头带XID)
  └─Feign→ order    /order             建订单(请求头带XID)
              └─RestTemplate→ account /account  扣余额(请求头继续带XID!)
任一环节抛异常 → TM 通知 TC 回滚 → 所有 RM 用 undo_log 反向补偿
```

`/seata/rest` 是同样业务,但 business 用裸 RestTemplate 直连 IP:端口调用(演示 XID 传播不依赖 Feign)。

## 6. 环境搭建与运行

> 前置组件较多,这是全仓库**搭环境最费劲的示例**,按顺序来:

### 6.1 MySQL(建库 seata,导入 all.sql)

```sql
CREATE DATABASE seata;
USE seata;
SOURCE all.sql;   -- 5 张 Seata 表 + 3 张业务表
```

`all.sql` 里两类表的归属(必须理解):

| 表 | 放哪 | 作用 |
|----|------|------|
| `undo_log` | **每个业务库** | RM 记录前后镜像,回滚的依据 |
| `global_table` / `branch_table` / `lock_table` / `distributed_lock` | **seata-server 的库**(storeMode=db 时) | TC 存全局事务/分支/锁 |
| `storage_tbl` / `order_tbl` / `account_tbl` | 业务库 | 业务数据 |

> 本示例 4 个服务共用一个 `seata` 库(图省事);**真实环境各服务各库,undo_log 每库一张**。

### 6.2 Nacos(2.2.x)

创建配置:`dataId=seata.properties`,`Group=SEATA_GROUP`,内容来自
[seata 官方 config.txt](https://github.com/seata/seata/blob/2.1.0/script/config-center/config.txt),
并**追加事务组映射**(缺了必挂,见坑 2):

```properties
service.vgroupMapping.business-service-tx-group=default
service.vgroupMapping.storage-service-tx-group=default
service.vgroupMapping.order-service-tx-group=default
service.vgroupMapping.account-service-tx-group=default
```

### 6.3 seata-server(2.1.0)

改 `seata-server/conf/application.yml`:registry 与 config 都指向 Nacos(注释默认 group、补账号密码),
storeMode 建议 db(指向 6.1 建的表)。启动后:
- 控制台 `http://127.0.0.1:7091`(观察全局事务/全局锁,**学习神器**)
- Nacos 服务列表出现 `seata-server`

### 6.4 改 3 个 RM 的数据库连接

`storage/order/account` 的 `application.yml` 里 `base.config.mdb.*`(host/库名/端口/账号/密码)。

### 6.5 启动顺序与实验

```
Nacos → MySQL(已备)→ seata-server → storage → order → account → business

curl http://localhost:18081/seata/feign     # 多刷几次!
```

实验观察:
1. **成功链路**:返回 SUCCESS;查 3 张业务表,数据全部变化;`undo_log` 被自动清空(二阶段提交=删日志)
2. **失败链路**(骰子触发):接口报错;查表发现**库存没少、订单没插、钱没扣**——一切像没发生过
3. **日志追踪**:business 开了 `io.seata: debug`,能完整看到 `xid` 的诞生与传播、回滚指令
4. **控制台追踪**:7091 里看全局事务状态(执行结束即清除,趁失败瞬间刷新)

## 7. 企业里怎么用?

### 7.1 真实场景
- **订单/交易主干**:下单-扣库存-扣余额-发优惠券,正是本示例的放大版
- 跨服务的**资金/账务类操作**,人工对账成本高、错不起的地方
- 存量系统改造成本敏感 → AT 模式"加注解+建表"就能上,这是它企业渗透率第一的原因

### 7.2 部署形态
- seata-server **集群部署** + Nacos 注册(客户端自动发现 TC),storeMode 用 db/redis(高可用)
- 客户端零改造接入:引 starter + yml 配事务组,业务方法加 `@GlobalTransactional`
- 生产必配:**事务监控告警**(全局回滚率是重要指标)、console 权限控制

### 7.3 性能与容量(架构师视角)
- **热点行全局锁是 AT 最大的坑**:秒杀扣同一行库存时,全局事务在行上排队,吞吐骤降。
  对策:库存分桶(拆行)、或热点场景改 TCC/消息最终一致
- undo_log 增加每次写入成本(约一次额外 insert + 两次镜像查询),批量 SQL 放大该成本
- 全局锁超时时间(`client.rm.lock.retryTimes` 等)与 `timeoutMills` 要按业务 SLA 调

### 7.4 技术选型口径(企业常见)
```
默认 AT → 遇热点/性能瓶颈 → TCC
长流程跨系统 → Saga
强一致报表/对账 → XA(少)
非核心链路 → 不上 Seata,用 本地消息表/RocketMQ 事务消息(更轻)
```
**不是所有跨服务写操作都需要 Seata**——能用消息最终一致的旁路逻辑(积分、通知)就别上全局事务。

## 8. ⚠️ 全家族注意事项与坑

### 坑 0:parent 链断裂(与 nacos 家族同款)
4 个模块的 parent 都指向根 pom `com.alibaba.cloud:spring-cloud-alibaba-examples:${revision}`,
而当前根 pom 已是 `com.thm.cloud` 空壳 → **编译不过**。修法同前:根 pom 补 `${revision}` + 三大 BOM。

### 坑 1:版本对齐是 Seata 第一坑
客户端版本由 SCA BOM 决定(本示例对应 seata 2.1.0,包名 `io.seata`);
seata-server 也要用 2.1.0。**client/server 大版本不一致**会出现各种灵异问题(注册不上、协议不兼容)。
注意:Seata 2.2+ 已捐 Apache,包名改 `org.apache.seata`,与老教程混抄必炸。

### 坑 2:vgroupMapping 没配/名字对不上
报错经典:`can not get cluster name for registry`。
排查链:`seata.tx-service-group`(如 `storage-service-tx-group`)
↔ Nacos 里 `seata.properties` 的 `service.vgroupMapping.storage-service-tx-group=default`
↔ seata-server 集群名。三处一致才通。

### 坑 3:undo_log 忘建/建错库
每个**业务数据源**都要有 undo_log;回滚时找不到日志 → 只能人工修数据。
本示例所有服务共库,新手容易误会"建一张就够"。

### 坑 4:业务表必须有主键
undo_log 靠主键定位行、生成反向 SQL;无主键表回滚直接失败。

### 坑 5:@GlobalTransactional 只加在发起方
参与者(storage/order/account)**不加**任何注解,靠 XID 传播加入全局事务。
新手常犯:每个服务都加 → 嵌套全局事务,行为混乱。

### 坑 6:异常必须"冒泡"回 TM 才能触发回滚
发起方必须感知到失败(抛 RuntimeException)。若下游"吞异常返回 FAIL 字符串"而上游不检查,
事务照常提交。本示例 HomeController 特意写了 `if (!SUCCESS.equals(result)) throw ...`,这就是示范。
真实项目建议:统一异常码 + 异常透传,别靠魔法字符串。

### 坑 7:端口冲突
18083 与 nacos 家族的 consumer 示例撞端口;若同时跑实验,先停掉另一边。

### 坑 8:business-service 的 yml 有个语法错误
```yaml
loadbalancer:
  ribbon:
    enabled:true      # ← 冒号后缺空格!YAML 里这不是 enabled=true,而是个废键
```
应为 `enabled: true`。本示例没用 ribbon,影响为零,但**抄配置时别照搬这个错误**。

### 坑 9:启动造数据的 hack
三个 RM 的 `DatabaseConfiguration` 在 `@Bean` 方法里 delete/insert 重置测试数据——
每次重启数据归位(库存 100/余额 10000/订单清空)。**仅适合 demo,企业代码千万别在配置类里写业务 SQL**。
