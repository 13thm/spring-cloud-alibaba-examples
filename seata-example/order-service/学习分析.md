# Order Service 学习分析 — Seata 链中参与者(RM + 下游调用者)

> 订单服务是全链路**最有戏**的一环:它**既是参与者**(写自己的 order_tbl),
> **又是发起者**(用 RestTemplate 调 account 扣钱)——XID 在它手上要**接力传下去**。
> 它体内还埋着全示例最精妙的"骰子位置学":同样的 50% 异常,掷在 SQL 前和 SQL 后,回滚的分支数完全不同。

## 1. 项目定位:承上启下的链中节点

```
business ──Feign──► order ──RestTemplate(写死IP)──► account
                      │
                      └─ 写 order_tbl(自己的库)
```

| 维度 | 说明 |
|---|---|
| 角色 | **RM**(写订单)+ **中转**(把 XID 继续传给 account) |
| 端口 | 18083(注意与 nacos 家族 consumer 撞端口) |
| 调用方式 | 对下游 account 用**裸 RestTemplate 直连** `127.0.0.1:18084`(pom 里没有 feign!) |
| 事务注解 | 同样**零**——中转 XID 不需要任何注解 |

**为什么它最值得精读?** 因为企业里的真实服务大多长这样:一层套一层的调用链里,
中间节点"既被别人调、又调别人"。Seata 能不能撑住**两跳以上的链式传播**,看它就知道了。

## 3. 核心代码精读:order() 方法的四步棋

```java
@PostMapping(value = "/order", produces = "application/json")
public String order(String userId, String commodityCode, int orderCount) {
    LOGGER.info("Order Service Begin ... xid: " + RootContext.getXID());  // ⓪ XID 已从 business 传来

    int orderMoney = calculate(commodityCode, orderCount);   // ① 算钱:2 × count = 4 元

    invokerAccountService(orderMoney);                       // ② ★ 先调 account 扣钱(下游!)

    final Order order = new Order();                         // ③ 再落自己的订单(INSERT)
    ... // 填充字段
    KeyHolder keyHolder = new GeneratedKeyHolder();
    int result = jdbcTemplate.update(psc, keyHolder);        //    PreparedStatementCreator 方式插入
    order.id = keyHolder.getKey().longValue();               //    拿回自增主键

    if (random.nextBoolean()) {                              // ④ ★ 骰子:50% 抛异常(SQL 之后!)
        throw new RuntimeException("this is a mock Exception");
    }

    return result == 1 ? SUCCESS : FAIL;
}
```

值得咀嚼的**执行顺序**:`先扣钱,后落单`。

- 这是刻意的教学安排:若第②步 account 失败,order 的 INSERT 根本没执行(少一个分支要回滚);
- 业务上,"扣钱成功才允许创建订单"也是一种合理的时序(先验证支付能力)。
- 现实电商往往相反(先建单再支付),顺序由业务语义决定,**Seata 不关心顺序,只关心边界内的异常**。

## 4. 骰子位置学:三种结局与回滚分支数(必看)

全示例有**两个骰子**,位置一前一后:

```
order 骰子:  在自己的 INSERT 之后      ← SQL 后
account 骰子: 在自己的 UPDATE 之前     ← SQL 前
```

推演所有结局(记住:**分支事务在"SQL 真正执行"时才向 TC 注册**):

| 结局 | 概率 | 已注册的分支 | 回滚动作 |
|------|------|-------------|---------|
| ① account 骰子爆(扣钱前) | 50% | 只有 storage | storage 的 undo_log 补偿(count 98→100);order 未插入、account 未扣,**无事可回** |
| ② account 过、order 骰子爆(落单后) | 25% | storage + order + **account** | **三路 undo_log 全部反向补偿**:库存恢复、订单删除、余额恢复 |
| ③ 全过 | 25% | 三个分支 | 全局提交,删 undo_log,数据永久生效 |

**这个表是理解 AT 的试金石**,三个推论:

1. **"SQL 前抛异常"的服务自己不需要回滚**——它什么都没做,连分支都没注册。这就是 account 骰子的位置含义。
2. **"SQL 后抛异常"才考验回滚**——order 的骰子掷在 INSERT 之后,undo_log 里已有镜像,全局回滚时这条 INSERT 会被反向补偿(DELETE)。
3. **回滚与"谁惹的祸"无关**——不管异常出在哪,TC 令**所有已注册分支**统一补偿。第②种结局里 account 是"受害者"(它明明扣钱成功了),照样要回滚——**全局事务一荣俱荣一损俱损**。

## 5. XID 二次接力:order→account

business→order 走 Feign,order→account 走**裸 RestTemplate**——两种工具接力传同一个 XID:

```
business                    order                       account
RootContext: XID=A
  │ Feign(SeataFeignClient 包装)
  │ 请求头 TX_XID=A
  └──────────────► 收到 → RootContext 绑定 A
                    │ RestTemplate(SeataRestTemplateInterceptor 拦截)
                    │ 请求头 TX_XID=A          ★ 二次接力!
                    └──────────────► 收到 → RootContext 绑定 A
                                      account 的日志打印 xid 与上游相同
```

这证明:**XID 传播与调用工具解耦**,Feign→RestTemplate 混用链路照样全员入伙。
前提只有一个:每个服务的 starter 都把"取头/塞头"的机器装好了(引依赖即得)。

> ⚠️ 但注意:order 的 RestTemplate 是**写死 IP 直连**(`127.0.0.1:18084`)。
> XID 传播没问题,**可扩展性有问题**——account 多实例时它永远只打一个,还绕过了注册中心(见坑 2)。

## 6. JDBC 细节:为什么用 PreparedStatementCreator + KeyHolder

storage 用的是简单写法 `jdbcTemplate.update(sql, args)`,order 却"绕"了一大圈:

```java
jdbcTemplate.update(new PreparedStatementCreator() {
    @Override
    public PreparedStatement createPreparedStatement(Connection con) throws SQLException {
        PreparedStatement pst = con.prepareStatement(
                "insert into order_tbl (user_id, commodity_code, count, money) values (?, ?, ?, ?)",
                PreparedStatement.RETURN_GENERATED_KEYS);      // ★ 声明"我要拿回自增键"
        pst.setObject(1, order.userId);
        ...
        return pst;
    }
}, keyHolder);

order.id = keyHolder.getKey().longValue();                     // ★ 拿回数据库生成的主键
```

**原因:INSERT 后要拿自增主键** `order.id`(打日志用)。两种写法的取舍:

| 写法 | 能拿自增主键? | 适用 |
|------|--------------|------|
| `update(sql, args...)` | ❌ | 不关心主键 |
| `update(PreparedStatementCreator, KeyHolder)` | ✅ | 需要回填主键 |
| `SimpleJdbcInsert`(更简洁的替代) | ✅ | 企业里常用它替代上面 |

> 这是纯 JDBC 知识点,与 Seata 无关——但**真实业务 90% 的 INSERT 都需要主键回填**,值得记住。

## 7. 企业里怎么用?

### 7.1 链中节点的标准姿势(本模块的模板价值)
- 入口(Controller/Service)不写事务注解,**靠 XID 入伙**
- 调下游时用 Feign/RestTemplate 正常调,**starter 自动续传 XID**
- 自己的 DB 写操作自动成为分支事务
- **一个服务串起 N 层调用,事务照样罩得住**——这就是"编排自由"的底气

### 7.2 订单服务的真实形态(与本 demo 的差距)
```
demo:算钱 = 2 × count(硬编码)
真实:调"价格服务/营销服务"算价 → 优惠券核销 → 库存 → 支付 → 落单 → 通知
```
企业里的 advice:
- 全局事务**只包核心资金流**(扣库存+扣钱+落单),优惠券/通知等旁路放事务外(消息驱动)
- 链上每多一环,全局锁持有时间越长、吞吐越低——**边界要小**,这是架构纪律

### 7.3 中间件调用的"事务边界"原则
```
✅ 边界内:DB 写操作(可回滚)
❌ 边界内:发短信/发 MQ/调第三方支付(不可回滚!外部世界没有 undo_log)
```
不可回滚动作要么挪到事务提交后,要么用事务消息/本地消息表兜底。demo 没有这类动作,纯 DB,才敢这么玩。

### 7.4 对下游的调用方式选型
demo 用写死 IP 的 RestTemplate 是反面教材;企业标准:Feign + 服务名(负载均衡+熔断+重试策略统一治理)。

## 8. ⚠️ 注意事项与坑

### 坑 0:parent 链断裂(同全家族)→ 见总览坑 0

### 坑 1:两处 RestTemplate 定义位置不一致
business 把 RestTemplate Bean 放启动类里,order 也放启动类——能跑但不规范;企业放独立 `config/` 类
(storage 的 DatabaseConfiguration 就规范些)。小问题,见贤思齐即可。

### 坑 2:写死 IP 直连下游
`http://127.0.0.1:18084/account`:
- 容器/K8s 环境直接失效(没有 127.0.0.1 的 account)
- 单实例假设:account 扩容无效
- 绕过负载均衡与健康检查
demo 图省事,**生产必须服务名调用**。

### 坑 3:骰子导致"实验结果随机"带来的困惑
新手常见疑问:"为什么有时数据回滚有时不回?"——因为异常点不同,参与分支数不同(见第 4 节表)。
做实验时要**对着日志的 xid 和报错位置**分析这次是哪种结局,别盲目重试。

### 坑 4:`random.nextBoolean()` 抛异常前的日志
骰子爆时方法异常终止,`Order Service End ... Created` 不会打印——用日志判断"这次死在哪一步"很可靠:
```
看到 "Order Service Begin ... xid: xxx" 而无 "End" → 死在 order 内部
account 日志有 xid 无 "End"                        → 死在 account 骰子
```

### 坑 5:TRUNCATE 造数据的位置
order 的 DatabaseConfiguration 用 `TRUNCATE TABLE order_tbl` 清空订单(storage 用 delete+insert,account 同)。
**TRUNCATE 是 DDL**——它隐式提交、绕过事务。若有人"聪明地"把造数据逻辑挪进事务方法里,行为会很诡异。
再次强调:**这种造数据 hack 仅限 demo**。

### 坑 6:实体类 public 字段
`Order` 全 public 字段无 getter/setter——demo 风格;企业用 Lombok/标准 POJO,别学。

### 坑 7:金额用 int
`money int` 存"2 × count"的整数——真实资金必须 `DECIMAL`+金额服务统一换算,demo 的简化别照抄。

## 9. 动手练习

1. **验证第 4 节的结局表**:连刷 `/seata/feign` 十几次,记录每次结果;对照三个服务日志里的 xid 与报错位置,归类属于结局①/②/③,统计比例是否约 50/25/25
2. **数分支**:成功链路中在 Seata 控制台(7091)观察全局事务下的分支列表(应该 3 个);失败瞬间看被回滚的分支数差异
3. **改骰子做对照实验**:把 account 的 `random.nextBoolean()` 挪到 `jdbcTemplate.update()` **之后**,
   再触发——现在结局①也会产生 account 分支并回滚。亲手验证"分支注册发生在 SQL 执行时"
4. **看 INSERT 的反向补偿**:结局②发生时,查 `undo_log` 回滚前的瞬间(或 debug 日志),看 INSERT 的 undo 是 DELETE 补偿
5. **打通扩展性**:给 account 再起一个实例(改端口),把 order 的 RestTemplate 换成 `@LoadBalanced` + 服务名 URL,
   验证 XID 在负载均衡下仍正确传播到两个实例
6. **进阶**:把 order→account 改成 Feign 接口(pom 补依赖),对比两种调用在代码整洁度上的差异

### 一句话总结

> order-service 证明了 Seata 的两个"扛把子"能力:**链式传播**(XID 经 Feign 进、经 RestTemplate 出,二次接力不断链)
> 和**分支纪律**(分支在 SQL 执行时才注册——骰子掷在 SQL 前后,决定了回滚舞台上有几个演员)。
> 它同时暴露了 demo 的工程短板:写死 IP 直连、硬编码价格——这些正是企业版要修的地方。
