## 1. 项目定位:链尾,动钱的那一站

```
business ─Feign─► storage(扣库存)
       └─Feign─► order(落单) ─RestTemplate─► ★account(扣余额)  18084
                                           库表: account_tbl (user_id 唯一, money)
```

| 维度 | 说明 |
|---|---|
| 角色 | **RM**,链路终点(不再调任何人,pom 里连 RestTemplate 都没有) |
| 动作 | `money = money - 4`(user_id=U100001) |
| 骰子 | `random.nextBoolean()` 掷在 **UPDATE 之前**(与 order 相反!) |

它是四个模块里**代码最少**的(一个 Controller + 一个配置类),
但"钱"字让它成为企业视角下**最值得多聊几句**的模块。

## 2. 项目结构:全家最简

```
account-service

└── src/main
```

**没有 controller/config 子包**(storage 有)——四个模块的包结构各不相同,恰好展示了
"demo 代码风格不统一"这一现实;企业里应有统一的工程脚手架约束。

## 3. 核心代码:骰子掷在 SQL 之前

```java
@PostMapping(value = "/account", produces = "application/json")
public String account(String userId, int money) {
    LOGGER.info("Account Service ... xid: " + RootContext.getXID());  // XID 从 order 二次接力而来

    if (random.nextBoolean()) {                       // ★ 骰子在 SQL 之前!
        throw new RuntimeException("this is a mock Exception");
    }

    int result = jdbcTemplate.update(
            "update account_tbl set money = money - ? where user_id = ?",
            new Object[] { money, userId });          // UPDATE 执行时才注册分支
    ...
}
```

与 order 骰子的位置对比(复习上一讲的第 4 节表):

```
account 骰子爆(50%):
   异常发生在 UPDATE 之前 → 本服务一个分支都没注册
   → 全局回滚时,TC 的补偿名单里根本没有 account
   → 实际需要 undo_log 补偿的只有 storage(order 的 INSERT 也没来得及执行)

order 骰子爆(25%):
   account 已正常执行完(分支已注册)
   → 回滚名单:storage + order + account 三家
```

**一句话:骰子在 SQL 前后,决定了这个服务在回滚舞台上是"演员"还是"观众"。**

另注意入参风格:`public String account(String userId, int money)` **无任何注解**,
靠 Spring MVC 的参数名匹配表单/查询参数(business 发的是 `APPLICATION_FORM_URLENCODED` 表单)。
能跑,但**企业代码显式 `@RequestParam`** 更安全(编译参数名丢失时不炸)。

## 4. 进阶一:AT 的隔离性,脏读风险与 @GlobalLock

动钱的服务迟早会被人问:"Seata 的隔离级别够不够?" 这节把话说透。

### 4.1 默认隔离:全局读未提交

```
时刻T1:全局事务A(买2件)在 account 扣了钱 → 一阶段本地事务已提交(9996 已落库!)
        但全局事务A还没结束(等 order/storage 那边收尾)
时刻T2:普通查询(不在任何全局事务里)读到 money=9996
        ↓
时刻T3:全局事务A回滚!9996 被补偿回 10000
        ↓
T2 读到的 9996 = "脏读"(从未真正提交过的数据)
```

根因:**AT 一阶段就提交本地事务**,全局提交前数据对外可见——这正是它高性能的代价。

### 4.2 需要读隔离时:@GlobalLock

```java
// 方式一:只加锁(读取前确保没有未决的全局事务在改这行)
@GlobalLock
@Transactional
public Account getAccount(String userId) {
    return accountDao.selectForUpdate(userId);      // SELECT ... FOR UPDATE
}

// 方式二:干脆加入全局事务(读写都隔离)
@GlobalTransactional
public ... 
```

`@GlobalLock` 的机制:执行前向 TC 检查目标行是否被别的全局事务锁定 → 锁着就**重试等待** →
保证读到的一定是"全局已提交"的数据。

**企业判断口径**:
- 展示型查询(页面余额)→ 默认即可,短暂脏读无感
- 决策型读取(风控判断、对账、外部分账)**→ 必须隔离**,用 @GlobalLock / 全局事务 / 或走读库延迟

### 4.3 写隔离:全局锁自动管

两个全局事务同时改 `U100001` 的余额?后到者在 TC 的行锁上重试等待(`client.rm.lock.retryTimes`),
超时回滚自己。**写冲突 AT 已天然防护,读隔离才要你操心**——这是最常见的认知盲区。

## 5. 进阶二:热点账户难题

demo 里 `U100001` 一个用户一行数据,一切岁月静好。真实世界的账户表是这样的:

```
头部主播/平台大账户:每秒成千上万笔扣款,全打在同一行 money 上
   ↓ AT 全局行锁
所有全局事务在这一行上排队 → 锁等待超时 → 大面积回滚 → 吞吐崩盘
```

企业的典型解法(资金架构常识):

| 方案 | 思路 | 适用 |
|------|------|------|
| **余额拆分(子账户)** | 大账户拆 N 行(桶),扣款路由到某桶;汇总时 SUM | 通用,首选 |
| **缓冲记账** | 扣款先进 Redis/内存累计,异步批量落库 | 允许短暂延迟的场景 |
| **TCC** | Try 冻结、Confirm 扣减、Cancel 解冻——锁粒度自己控制 | 资金强实时 |
| **账务(流水)倒推** | 不存余额只存流水,余额=期初+SUM(流水),天然无热点行 | 财务级账本 |

> 这就是总览说的:"**不是所有跨服务写操作都适合 AT**"——账户恰是 AT 弱点与钱的安全重叠的地方,
> 企业里资金链路更多用 TCC/账务模式,AT 多用于订单、库存等一般业务。

## 6. 企业里怎么用?(资金安全的完整视角)

### 6.1 真实账户服务的标配(demo 全没有)

```
① 幂等:同一笔交易重复请求只扣一次
   (唯一交易号 + 唯一索引/Redis setnx;Seata 重试可能重发分支指令)
② 流水:每次变动记 account_flow(交易号、变动前后金额、原因)
   ——对账、审计、故障恢复全靠流水,余额只是缓存
③ 余额校验:money - 扣款 >= 0,超扣拒绝(demo 没做,能扣成负数!)
④ 双记录账:借/贷双方同时记(复式记账)
⑤ 金额精度:DECIMAL 而非 int;分层币种/汇率
⑥ 对账系统:每日 T+1 对账,差异自动/人工处理
```

对照 demo:`update account_tbl set money = money - ?` 一句裸 SQL,以上六条全无——
**这就是"示例代码"与"资金服务"之间的鸿沟**,面试聊分布式事务时能讲出这六条,立刻和背题的拉开差距。

### 6.2 Seata 在资金链路的定位建议
```
核心资金(支付/退款/分账)   → TCC 或 账务流水模式(强控制)
一般资金(会员积分/优惠券)   → AT 足够(错了可修)
跨服务业务一致性(订单-库存) → AT 的甜点区(本示例的主场景)
```

### 6.3 回滚失败的兜底
undo_log 损坏/被人绕过 Seata 改数据 → 自动补偿失败 → TC 标记 RollbackFailed 重试。
企业必须配:**人工干预工单 + 按流水反向修复**的流程。Seata 不是银弹,兜底预案是资金系统的底线。

## 7. ⚠️ 注意事项与坑

### 坑 0:parent 链断裂(同全家族)→ 见总览坑 0

### 坑 1:超扣成负数
`money = money - ?` 无下限校验,刷爆了余额能变负。教学实验无妨,**真实代码必须带条件**:
```sql
UPDATE account_tbl SET money = money - ? WHERE user_id = ? AND money >= ?
```
影响行数 0 → 返回 FAIL → 上游抛异常回滚。(顺带这也是乐观式防超扣。)

### 坑 2:幂等缺失
Seata/网络的任何重试都可能让 `/account` 收到重复请求 → 重复扣款。
demo 无交易号无法幂等;企业版第一件事就是加唯一业务单号。

### 坑 3:GET/POST 与参数注解
接口是 POST 但参数裸奔(无 @RequestParam);business 发 FORM 表单能对上。
**参数名依赖编译保留(-parameters)**,换构建配置可能突然拿不到值——显式注解保平安。

### 坑 4:链尾的服务也最容易被"绕过"
账户往往还有**别的入口**(后台调额、运营手动 SQL)。
任何**绕过 Seata 的直接改写**都会破坏 afterImage 校验 → 全局回滚卡死(BranchRollbackFailed)。
企业纪律:**接入 Seata 的表,所有变更通道都必须走 Seata 体系**(或停机窗口改数)。

### 坑 5:脏读排查难
"读到的余额过会儿又变了"——新人以为是 bug,其实是 AT 默认全局读未提交(见 4.1)。
排查思路先问:这个读是决策型还是展示型?决策型加 @GlobalLock。

### 坑 6:重置数据只在启动时
余额重置(10000)发生在启动的 @Bean 里;**跑的过程中刷爆了不会自动恢复**,要重启 account。
做实验前记得"先重启三个 RM 再开刷",保持数据基线一致。

## 8. 动手练习

1. **复现骰子位置差异**:连刷 `/seata/feign`,专门收集"account 骰子爆"的案例,
   确认此时 order 表无新订单、storage 已回滚、account 余额纹丝不动(结局①的现场)
2. **亲眼看脏读(4.1)**:写个普通查询接口(不带任何注解)读余额;
   人为把 business 的某环节 sleep 5 秒拉长全局事务,在 sleep 期间查询——读到的就是"将被回滚的脏数据"
3. **实验 @GlobalLock**:给 2 的查询接口加上 `@GlobalLock + SELECT FOR UPDATE`,重复实验——
   现在查询会**等待**全局事务结束后才返回干净数据
4. **修坑 1**:给 UPDATE 加 `AND money >= ?` 条件,把余额手动改成 2,买 2 件(需 4 元)→
   观察 account 返回 FAIL → 全局回滚,库存复原。体验"参与者主动失败"的正确姿势
5. **压测热点行**(进阶):JMeter 200 并发刷 `/seata/feign`(同一用户),观察全局锁竞争下的
   报错/回滚率;再把账户拆成 10 个子账户行(改表+改扣款逻辑),对比吞吐
6. **思考题**:如果把 account 的扣款换成"调用第三方支付网关"(外部 HTTP),AT 还能回滚吗?
   答案是不能(外部世界无 undo_log)——想清楚为什么,你就理解了"事务边界内只放可补偿资源"的原则

### 一句话总结

> account-service 用最少的代码站在链路终点,却踩在企业最敏感的"钱"上。
> 它的骰子(SQL 前抛)演示了分支注册的时机;它的场景逼出了 AT 的两大深层话题——
> **隔离性**(默认全局读未提交,决策型读取要 @GlobalLock)与**热点行**(账户余额是全局锁的死穴)。
> 企业里资金链路的真相是:幂等、流水、防超扣、对账,一个都不能少;AT 多用于一般业务,核心资金更信 TCC 与账务。
