## 1. 项目定位:全链路响应式的消费者

| | 前面学的 consumer 项目 | **本项目(reactive)** |
|---|---|---|
| Web 容器 | Tomcat + Spring MVC | **Netty + Spring WebFlux** |
| HTTP 客户端 | RestTemplate(阻塞) | **WebClient(非阻塞)** |
| 服务发现接口 | DiscoveryClient | **ReactiveDiscoveryClient** |
| 负载均衡 | SCLB(轮询等) | **SCLB 响应式实现(ReactorLoadBalancer)** |
| 返回类型 | String/对象 | **Mono/Flux(异步流)** |

它演示两件事:
1. **响应式地查服务列表**(ReactiveDiscoveryClient)
2. **响应式地发起带负载均衡的远程调用**(`@LoadBalanced` 的 WebClient)

服务名 `service-consumer-reactive`,端口 18083(与其他 consumer 相同,**同时只能跑一个**),调用的仍是 `service-provider`。

## 2. 背景:阻塞 vs 非阻塞,为什么要有响应式?

### 2.1 传统阻塞模型(Servlet/Tomcat)

```
每个请求占用一个线程(线程池默认 200)
请求A → 线程1 ──调用下游──等1秒──(线程1干等,什么也不干)──返回
请求B → 线程2 ──等1秒──...

并发 10000 个慢请求?需要 10000 个线程 → 内存爆炸/频繁上下文切换
```

### 2.2 响应式模型(Netty 事件循环)

```
少量事件循环线程(≈CPU核数)处理成千上万的连接
请求A → 注册"我等下游响应" → 线程立刻去处理请求B(不等!)
        └─下游响应到达 → 事件通知 → 回来继续处理A

线程数极少,吞吐量极高 —— 代价:代码模型"难懂"(这就是你要学的)
```

### 2.3 什么时候值得上响应式?(企业决策口径)

- ✅ IO 密集:网关、BFF、聚合接口(等下游的占比高,等待期可腾出线程)
- ❌ CPU 密集:计算逻辑重的服务,收益小、复杂度高
- 经验:**响应式收益在"等待"上,没有大量等待就别折腾**

```
nacos-reactivediscovery-consumer-example

└── src/main
    ├── java/com/alibaba/cloud/examples
    │   ├── ConsumerReactiveApplication.java  # 启动类
    │   ├── WebClientConfiguration.java       # ★ @LoadBalanced 的 WebClient.Builder
    │   └── MyController.java                 # ★ Mono/Flux 返回值
```

| 依赖 | 作用 | 与阻塞版的差异 |

## 4. 核心概念:MVC→WebFlux 的"翻译对照表"

| Spring MVC(阻塞世界) | WebFlux(响应式世界) | 说明 |
|---|---|---|
| `RestTemplate` | `WebClient` | HTTP 客户端 |
| `DiscoveryClient` | `ReactiveDiscoveryClient` | 服务发现(方法返回 Mono/Flux) |
| Controller 返回 `String` | 返回 `Mono<String>` | 0~1 个异步值 |
| 返回 `List<T>` | 返回 `Flux<T>` | 0~N 个异步值(流) |
| `@LoadBalanced RestTemplate` | `@LoadBalanced WebClient.Builder` | 客户端负载均衡 |
| Tomcat 线程池 | Netty EventLoop | 容器模型 |
| `spring-boot-starter-web` | `spring-boot-starter-webflux` | starter |

**Mono/Flux 一分钟入门**(够你读懂本项目):

```
Mono<String>  : "未来会有一个 String"(0或1个) → 直接当返回值写
Flux<String>  : "未来会陆续来一批 String"(0~N个) → 流式返回

不调用 .block() —— 响应式代码里阻塞是大忌
```

## 5. 逐文件精读

### 5.1 ConsumerReactiveApplication.java

```java
@SpringBootApplication
@LoadBalancerClients({
        @LoadBalancerClient("service-provider")   // 与第一个consumer相同的"空配置"写法
})
public class ConsumerReactiveApplication { ... }
```

- **没写 `@EnableDiscoveryClient`**——再次印证:现代版本里它是声明性的,nacos starter 自动装配
- `@LoadBalancerClient("service-provider")` 没带 configuration,**等于没有实际定制**(老朋友了,正确用法见 sclb 项目文档 6.3)

### 5.2 WebClientConfiguration.java

```java
@Configuration
public class WebClientConfiguration {

    @Bean
    @LoadBalanced                                // ★ 响应式客户端负载均衡开关
    public WebClient.Builder webClient() {
        return WebClient.builder();
    }
}
```

**三个易错点,初学者必看:**

1. **@LoadBalanced 必须打在 Builder 上**,官方模式就是"注入 `WebClient.Builder`,用时 `.build()`"。如果你自己 `new WebClient.create()` 并注入,负载均衡失效(URL 里的服务名没人解析)。
2. 为什么注册 Builder 而不是 WebClient?——Builder 上可以被 LoadBalancer 挂过滤器(ExchangeFilterFunction),由使用方按需 build 出多个 client。
3. Controller 里是 `webClientBuilder.build().get()...`,每次 build 即可,Builder 可复用。

### 5.3 MyController.java(全部业务就两个接口)

```java
@RestController
public class MyController {

    @Resource
    private ReactiveDiscoveryClient reactiveDiscoveryClient;  // 响应式服务发现

    @Resource
    private WebClient.Builder webClientBuilder;               // 负载均衡 WebClient

    // ① 列出 service-provider 所有实例的 host:port —— 返回 Flux(流式多值)
    @GetMapping("/all-services")
    public Flux<String> allServices() {
        return reactiveDiscoveryClient.getInstances("service-provider")
                .map(instance -> instance.getHost() + ":" + instance.getPort());
    }

    // ② 响应式调用 provider 的 /echo 接口 —— 返回 Mono(单值)
    @GetMapping("/service-call/{name}")
    public Mono<String> serviceCall(@PathVariable("name") String name) {
        return webClientBuilder.build().get()
                .uri("http://service-provider/echo/" + name)   // 服务名 URL → LB解析
                .retrieve()                                     // 发起请求(异步)
                .bodyToMono(String.class);                      // 响应体 → Mono<String>
    }
}
```

对照阻塞版"翻译"一下就懂:

```java
// 阻塞等价代码(方便理解,不是本项目代码)
discoveryClient.getInstances("service-provider").stream().map(i -> host+":"+port)...
restTemplate.getForObject("http://service-provider/echo/" + name, String.class);
```

## 6. 一次请求的链路:负载均衡在响应式下怎么工作

`GET /service-call/hi` 的全链路:

```
Netty EventLoop 收到请求
   ↓
MyController.serviceCall("hi") 立即返回一个 Mono(注意:此刻请求还没发出去!)
   ↓ Spring 把 Mono 交给框架订阅,异步驱动:
WebClient 构造请求 http://service-provider/echo/hi
   ↓
[ReactiveLoadBalancerExchangeFilterFunction]        ← @LoadBalanced 挂的过滤器
   ↓  异步选择实例(不阻塞线程!)
ReactorLoadBalancer.choose()
   → ServiceInstanceListSupplier 从 Nacos 拿实例列表
   → 轮询/随机选一个
   ↓
真实请求 http://<实例IP:PORT>/echo/hi 发出
   ↓ 响应到达(事件回调,不占线程等待)
bodyToMono → 数据流回 Controller → 写回给浏览器
```

**与阻塞版最本质的区别:等待下游期间,Netty 线程去服务别的请求了。**
这也解释了为什么 SCLB 的核心接口是 `Mono<Response<ServiceInstance>> choose()`——它自己就是响应式的(sclb 项目文档里你见过的 RandomLoadBalancer 实现的正是这套接口)。

## 7. 企业里怎么用?

### 7.1 最大落地场景:Spring Cloud Gateway
网关每天承接着"等上游响应"的海量等待,是响应式价值最高的地方。**Spring Cloud Gateway 全家桶 = WebFlux + WebClient + Reactor LoadBalancer**——你现在学的这三样,正是 Gateway 的底层。企业里你写的 Gateway 过滤器(鉴权、限流、改写),返回值就是 Mono/Flux。

### 7.2 高并发聚合层(BFF)
一个接口聚合 5 个下游:`Mono.zip(a, b, c, d, e)` 五路并发、总耗时≈最慢一路;阻塞版要开 5 个线程手工编排。

### 7.3 团队采用的实际口径
- 大多数业务服务仍是 MVC(开发效率、生态成熟、事务简单)
- **网关/长连接推送/IO密集中间层**用响应式——两种技术栈并存是常态
- 用了响应式,配套也要响应式:**R2DBC 替代 JDBC**、Redis 用 Lettuce(reactive API)等,否则链路上一个阻塞点就前功尽弃

### 7.4 可观测性
响应式链路跨线程执行,TraceId 传递要用 Reactor Context 而非 ThreadLocal,SkyWalking/Zipkin 需要专门的 reactor 插件——企业落地时这是排障的关键准备。

## 8. ⚠️ 注意事项与坑

### 坑 0:parent 链断裂(同家族其他项目)
根 pom 是 `com.thm.cloud` 空壳,`${revision}`、BOM 全缺。修复见 provider 文档坑 0。

### 坑 1:web 和 webflux 不能同时引入
类路径同时有 `spring-boot-starter-web` 和 `webflux` 时,Spring Boot 会**优先按 Servlet 栈启动**(退回 Tomcat+MVC),`ReactiveDiscoveryClient` 等 WebFlux 语义可能行为不一致。二选一!(从别的项目拷 pom 时最容易犯)

### 坑 2:`@LoadBalanced` 打错位置 → 服务名没人解析
- ✅ 打在 `WebClient.Builder` 的 @Bean 上(本项目写法)
- ❌ 自己 new WebClient / 打在 WebClient 上 / 在 Builder 之外 build——请求发出 `service-provider` 会被当域名解析,报 `UnknownHostException`

### 坑 3:响应式链路里严禁阻塞调用
链路中出现 `JDBC 调用`、`RestTemplate 调用`、`.block()`、`Thread.sleep`,Netty 的 EventLoop 被占住 → **整个服务并发能力崩塌**(比阻塞版更糟)。练习:在 serviceCall 里加 `Thread.sleep(2000)`,并发 100 请求观察吞吐骤降。

### 坑 4:`@LoadBalancerClient("service-provider")` 仍是空配置
老问题重现:没配 configuration 就没有实际定制。想自定义随机策略,照搬 sclb 项目的 `MyLoadBalancerConfiguration`(它实现的 `ReactorServiceInstanceLoadBalancer` 本来就是响应式接口,WebClient 场景通用)。

### 坑 5:端口 18083 与其他 consumer 冲突
家族里三个 consumer 都用 18083,同时启动必撞端口;想并行对比,改 `server.port`。

### 坑 6:调试与排障方式不同
断点单步跨线程会"跳来跳去";日志要打全链路需 `Hooks.onEachOperator` 或 log() 操作符(`mono.log()`)。初学时多在链尾加 `.doOnError(e -> log.error(...))` 兜住异常——**WebClient 的异常不会自己冒出来,没人订阅错误就是"静默吞掉"**。

### 坑 7:provider 不启动时的现象
`/all-services` 返回**空流**(不是错误,Flux 没元素就是 200+空body);`/service-call` 返回 503。别把"空"当 bug。

## 9. 动手练习

1. **跑通基础链路**:Nacos → provider(建议2实例)→ 本项目;`curl http://localhost:18083/all-services`(看到实例列表)和 `curl http://localhost:18083/service-call/hi`
2. **多刷 service-call**,在 provider 日志观察轮询命中(体验响应式 LB 与阻塞版行为一致)
3. **Flux 流式体验**:临时加一个 `Flux.interval` 接口,浏览器里看数据"一条条到达":
   ```java
   @GetMapping("/stream")
   public Flux<String> stream() {
       return Flux.interval(Duration.ofSeconds(1)).map(i -> "tick " + i);
   }
   ```
4. **验证坑 2**:注入一个非 @LoadBalanced 的 WebClient 调用服务名,看 UnknownHostException
5. **并发对比实验**(选做):写一个阻塞版接口(Thread.sleep 1s)+ wrk/ab 压 200 并发,对比本项目 `/service-call`(下游 /sleep 1s)的吞吐差异,亲身感受事件循环的价值
6. **进阶**:把 sclb 项目的 RandomLoadBalancer 搬进来,给 `service-provider` 配随机策略,验证响应式场景同样生效

### 一句话总结

> 本项目把消费者链路的每一环都换成了非阻塞版:**WebFlux/Netty 跑应用、ReactiveDiscoveryClient 查实例、@LoadBalanced WebClient 发请求、Mono/Flux 承载数据**。它最直接的现实意义是——这就是 Spring Cloud Gateway 的底层模型;学习它的同时务必记住两条铁律:**别混用两个 web starter,响应式链路里不能有阻塞调用**。
