## 1. 项目定位:它是干嘛的?

一句话:**演示用 Spring Cloud LoadBalancer(替代 Netflix Ribbon)做客户端负载均衡,包括"自定义随机策略"和"区域优先策略"两种玩法。**

| 角色 | 服务名 | 端口 | 说明 |
|------|--------|------|------|
| 消费者 | `service-consumer-sclb`(**本项目**) | 18083 | 调用方,**注意:不注册自己到 Nacos** |
| 提供者 | `service-provider`(同级 module) | 随机 | 被调方,已在本仓库中 |

三个演示主题:

1. **自定义负载均衡器**:手写一个 `RandomLoadBalancer`(随机选实例),通过 `@LoadBalancerClient` 只对 `service-provider` 生效
2. **zone 区域优先**:配置 `zone-preference`,优先调用同区域的 provider 实例
3. **Sentinel 完整集成**:限流 + 熔断 + 降级(上个项目中"被注释"的完整版)

## 4. 背景知识:从 Ribbon 到 Spring Cloud LoadBalancer

### 4.1 为什么会有这个项目?

历史脉络:

```
2015~2020:Netflix Ribbon 是 Spring Cloud 客户端负载均衡的事实标准
        ↓ Netflix 停止维护,Ribbon 进入维护模式
2020.0 (Ilford) 起:Spring Cloud 官方移除 Ribbon,推 Spring Cloud LoadBalancer(SCLB)
        ↓
今天:RestTemplate/@LoadBalanced、OpenFeign、Gateway 底层统一使用 SCLB
```

### 4.2 SCLB 的两种配置方式

| 方式 | 适用场景 | 本项目示例 |
|------|---------|-----------|
| **yml 全局配置** `spring.cloud.loadbalancer.configurations` | 用内置策略(轮询/随机/区域优先) | `zone-preference` |
| **代码自定义** `@LoadBalancerClient` + 配置类 | 完全自己写选实例逻辑 | `RandomLoadBalancer` |

### 4.3 SCLB 的关键抽象(读代码前的地图)

```
ServiceInstanceListSupplier   → "去哪拿实例列表"(从 Nacos 拉服务实例,可叠加过滤)
        ↓
ReactorServiceInstanceLoadBalancer → "怎么选一个"(选实例的策略,返回 Mono 响应式)
        ↓
ReactorLoadBalancer<ServiceInstance> → 接口定义,choose() 返回被选中的实例
```

`Mono` 来自 **Reactor 响应式库**:SCLB 内部全异步非阻塞,所以接口签名是 `Mono<Response<ServiceInstance>>` 而不是直接返回实例。初学阶段只需理解:**"Mono 就是'将来会有的一个值',`.map()` 里处理它"**。

## 6. 核心一:自定义负载均衡器 RandomLoadBalancer

这是本项目最重要的代码,三个文件环环相扣:

### 6.1 RandomLoadBalancer.java —— 手写的随机策略

```java
public class RandomLoadBalancer implements ReactorServiceInstanceLoadBalancer {

    private ObjectProvider<ServiceInstanceListSupplier> serviceInstanceListSupplierProvider;
    private final String serviceId;      // 目标服务名,如 service-provider
    private final Random random;

    @Override
    public Mono<Response<ServiceInstance>> choose(Request request) {
        // ① 拿到"实例列表提供者"(它知道去 Nacos 查实例)
        ServiceInstanceListSupplier supplier = serviceInstanceListSupplierProvider
                .getIfAvailable(NoopServiceInstanceListSupplier::new);
        // ② 异步获取实例列表,再 map 成"选一个实例"的响应
        return supplier.get().next().map(this::getInstanceResponse);
    }

    // 核心选实例逻辑
    private Response<ServiceInstance> getInstanceResponse(List<ServiceInstance> instances) {
        if (instances.isEmpty()) {
            return new EmptyResponse();          // 没有实例 → 空响应(调用方会收到 503)
        }
        // ★ 随机挑一个:列表里随机取下标
        ServiceInstance instance = instances.get(random.nextInt(instances.size()));
        return new DefaultResponse(instance);
    }
}
```

**逐行读懂它:**

| 代码 | 含义 |
|------|------|
| `implements ReactorServiceInstanceLoadBalancer` | 实现 SCLB 的负载均衡器接口(它是 `ReactorLoadBalancer<ServiceInstance>` 的子接口) |
| `ObjectProvider<ServiceInstanceListSupplier>` | 惰性获取"实例列表供应商";`ObjectProvider` 让 Bean 可以按需取、允许暂时不存在 |
| `supplier.get().next()` | `get()` 返回 `Flux<List<ServiceInstance>>`(实例列表流),`next()` 取第一帧 → `Mono<List<实例>>` |
| `.map(this::getInstanceResponse)` | 拿到列表后转成"选中一个实例"的响应 |
| `DefaultResponse(instance)` | 包装选中的实例 |
| `EmptyResponse()` | 无可用实例时的"空响应",上层会抛 `No instances available` 类错误 |

> 💡 对比:Spring Cloud 默认策略是 `RoundRobinLoadBalancer`(轮询),核心差异就是最后一行——**轮询用 `position % 实例数`,随机用 `random.nextInt(实例数)`**。你会发现源码极其简单,消除神秘感。

### 6.2 MyLoadBalancerConfiguration.java —— 注册负载均衡器 Bean

```java
public class MyLoadBalancerConfiguration {          // ★ 注意:故意不加 @Configuration!

    @Bean
    @ConditionalOnMissingBean
    public ReactorLoadBalancer<ServiceInstance> reactorServiceInstanceLoadBalancer(
            Environment environment,
            LoadBalancerClientFactory loadBalancerClientFactory) {
        // 从环境变量取"当前要为哪个服务创建负载均衡器"
        String name = environment.getProperty(LoadBalancerClientFactory.PROPERTY_NAME);
        return new RandomLoadBalancer(
            loadBalancerClientFactory.getLazyProvider(name, ServiceInstanceListSupplier.class),
            name);
    }
}
```

**为什么不加 `@Configuration`?这是 SCLB 的经典设计考点:**

SCLB 为**每个服务名**创建一个独立的**子上下文**,这个类会被放入 `service-provider` 的子上下文里:
- 加了 `@Configuration` → 可能被主上下文组件扫描到 → 对**所有服务**生效(污染全局)
- 不加 → 只作为参数传给 `@LoadBalancerClient`,只在**对应服务的子上下文**中生效 ✅

(和 OpenFeign 的 `FeignConfiguration` 不加 `@Configuration` 是同一个道理,见 8.2)

### 6.3 MySCLBConfiguration.java —— 把配置绑定到服务名

```java
@Configuration
@LoadBalancerClient(value = "service-provider", configuration = MyLoadBalancerConfiguration.class)
public class MySCLBConfiguration {
}
```

**这就是上个项目"坑 3"的正确写法!** 上个项目只写了 `@LoadBalancerClient("service-provider")` 没给 configuration,等于空转;本项目补上了 `configuration = MyLoadBalancerConfiguration.class`,意思是:

> **"以后所有对 `service-provider` 的负载均衡,都用 MyLoadBalancerConfiguration 里定义的 RandomLoadBalancer"**

### 6.4 SCLB 子上下文机制图解

```
主应用上下文 (service-consumer-sclb)
│
├── RestTemplate(@LoadBalanced) ──┐
│                                 ▼
│              LoadBalancerClientFactory(工厂)
│                    │ 为每个服务名创建独立"子上下文"
│                    │
│                    ├── 子上下文: "service-provider"      ★
│                    │     └── MyLoadBalancerConfiguration
│                    │           └── RandomLoadBalancer Bean ──→ choose() 随机选实例
│                    │     └── (yml 的 zone-preference 也在这个子上下文生效)
│                    │
│                    └── 子上下文: "other-service"(如有)
│                          └── 用默认 RoundRobin 轮询
```

**默认子上下文的构造线索**:`LoadBalancerClientFactory` 的 `name`(属性 `loadbalancer.client.name`)就是目标服务名,所以 6.2 中 `environment.getProperty(PROPERTY_NAME)` 拿到的正是 `service-provider`。

## 7. 核心二:zone 区域优先负载均衡

### 7.1 是什么?为什么需要?

多机房/多地域部署时,跨机房调用延迟高。**区域优先(zone-preference)**:优先调用与自己同区域的实例,同区域没有才考虑其他。

### 7.2 配置怎么生效?

```yaml
spring:
  cloud:
    loadbalancer:
      configurations: zone-preference   # 启用内置 ZonePreference 策略
      zone: hangzhou                    # 我在杭州区
```

SCLB 看到这行配置,会自动装配 `ZonePreferenceServiceInstanceListSupplier`,它在"实例列表供应商"链上**加一层过滤/排序**:优先返回 `metadata` 中 `zone=hangzhou` 的 provider 实例。

### 7.3 TestController 中的 /zone 接口 —— 亲眼验证

```java
@Value("${spring.cloud.loadbalancer.zone:null}")
private String zone;                        // 注入 yml 里的 hangzhou

@GetMapping("/zone")
public String zone() {
    return "consumer zone " + zone + "\n"          // 消费者在哪个区
        + urlCleanedRestTemplate
            .getForObject(SERVICE_PROVIDER_ADDRESS + "/zone", String.class);  // 远程问 provider 在哪个区
}
```

provider 端(`nacos-discovery-provider-example` 的 `EchoController`)对应接口:

```java
@GetMapping("/zone")
public String zone() {
    Map<String, String> metadata = ...;  // Nacos 实例元数据
    return "provider zone " + metadata.get("zone");
}
```

**一次 `/zone` 调用的效果**(provider 带元数据时):

```
consumer zone hangzhou
provider zone hangzhou
```

### 7.4 关键前提:provider 要声明自己的 zone

实例的 `zone` 来自 **Nacos 注册元数据(metadata)**。provider 需要在注册时带上,例如:

```yaml
# provider 的 application.yml
spring:
  cloud:
    nacos:
      discovery:
        metadata:            # ★ 注册元数据:我是杭州区的
          zone: hangzhou
```

⚠️ 当前 provider 模块的 yml **没有配置 metadata.zone**,所以直接跑 `/zone` 会看到 `provider zone null`,且区域过滤实际不生效(见第 12 节坑 2)。

### 7.5 自定义 RandomLoadBalancer 和 zone-preference 同时存在,谁生效?

yml 的 `zone-preference` 影响的是**实例列表供应商**(先过滤出杭州区实例);
`@LoadBalancerClient` 的 RandomLoadBalancer 影响的是**选实例策略**(在过滤后的列表里随机挑)。
两者是**上下游叠加关系,不冲突**:

```
Nacos 全部实例 → [zone-preference 过滤:只留 hangzhou] → [RandomLoadBalancer:随机挑一个]
```

## 8. 核心三:这次 Sentinel 是"真的"(UrlCleaner/Fallback 都接上了)

### 8.1 UrlCleaner 终于被"接线"了

上个项目的疑问在这里有了答案。`RestTemplateConfiguration.java`:

```java
@Configuration
public class RestTemplateConfiguration {

    @LoadBalanced
    @Bean
    @SentinelRestTemplate(urlCleanerClass = UrlCleaner.class, urlCleaner = "clean")  // ★ 没有注释!
    public RestTemplate urlCleanedRestTemplate() { return new RestTemplate(); }

    @LoadBalanced
    @Bean
    @SentinelRestTemplate                                    // 普通 Sentinel 包装
    public RestTemplate restTemplate() { return new RestTemplate(); }
}
```

接线链路:`@SentinelRestTemplate(urlCleanerClass=UrlCleaner.class, urlCleaner="clean")` → Sentinel 给 RestTemplate 织入拦截器 → 每次请求**反射调用** `UrlCleaner.clean(url)` → 把 `/echo/abc` 归并成 `/echo/{str}` → 与 flowrule.json 的资源名 `GET:http://service-provider/echo/{str}` 对上。

**验证方法**:调用 `/echo-rest/xxx` 时看日志输出 `enter urlCleaner`,证明清洗已介入。

### 8.2 Fallback 这次也真的生效了

`EchoClient.java`(对比上个项目缺属性的写法):

```java
@FeignClient(
    name = "service-provider",
    fallback = EchoClientFallback.class,          // ★ ① 指定降级类
    configuration = FeignConfiguration.class      // ★ ② 指定配置类(里面有 Fallback 的 Bean)
)
public interface EchoClient { ... }
```

`FeignConfiguration.java`:

```java
public class FeignConfiguration {                 // ★ 故意不加 @Configuration(原因同 6.2)
    @Bean
    public EchoClient echoClientFallback() {
        return new EchoClientFallback();
    }
}
```

生效三件套全部就位:
1. pom 有 `spring-cloud-starter-alibaba-sentinel` ✅
2. yml 有 `feign.sentinel.enabled: true` ✅
3. `@FeignClient` 声明了 `fallback` + `configuration` ✅

**效果**:当 `/echo/{str}` 触发限流(flowrule QPS>2)或 provider 不可用时,返回 `"echo fallback"` 而不是 500。

### 8.3 规则文件(与上个项目基本一致,阈值不同)

`flowrule.json`(**count=2**,上个项目是 1):

```json
{ "resource": "GET:http://service-provider/echo/{str}",
  "controlBehavior": 0, "count": 2, "grade": 1, "limitApp": "default", "strategy": 0 }
```
→ 对 echo 接口,QPS 超过 2 就限流走降级。

`degraderule.json`:与上个项目相同(test/index/sleep/divide 的慢调用比例、异常比例熔断规则)。

## 10. 一次请求的完整流程图

以 `GET http://localhost:18083/echo-rest/hi` 为例(串联本项目所有知识点):

```
HTTP 客户端
   │
   ▼
service-consumer-sclb (18083, 未注册到 Nacos)
   │ TestController.rest("hi")
   ▼
urlCleanedRestTemplate ──► [Sentinel 拦截器]
   │                          │
   │                     UrlCleaner.clean("http://service-provider/echo/hi")
   │                          │ → "http://service-provider/echo/{str}"
   │                     按 flowrule.json 检查 QPS>2?
   │                     超限 → 直接抛异常/走降级,不再发请求
   ▼ 通过
[LoadBalancerClientFactory]  ──取子上下文──►  "service-provider" 子上下文
   │                                          ├── zone-preference 供应商:只挑 zone=hangzhou 的实例
   │                                          └── RandomLoadBalancer.choose():随机选 1 个
   ▼
真实 HTTP:GET http://<选中实例IP:PORT>/echo/hi
   │
   ▼
service-provider(已注册到 Nacos,含实例列表)
   返回 echo 响应
   │
   ▼(若 provider 挂了/超时/被限流)
Sentinel 熔断/降级 → Feign 场景返回 "echo fallback"
```

## 12. ⚠️ 注意事项与坑

### 坑 1:parent 指向官方根 pom,本地构建可能失败

本 module 的 pom:

```xml
<parent>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-alibaba-examples</artifactId>
    <version>${revision}</version>
    <relativePath>../../pom.xml</relativePath>
</parent>
```

它依赖**仓库根目录** `E:\code\java_code\spring-cloud-alibaba-examples\pom.xml`(定义了 `${revision}`、BOM 版本管理等)。
**必须在仓库根目录构建**,例如:

```bash
cd E:/code/java_code/spring-cloud-alibaba-examples
mvn -pl nacos-example/nacos-discovery-example/nacos-discovery-consumer-sclb-example -am spring-boot:run
```

如果根 pom 不存在/不完整,需要自行补 BOM(Spring Boot 3.x + Spring Cloud 2023.0.x + Spring Cloud Alibaba 2023.0.x)。

### 坑 2:provider 默认没有 zone 元数据,区域优先不生效

provider 的 `application.yml` 没有 `metadata.zone` 配置:
- `/zone` 会返回 `provider zone null`
- `zone-preference` 过滤时找不到 hangzhou 实例

**修复**:给 provider 的 yml 加:

```yaml
spring:
  cloud:
    nacos:
      discovery:
        metadata:
          zone: hangzhou
```

### 坑 3:Ribbon 排除代码是"历史遗留"

`<exclusions>` 排除 ribbon、`spring.cloud.loadbalancer.ribbon.enabled: false` 在新版依赖里其实已无对象,但保留它们能加深理解:**确保负载均衡器只有 SCLB 一个**。

### 坑 4:限流脚本可能"刷不出"限流

flowrule 是 **QPS=2**,脚本是串行 curl,若网络延迟大可能达不到 2 QPS。可用 `seq 1 20 | xargs -P 10 -I{} curl -s http://localhost:18083/echo-rest/hi` 并发刷,必触发。

### 坑 5:@LoadBalancerClient 的配置类千万别加 @Configuration

若 `MyLoadBalancerConfiguration` 被 `@ComponentScan` 扫进主上下文,`RandomLoadBalancer` 会对**所有服务**生效,违背"只为 service-provider 定制"的意图。(本项目写法正确,这里只是提醒自己写时别加。)

## 13. 知识点总结与进阶练习

### 本项目覆盖的知识点

- ✅ Spring Cloud LoadBalancer 替代 Ribbon 的背景与配置
- ✅ **实现 `ReactorServiceInstanceLoadBalancer` 自定义负载均衡策略**(随机)
- ✅ `@LoadBalancerClient(value, configuration)` 按服务名定制负载均衡
- ✅ SCLB **子上下文**机制(为何配置类不加 `@Configuration`)
- ✅ `zone-preference` + `spring.cloud.loadbalancer.zone` 区域优先
- ✅ Nacos 实例 **metadata** 与 zone 的关系
- ✅ Sentinel 完整链路:`@SentinelRestTemplate` + UrlCleaner 资源名清洗 + flowrule/degraderule + Feign fallback
- ✅ `@EnableDiscoveryClient(autoRegister=false)` 只发现不注册
- ✅ Reactor 响应式编程入门(`Mono`/`Flux`/`map`)

### 推荐动手练习

1. **跑通基础链路**:按 11 节启动,完成 6 个验证 curl
2. **验证随机策略**:启动 2~3 个 provider 实例(provider 日志能看到端口),刷 `/echo-rest/hi` 50 次,统计各实例命中比例(应大致均匀但无规律,区别于轮询的 1-2-1-2)
3. **改造成"加权随机"**:给 `RandomLoadBalancer` 的 `getInstanceResponse` 加权重逻辑(提示:按实例 metadata 中的 `weight` 值构建下标区间)
4. **玩转 zone**:provider 配 `metadata.zone=hangzhou` 启 2 个实例、`zone=shanghai` 启 1 个,刷 `/zone` 看是否永远命中杭州实例
5. **对比实验**:把 yml 的 `configurations` 改成 `random`/删掉,观察默认行为差异
6. **对照复盘**:回到上个项目(consumer-example),对照本文第 2 节的表格,亲手把它的 Sentinel/Fallback 修到和本项目一样(答案全部可抄本项目)
7. **进阶**:打断点跟一遍 `LoadBalancerClientFactory.getInstance()` → 子上下文创建 → `RandomLoadBalancer.choose()` 调用栈,彻底吃透 SCLB 机制

### 一句话总结

> 本项目是上个 consumer 项目的"满血版":**Ribbon 退场、SCLB 登台**——用 `@LoadBalancerClient` + 自定义 `RandomLoadBalancer` 控制"怎么选实例",用 `zone-preference` 控制"优先选哪里的实例",而上次缺席的 Sentinel/UrlCleaner/Fallback 这次全部真实生效。学完它,你就掌握了 Spring Cloud 负载均衡的主干知识。
