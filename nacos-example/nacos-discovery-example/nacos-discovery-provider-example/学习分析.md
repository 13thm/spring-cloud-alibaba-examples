# Nacos Discovery Provider Example — 学习分析文档

> 这是整个 nacos-discovery-example 家族里**最简单也最基础**的一个项目,但"简单"不等于"没东西学"——
> 它是所有 consumer 项目的"靶子服务",它上面的每一个接口都是**精心设计的测试素材**。
> 本文档讲透:服务注册的原理、每个接口的设计意图、企业里真实的服务提供者长什么样、以及必须注意的坑。

## 1. 项目定位:被调用方(靶子服务)

```
                    ┌────────────────────┐
   谁调用它?        │  service-provider   │ ← 本项目
   ├─ consumer-example (RestTemplate/Feign)
   ├─ consumer-sclb-example (自定义负载均衡/zone)
   └─ reactive-consumer (WebClient 响应式)
                    └────────────────────┘
```

前面你学的所有 consumer 项目,调用的都是它!它就是那个神秘的 `service-provider`:
- 启动后把自己注册进 Nacos
- 暴露一组接口,**故意**包含正常接口、报错接口、慢接口——专门用来触发 consumer 侧的限流/熔断/降级演示

**一句话:它是"陪练",没有它,前面所有 Sentinel/负载均衡实验都跑不起来。**

## 3. 核心原理:服务注册到底发生了什么?

这是本项目最重要的知识点。`ProviderApplication` 里只有一个 `@EnableDiscoveryClient`,启动后到底发生了什么?

### 3.1 启动时序(自动注册的真相)

```
SpringApplication.run()
   ↓
1. 引入 nacos-discovery starter → 自动装配 NacosServiceAutoConfiguration 等一堆配置类
   (所以 @EnableDiscoveryClient 注解现在只是"声明性的",不写也会注册!)
   ↓
2. 监听 WebServerInitializedEvent(Tomcat 启动完成,端口确定了)
   ↓
3. NacosAutoServiceRegistration.start() 被触发
   ↓
4. 组装实例信息(NacosRegistration):
      serviceName = service-provider     ← spring.application.name
      ip         = 本机网卡 IP
      port       = Tomcat 实际端口(server.port=0 时是随机端口)
      cluster/metadata/weight/ephemeral...
   ↓
5. 调用 Nacos OpenAPI: POST /nacos/v1/ns/instance (注册)
   ↓
6. 之后每 5 秒向 Nacos 发一次心跳(临时实例)
```

### 3.2 临时实例 vs 持久实例(面试高频!)

| | 临时实例(默认,ephemeral=true) | 持久实例(ephemeral=false) |
|---|---|---|
| 健康检查方式 | **客户端心跳**(每 5s) | **服务端主动探测**(定时 HTTP/TCP) |
| 掉线判定 | 15s 未收到心跳 → 标记不健康;30s → 剔除 | 不健康只标记,**不剔除** |
| 数据一致性协议 | Distro(AP,最终一致) | Raft(CP,强一致) |
| 适用场景 | 常规微服务节点 | DB、Redis 等基础设施(挂了也要留在列表里告警) |

本项目没配置 → 默认临时实例 → **provider 被 kill -9 后,最多 30 秒就会从 Nacos 消失**,这就是 consumer 侧列表自动更新的原因。

### 3.3 Nacos 数据模型(四层)

```
Namespace(命名空间,如 dev/test/prod 环境隔离)
   └── Group(分组,默认 DEFAULT_GROUP)
         └── Service(服务,如 service-provider)
               └── Instance(实例,如 192.168.1.5:53121,含 metadata/weight/healthy)
```

企业里最常用 namespace 隔离环境,group 区分业务线。

## 4. 逐文件精读

### 4.1 application.yml

```yaml
spring:
  application:
    name: service-provider       # ① 服务名:注册到 Nacos 的唯一标识,consumer 全靠它找你

  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848   # ② Nacos 服务端
        enabled: true
        # ip-type: IPv4 / IPv6        # ③ 可选:多网卡机器上指定注册的 IP 协议
        username: nacos
        password: nacos

server:
  port: 0                          # ④ ★ 随机端口!一台机器起多个实例不冲突

management:
  endpoints:
    web:
      exposure:
        include: '*'
  endpoint:
    health:
      show-details: always         # ⑤ 健康检查显示细节
```

**`server.port: 0` 是本项目的点睛之笔**:端口随机分配,意味着你可以在同一台电脑上启动 N 个 provider 实例(每个端口不同),完美模拟"多实例集群"来验证 consumer 的负载均衡效果。

### 4.2 ProviderApplication.java

```java
@EnableDiscoveryClient
@SpringBootApplication
public class ProviderApplication {
    public static void main(String[] args) {
        SpringApplication.run(ProviderApplication.class, args);
    }
}
```

`@EnableDiscoveryClient` 在 Spring Cloud 新版本里**可写可不写**(自动装配已覆盖),写上只是表达意图、提高可读性。

## 5. EchoController 每个接口的设计意图(重点)

别看接口又土又简单,每一个都是**为 consumer 侧的实验量身定制的**:

| 接口 | 行为 | 为谁服务 |
|------|------|---------|
| `GET /echo/{string}` | 正常返回 `hello Nacos Discovery xxx` | 基础调用验证 |
| `GET /divide?a=&b=` | `b==0` 时返回 `0`(不抛异常),否则返回商 | consumer 的 feign-error 脚本素材 |
| `GET /sleep` | **睡 1 秒**再返回 ok | 触发 Sentinel **慢调用比例熔断**(degraderule 里配了它) |
| `GET /` | 返回 **HTTP 500** `"index error"` | 制造持续错误,触发降级规则 |
| `GET /test` | 返回 **HTTP 500** `"error"` | 同上,给 `/test` 的熔断规则当素材 |
| `GET /zone` | 读取**注册元数据**里的 zone 并返回 | sclb 项目的 zone 区域优先实验 |

```java
@GetMapping("/zone")
public String zone() {
    Map<String, String> metadata = nacosDiscoveryProperties.getMetadata(); // 当前实例的注册元数据
    return "provider zone " + metadata.get("zone");
}
```

注意 `/zone` 直接注入了 `NacosDiscoveryProperties`(**Nacos 注册信息的配置类**),能读到当前实例注册到 Nacos 的 metadata——这是"服务自己查看自己名片"的演示。

**理解了这个表,你就明白了为什么 consumer 的 degraderule.json 里会出现 `GET:http://service-provider/sleep`、`GET:http://service-provider/test` 这些资源名——全是这里配对的!**

> 💡 一个诚实的提醒:`/` 和 `/test` 秒回 500(是"快错误"而非"慢调用"),而 degraderule 里 sleep 用的是 grade=0(异常比例),test 用的是 grade=1(慢调用比例),演示值与行为未必精确对应,跑实验时以实际现象为准。官方示例的规则更多是"给你看字段怎么配"。

## 6. 企业里怎么用?

本项目是最小 Demo,企业真实的服务提供者通常还有这些标配:

### 6.1 部署形态
- **多实例 + 容器编排**:K8s Deployment 起 3~5 个副本(而不是像 Demo 在一台机起多进程)
- **固定端口**:容器内端口固定(Demo 的 `port: 0` 只是为了本机多开)
- 注册的 IP 常是 Pod IP / 容器 IP,多网卡机器需要 `spring.cloud.nacos.discovery.ip` 显式指定

### 6.2 发布安全(生产刚需,Demo 没演示但必须知道)
- **优雅上线**:应用就绪后才注册(配置 `spring.cloud.nacos.discovery.register-enabled` 时机、K8s readinessProbe),避免"注册了但还没准备好"被调用方打死
- **优雅下线**:先从 Nacos 注销(`curl -X DELETE .../instance` 或 `/actuator/serviceregistry` 端点),处理完存量请求再停进程;K8s preStop 钩子
- **预热**:权重从低到高逐步放大(冷启动 JIT/缓存未就绪时扛不住全量流量)

### 6.3 元数据 metadata 的企业玩法
```yaml
spring.cloud.nacos.discovery.metadata:
  zone: hangzhou          # 机房/区域 → 配合 zone 优先负载均衡
  version: v2             # 版本 → 灰度/金丝雀发布
  weight-tag: gray        # 标签 → 全链路灰度
```
配合 consumer 侧自定义 ServiceInstanceListSupplier 可以实现"按标签路由",这是**灰度发布的客户端实现基础**。

### 6.4 健康与探活
- Nacos 临时实例靠心跳,但企业还会配 actuator health 给 K8s 用
- 保护阈值:`spring.cloud.nacos.discovery.protect-threshold`(大量实例掉线时,Nacos 停止全量摘除,防止雪崩)——**面试常问**

### 6.5 版本与契约
- 接口提供方通常还会暴露 API 文档、维护版本(`/v1/echo`)、限流自保(自己挂 Sentinel,而不是指望调用方善良)

## 7. ⚠️ 注意事项与坑

### 坑 0:parent 链断裂,当前根本编译不了(最优先!)
本 module 的 parent 是:
```xml
<parent>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>nacos-discovery-example</artifactId>
    <version>${revision}</version>
</parent>
```
而它的 parent 又指向仓库根 `com.alibaba.cloud:spring-cloud-alibaba-examples:${revision}`。
**但当前仓库根 pom 已被替换成 `com.thm.cloud:...:1.0-SNAPSHOT` 的空壳**(没有 `${revision}` 属性、没有任何 dependencyManagement)。
后果:① parent 坐标对不上;② 所有不带版本号的依赖(如 `spring-boot-starter-web`)无法解析版本。
**修复方案**:在根 pom 补上 `revision` 属性 + 三大 BOM(Spring Boot 3.2.x / Spring Cloud 2023.0.x / Spring Cloud Alibaba 2023.0.x),或改用你自己 consumer-example 那套写死版本的方式。

### 坑 1:metadata 里没有 zone
`/zone` 接口会返回 `provider zone null`。想跑通 sclb 项目的 zone 实验,必须给 provider 加:
```yaml
spring.cloud.nacos.discovery.metadata:
  zone: hangzhou
```

### 坑 2:看到 /test、/ 一直返回 500 别慌
那是故意的,就是给 consumer 触发熔断降级用的素材,不是 bug。

### 坑 3:`port: 0` 的副作用
- 日志里要找 `Tomcat started on port xxxxx` 才知道实际端口
- 想复现"固定地址调试"时改成固定端口
- Nacos 控制台能直接看到每个实例的随机端口

### 坑 4:多网卡机器注册错 IP
公司电脑常有 VPN/虚拟网卡,Nacos 可能注册一个 192.168.x 或虚拟网卡的 IP,导致 consumer 连不上。用 `spring.cloud.nacos.discovery.ip` 强制指定,或 `ip-type` 限定 IPv4。

## 8. 动手练习

1. **看注册过程**:启动 Nacos → 启动 provider → 打开 Nacos 控制台(localhost:8848/nacos)→ 服务列表 → 点开 `service-provider` 看实例(IP/端口/临时/权重)
2. **验证心跳剔除**:启动后 `kill -9` 杀掉进程,掐表看 Nacos 控制台实例多久消失(15s 不健康 / 30s 剔除)
3. **多实例实验**:连开 3 个 provider 实例(port=0 不冲突),回到 consumer-sclb 项目刷 `/echo-rest/xxx`,观察随机/轮询命中分布
4. **补 zone 元数据**:加上 `metadata.zone`,再跑 sclb 项目的 `/zone` 接口,前后对比
5. **curl 直调 provider**:`curl http://<实例IP:端口>/echo/hi`(端口从 Nacos 控制台查),理解"consumer 不过是帮你做了'查地址+挑实例+发请求'"
6. **进阶**:写一个自定义接口返回本实例端口,刷 consumer 时统计各端口命中次数,亲手"看见"负载均衡

### 一句话总结

> Provider 是微服务的"被调用方标配形态":**起服务 → 注册 Nacos → 暴露接口**。本 Demo 额外的价值在于——它的报错接口、慢接口、zone 接口,都是为 consumer 侧的限流熔断/区域路由实验准备的"实验耗材"。企业里真正要操心的是它的**发布安全(优雅上下线、预热、灰度)与自保能力**。
