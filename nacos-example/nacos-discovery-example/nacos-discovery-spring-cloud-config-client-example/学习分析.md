# Spring Cloud Config Client Example — 学习分析文档

> 这是 Config Server 的另一半:**配置客户端**。它演示"应用启动时,通过 Nacos 找到 Config Server,
> 从 Git 仓库拉取自己的配置"。本文档重点讲透两个高频考点:**bootstrap.yml 的加载时序**
> 和 **discovery 模式拉配置的完整链路**,以及本项目一个"藏得很深"的经典大坑。

## 1. 项目定位:配置的消费者

```
启动时序(与上一个项目对照着看):

client(本项目)                        Nacos                     Config Server
    │                                   │                            │
    │ ①"configserver在哪儿?"            │                            │
    │ ─────────────────────────────────►│                            │
    │ ② 返回实例列表(10.x.x.x:7070)     │                            │
    │ ◄─────────────────────────────────│                            │
    │                                   │                            │

    ▼
```

项目本身简单到只有 3 个文件,但启动背后这一整套链路,才是 Spring Cloud Config 客户端的全部精髓。

## 3. 核心概念:bootstrap.yml 是什么?为什么它排在最前面?

### 3.1 引出问题

拉配置这件事有个"鸡生蛋"悖论:

> 配置中心的地址信息,本身也是配置。它不能放在"普通配置文件"里——
> 因为**普通配置文件要等 Spring 容器启动到一半才解析,而拉取远程配置必须发生在更早的阶段**,
> 否则本地 @Value、数据源等 Bean 创建时,远程配置还没到。

### 3.2 bootstrap 上下文(Bootstrap Context)

Spring Cloud 的解法:在**主上下文之前**先创建一个更小的"引导上下文",专干两件事:

```
启动流程:
main()
  │
  ▼
┌─ Bootstrap Context(由 bootstrap.yml 驱动)────────────┐
│  1. 读 bootstrap.yml                                   │
│  2. 连接 Nacos(找 configserver)                       │
│  3. 连接 Config Server 拉取 client-dev.yml             │
│  4. 把远程配置塞进 Environment(优先级很高)             │
└───────────────────────────────────────────────────────┘
  │
  ▼
┌─ Main Application Context(由 application.yml 驱动)───┐
│  5. 创建你的 Bean,@Value("${config}") 此时能取到远程值 │
└───────────────────────────────────────────────────────┘
```

### 3.3 配置优先级(必须记住)

```
bootstrap.yml < 远程配置(Config Server) < application.yml
(远程配置会覆盖 bootstrap 里的同名项;本地 application.yml 优先级高于远程——
 实践口诀:关键兜底值放 application.yml,公共值放远程仓库)
```

本项目正好演示了"兜底":本地 `application.yml` 里也有 `config: config-from-yml`,若远程没拉到/没有这个 key,应用也能起来(但注意坑 2)。

## 4. 一次启动的完整链路(本项目精髓)

对照 bootstrap.yml 逐行标注:

```yaml
spring:
  application:
    name: client                    # ① 我叫 client → 决定去拉 client-dev.yml
  cloud:
    nacos:
      username: nacos
      password: nacos
      discovery:
        server-addr: 127.0.0.1:8848 # ② 用这个 Nacos 做"服务发现"
    config:
      discovery:
        enabled: true               # ③ ★ 开启:通过服务发现找 Config Server(不写死URL)
  profiles:
    active: dev                     # ④ 激活 dev → 拉的文件是 client-dev
```

启动时序(串联①②③④):

1. Bootstrap 上下文读取 bootstrap.yml
2. 因为 `config.discovery.enabled=true` → client 先把自己当作 Nacos 的**发现客户端**,查询服务名 **`configserver`**(Spring Cloud Config 约定的默认服务名,可用 `spring.cloud.config.discovery.service-id` 改)的实例列表
3. 拿到实例(如 `192.168.1.7:7070`)→ 组装 URL:`GET http://192.168.1.7:7070/client/dev`
4. Config Server 去它配置的 Git 仓库找 `client.yml`、`client-dev.yml`、`application.yml`、`application-dev.yml`…合并返回
5. 远程配置进入 Environment;主上下文启动,`GetConfigController` 的 `@Value("${config}")` 注入成功

**注意:本 client 并不注册自己到 Nacos,它只是借 Nacos "问路"。**(对比:sclb 项目用 `autoRegister=false` 显式声明;这里没写 @EnableDiscoveryClient,只在引导阶段用了发现能力)

## 5. 逐文件精读

### 5.1 GetConfigController.java

```java
@RestController
public class GetConfigController {

	@Value("${config}")          // ★ 从 Environment 取 key=config 的值(远程或本地)
	private String config;

	@GetMapping("/config")
	public String getConfig() {
		return config;
	}
}
```

- `@Value("${config}")` 没有 `:默认值`,意味着 **Environment 里没有 `config` 这个 key 时,应用直接启动失败**(占位符解析异常)——这是故意设计的"快速失败"教学点
- 拉取来源优先级:`application.yml(本地)` > 远程配置 > bootstrap

### 5.2 application.yml(本地兜底)

```yaml
config: config-from-yml
```

作用:① 远程没这个 key 时兜底,保证能启动;② 是个"探针"——**如果你访问 /config 返回 `config-from-yml`,说明远程配置根本没拉到!**(下文坑 1 的验证方法)

## 6. 企业里怎么用?

### 6.1 动态刷新(@RefreshScope,生产标配)

本项目只有一个静态 `@Value`,改了 Git 配置后**已启动的 Bean 不会变**。企业里要动态生效:

```java
@RestController
@RefreshScope                        // ★ 标记:收到刷新事件后销毁重建本 Bean
public class GetConfigController {
    @Value("${config}") private String config;
}
```

```bash
# 修改 Git 上的 client-dev.yml 后,通知客户端刷新:
curl -X POST http://localhost:8080/actuator/refresh
```
一个服务一个服务手动刷显然不现实 → 引入 **Spring Cloud Bus**(MQ 广播),一次 `/actuator/busrefresh` 全量刷新;或改用 Nacos Config 的自动推送(这也是很多团队最终迁移到 Nacos 的原因)。

### 6.2 启动失败处理
- `spring.cloud.config.fail-fast=true`:连不上 Config Server 就立刻失败(默认会继续用本地配置跑,可能带病上线)
- `spring-retry` 重试:网络抖动时不至于起不来

### 6.3 环境隔离矩阵(企业标准玩法)

```
Git 仓库: application.yml(全局默认)
          application-{profile}.yml(环境差异)
          {服务名}.yml(服务专属)
          {服务名}-{profile}.yml(服务×环境)
Nacos 侧: namespace 隔离 dev/test/prod(注册+配置双隔离)
启动时:   --spring.profiles.active=prod 指定环境
```

### 6.4 敏感配置
- 交给 Config Server 的 `{cipher}` 加密,或企业级 KMS/Vault,明文不进 Git

## 7. ⚠️ 注意事项与坑(本篇最重要的一节)

### 坑 0:parent 链断裂(同前两个项目)
根 pom 被替换成 `com.thm.cloud` 空壳,`${revision}` 与依赖版本都解析不了。先修根 pom,详见 provider 文档坑 0。

### 坑 1:★ 最大的坑——bootstrap.yml 根本没生效!

**背景**:Spring Boot 2.4 / Spring Cloud 2020.0 起默认禁用了 bootstrap 上下文,必须显式引入:

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-bootstrap</artifactId>
</dependency>
```

**检查本项目的 pom:没有这个依赖!** 后果:

```
bootstrap.yml 被完全忽略
   ↓
不会去 Nacos 找 configserver、不会拉远程配置
   ↓
应用"看起来正常"启动了,/config 返回 config-from-yml(本地值)
   ↓
你以为配置中心跑通了,其实远程配置从未到达 —— 隐蔽且极易误判
```

**修复二选一:**

```xml
<!-- 方案A:补依赖,救活 bootstrap.yml -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-bootstrap</artifactId>
</dependency>
```

```yaml
# 方案B(新标准做法):删掉 bootstrap.yml,改用 application.yml + 导入语句
spring:
  config:
    import: optional:configserver:      # optional 前缀=连不上不阻断启动
```

> 💡 判断 bootstrap 有没有生效的口诀:**看启动日志有没有 "Fetching config from server" / 看到 /config 返回远程值**。

### 坑 2:`@Value("${config}")` 无默认值 = 启动炸弹
远程和本地都没有 `config` 这个 key 时,启动直接报 `Could not resolve placeholder 'config'`。写法上要么给默认值 `${config:default}`,要么接受 fail-fast(生产反而推荐 fail-fast,让缺配置的服务死在发布阶段而不是运行阶段)。

### 坑 3:必须先起 Nacos 和 Config Server
发现模式 = 两个前置依赖。顺序:Nacos → Config Server(等它注册上)→ client。Config Server 没注册成功时,client 会报 "Unable to find instance of configserver"。

### 坑 4:服务名/Profile 与 Git 文件名必须严格对应
`name: client` + `profile: dev` → 找的是 `client-dev.yml`。Git 仓库里文件叫 `clientDev.yml`、`client.yaml` 都不认。排查时直接用浏览器访问 `http://<configserver>:7070/client-dev.yml` 先验证 Server 侧有货。

### 坑 5:改了 Git 不等于客户端生效
Server 每次请求都会读 Git(新请求=新配置),但**客户端只在启动时拉一次**;运行期变更需要 `@RefreshScope` + 手动/总线刷新。这是 Config Client 最常被问到的问题。

## 8. 动手练习

1. **修复坑 1**(加 spring-cloud-starter-bootstrap),按顺序启动 Nacos → Config Server → client
2. **验证远程配置真的到了**:
   - 在 Config Server 的 Git 仓库里准备 `client-dev.yml`,`config: hello-from-git`
   - `curl http://localhost:8080/config` → 期待 `hello-from-git`(若返回 `config-from-yml` = bootstrap 没生效,回到坑 1)
3. **观察启动日志**:找 `Located property source` / `Fetching config from server at : http://...` 这几行,眼见为实
4. **体验刷新闭环**:加 `@RefreshScope` → 改 Git → `curl -X POST localhost:8080/actuator/refresh` → 再看 `/config` 变了
5. **制造失败**:停掉 Config Server 重启 client,观察报错(找不到 configserver 实例);再配 `fail-fast=true` 对比行为
6. **进阶**:把项目改造成 `spring.config.import` 新写法,对比 bootstrap 旧写法,写一段总结两者差异

### 一句话总结

> Config Client 的使命:在**主上下文启动之前**,通过 Nacos 找到 configserver → 拉取 `应用名-profile.yml` → 塞进 Environment,让 `@Value` 拿到远程值。记住三件事:**bootstrap.yml 要有 starter 才生效(本项目就栽在这)、本地 application.yml 优先级高于远程可当兜底、运行期刷新需要 @RefreshScope 主动触发**。
