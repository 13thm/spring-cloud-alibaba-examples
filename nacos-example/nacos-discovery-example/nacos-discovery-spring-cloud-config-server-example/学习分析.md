## 1. 项目定位:配置中心的服务端

```
                    ┌──────────────────────┐
   Git 仓库          │   Config Server      │  服务名: configserver
 (存配置文件) ─────► │   (本项目,端口7070)  │ ──► 同时注册到 Nacos
                    └──────────┬───────────┘
                               │ HTTP(客户端按需拉取)
                               ▼
                    ┌──────────────────────┐
                    │   Config Client      │ (下一个项目)
                    │   按服务名从Nacos找到 │
                    │   configserver拉配置  │
                    └──────────────────────┘
```

一句话:**它是一个"把 Git 仓库变成配置 HTTP API"的中转服务**——应用启动时不用直连 Git,而是问 Config Server 要配置。

---

## 2. 背景:为什么需要配置中心?

### 2.1 没有配置中心的痛

```
配置写死在 application.yml 里打进 jar 包
   ↓ 问题1:改个数据库密码要重新打包、重启 50 个服务
   ↓ 问题2:测试/生产配置不同,要维护 N 套 jar 或 N 个分支
   ↓ 问题3:50 台机器上的配置漂移(有人手改了某一台),没人说得清
   ↓ 问题4:改了配置没有审计记录,出事故查不到谁改的
```

### 2.2 配置中心 = 把配置从应用里剥离

| 能力 | 说明 |
|------|------|
| 集中存储 | 配置统一放 Git / Nacos / 数据库 |
| 环境隔离 | dev/test/prod 各一套(profile / namespace) |
| 动态刷新 | 改配置不重启,推送生效 |
| 版本审计 | 谁改的、改了什么、可回滚(Git 天然支持) |

### 2.3 Spring 家族的两大配置中心

| | Spring Cloud Config(本项目) | Nacos Config |
|---|---|---|
| 存储 | **Git 仓库**(外置) | Nacos 自带数据库 |
| 动态刷新 | 半自动(client 轮询 / Bus 广播) | 原生推送,秒级 |
| 额外部署 | 要部署 Server | 复用 Nacos(注册中心兼配置中心) |
| 企业采用 | 已有成熟 Git 流程的团队 | **用 SCA 技术栈的主流选择** |

> 💡 面试常问:"Nacos 也能做配置中心,为什么还学 Spring Cloud Config?"——因为很多存量系统、以及 Spring Cloud 官方生态里它仍是标准组件;更重要的是**两者解决的是同一类问题,学懂一个,另一个的模型(服务端存储 + 客户端拉取 + 刷新机制)完全通用**。

## 4. 核心原理:Config Server 是怎么工作的

### 4.1 `@EnableConfigServer` 干了什么

```java
@SpringBootApplication
@EnableDiscoveryClient        // 注册到 Nacos
@EnableConfigServer           // ★ 开启配置服务端:把本应用变成配置 HTTP 端点
public class SpringCloudConfigServerApplication { ... }
```

`@EnableConfigServer` 会激活 `ConfigServerAutoConfiguration`,给应用挂上一套 RESTful 端点(映射到 `EnvironmentController`),**你不用写任何 Controller,自动拥有配置查询 API**。

### 4.2 Git 后端与端点格式(必须背下来)

本项目的后端配置:

```yaml
spring:
  cloud:
    config:
      server:
        git:
          uri: https://github.com/fangjian0423/blogimages   # 配置存放的 Git 仓库
          search-paths: /                                    # 仓库内搜索路径
```

Config Server 暴露的 URL 模式:

```
/{application}/{profile}[/{label}]
/{application}-{profile}.yml
/{label}/{application}-{profile}.yml
```

举例:client 应用名为 `client`、激活 profile `dev`、分支/标签 `master`,则:

```
GET http://localhost:7070/client/dev/master
GET http://localhost:7070/client-dev.yml
```

Config Server 收到请求后的动作:

```
收到 GET /client-dev.yml
   ↓
1. 解析:application=client, profile=dev, label=master(默认)
2. 按 search-paths 去 Git 仓库找 client.yml、client-dev.yml、application.yml...
3. 合并出一份最终 Environment(profile 覆盖默认)
4. 以 YAML/JSON/Properties 格式返回给客户端
   (首次访问会把 Git 仓库 clone 到本地缓存目录,后续增量拉取)
```

**本质:Config Server = "Git 仓库的 HTTP 代理 + 配置合并器"。** Git 才是真正的存储,Server 只是无状态的读门面。

## 5. 逐文件精读

### application.yml(全项目唯一配置)

```yaml
server:
  port: 7070                     # Config Server 固定端口(给 demo 用;生产多实例随机/容器化)

spring:
  application:
    name: configserver           # ① ★ 服务名:client 通过这个名字在 Nacos 里找它!
  cloud:
    nacos:
      username: 'nacos'
      password: 'nacos'
      discovery:
        server-addr: 127.0.0.1:8848   # ② 注册进 Nacos
    config:
      server:
        git:
          uri: https://github.com/fangjian0423/blogimages   # ③ Git 后端
          search-paths: /
```

重点就是 **①+②+③ 的组合**:名字叫 `configserver`、注册进 Nacos、背后是 Git。下一个项目 client 的 bootstrap.yml 只需要 `discovery.enabled: true`,就能**通过 Nacos 服务发现找到这里**,完全不用写 IP:端口——这就是"配置中心高可用"的经典做法(详见第 6 节)。

## 6. 和 Nacos 的关系:为什么注册进 Nacos?

### 6.1 传统模式的死穴

```
client 写死: spring.cloud.config.uri=http://10.0.0.5:7070
                                     ↓
              Config Server 挂了/换机器/IP 变了 → 所有 client 失联
              → 悖论:"拉配置的服务"自己成了单点,配置中心的意义打折
```

### 6.2 服务发现模式(本项目的做法)

```
Config Server 启动 → 注册到 Nacos (服务名: configserver)
                              │
client 启动 → 先问 Nacos:"configserver 有哪些实例?"
                              │
                     挑一个活着的实例发请求
                              │
        Config Server 可以部署 N 个实例 → 天然高可用
```

对应 client 端配置(下个项目的 bootstrap.yml):

```yaml
spring.cloud.config.discovery.enabled: true   # 开启"通过注册中心找 Config Server"
# 可选: spring.cloud.config.discovery.service-id: configserver (默认就叫这个名字)
```

**这是"注册中心 + 配置中心"组合的最佳实践,企业里几乎都这么做(或直接用 Nacos 一站式)。**

## 7. 企业里怎么用?

### 7.1 典型工程结构(多环境)

```
config-repo (一个独立 Git 仓库)
├── application.yml            # 全局默认(日志级别、公共配置)
├── application-prod.yml       # 生产覆盖
├── order-service.yml          # 订单服务专属
├── order-service-dev.yml      # 订单服务 dev 环境
└── user-service.yml           # 用户服务专属
```
- **一个配置仓库管全公司所有服务**,权限由 Git 仓库的分支保护/审批流控制
- label 常用来区分 release 分支 / hotfix 分支的配置

### 7.2 高可用部署
- Config Server 无状态(数据在 Git)→ 直接横向扩容多实例 + 注册中心(本项目演示的模式)
- 生产会再加一层本地缓存(Git clone 本地目录本身就是缓存),Git 挂了还能用 `spring.cloud.config.server.git.basedir` 里的存量

### 7.3 安全(生产必做,Demo 没做)
- 加 `spring.security` 账号密码,client 端配 `spring.cloud.config.username/password`
- 敏感项(密码/密钥)用**加密存储**:`{cipher}...` + 对称/非对称密钥(`encrypt.key`)
- Git 仓库私有化(企业内 GitLab),Config Server 配 deploy key

### 7.4 与 Nacos Config 的选择(企业视角)
- 团队已在 SCA 体系 → 直接 Nacos Config,少一个组件、刷新更快
- 配置治理要求强(Git 审批流、回滚)→ Config Server + Git
- 混合场景也存在:遗留系统 Config Server,新服务 Nacos

## 8. ⚠️ 注意事项与坑

### 坑 0:parent 链断裂,编译不了(同 provider 项目)
parent 依赖 `com.alibaba.cloud:${revision}` 的根 pom,但当前仓库根 pom 是 `com.thm.cloud` 空壳。先修根 pom(补 `${revision}` 属性 + 三大 BOM),否则本模块无法构建。详见 provider 文档坑 0。

### 坑 1:Git 仓库是外网的,国内/断网环境启动即失败
首次请求配置时 Config Server 要 clone `github.com/fangjian0423/blogimages`,网络不通会抛异常。
**解决**:换成你自己的 Gitee/GitLab/本地路径仓库:
```yaml
spring.cloud.config.server.git.uri: file:///E:/code/config-repo   # 本地仓库也能演示
```

### 坑 2:Git 仓库里得真的有对应的配置文件
client(名 `client`、profile `dev`)会找 `client-dev.yml` / `client.yml` / `application-dev.yml`。
如果都没有,client 拉到空配置 → 启动报占位符错误(见下个项目坑)。**自己换仓库时记得造这些文件。**

### 坑 3:Demo 没有任何安全措施
7070 端口裸奔,任何能访问它的人都能读全部配置。生产必须加认证 + 网络隔离。

### 坑 4:配置改了不会自动推给客户端
Spring Cloud Config 的刷新是被动的:client 要主动调 `POST /actuator/refresh`(或配合 Spring Cloud Bus + MQ 广播批量刷新)。**这和 Nacos Config 的自动推送不同**,面试爱考。

### 坑 5:版本兼容
Spring Boot 3.2.x 应搭配 Spring Cloud 2023.0.x 的 config-server;旧教程的 `spring-cloud-config-server` 2.x 配置项有差异(如加密器行为)。

## 9. 动手练习

1. **先把 Git 后端换成本地仓库**(绕开坑1):建 `E:/code/config-repo`,放一个 `client-dev.yml`,内容 `config: hello-from-git`,uri 改成 `file:///E:/code/config-repo`
2. **直接用浏览器当 client**:启动后访问
   - `http://localhost:7070/client-dev.yml` → 应看到你的配置内容
   - `http://localhost:7070/client/dev` → 看 JSON 格式(propertySources 列表)
   - 故意访问不存在的 `http://localhost:7070/xxx-dev.yml` 看返回什么
3. **观察 Nacos 注册**:控制台应出现 `configserver` 服务(和 provider 一样的心跳机制)
4. **改 Git 文件再刷新**:改 `client-dev.yml` 内容 → 再访问端点 → 发现已是新值(Server 每次请求都重读 Git);体会"Server 侧总是新,但 Client 侧要自己刷新"(留给下个项目验证)
5. **进阶**:给 Server 加 `spring-cloud-starter-security`,体验 client 不带密码 401

### 一句话总结

> Config Server 是"**Git 仓库 → HTTP 配置 API**"的无状态转换器:`@EnableConfigServer` 白送你一套 `/{应用}/{profile}` 端点;注册进 Nacos 后,client 无需 IP 直连即可发现它,天然高可用。企业里它对应"Git 审批流管配置"的模式;但注意——**它的刷新是被动的**,以及 Demo 裸奔不安全、外网 Git 不可达就挂。
