# 学习指导：spring-cloud-alibaba-sidecar-consul-example

> 本模块演示 Spring Cloud Alibaba Sidecar **换注册中心**的能力：
> 不用 Nacos，改用 HashiCorp Consul（8500）作注册中心，同样把
> Node.js 异构服务（`node-service`，端口 8060）接入 Spring Cloud 生态。

---

## 一、这个模块做了什么

功能目标与 nacos 版完全一致——**派一个 Java 壳应用替 Node 服务去注册中心报到**，
但注册中心换成了 **Consul**，并且是**最简形态**：只演示"注册 + 健康检查"，
不带 Gateway（用 `spring-boot-starter-web` 而非 WebFlux/Gateway）。

### 核心组成（本模块只有 3 个文件）

| 文件 | 作用 |
|---|---|
| `DemoApplication.java` | 启动类，与 nacos 版相同：`@LoadBalancerClients({@LoadBalancerClient("node-service")})` |
| `application.yml` | sidecar 三行配置 + Consul 地址（localhost:8500） |
| `../node-service.js` | 共用的被接入方：Node.js 服务（8060），含 `/health.json` |

### 工作原理

```
Java Sidecar 应用(8070) ──注册──► Consul(8500)
        注册信息: name=node-service, ip=127.0.0.1, port=8060
        健康哨兵: 定时探 http://localhost:8060/health.json

其他 Java 服务 ──从 Consul 发现 node-service──► 直连 127.0.0.1:8060
```

### 本模块最有价值的一处细节（pom.xml）

`spring-cloud-starter-alibaba-sidecar` **默认传递依赖了 nacos-discovery**，
换 Consul 时必须显式排除，再引入 consul-discovery：

```xml
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-sidecar</artifactId>
    <exclusions>
        <exclusion>            <!-- ★ 关键：剔除默认的 Nacos 发现 -->
            <groupId>com.alibaba.cloud</groupId>
            <artifactId>spring-cloud-starter-alibaba-nacos-discovery</artifactId>
        </exclusion>
    </exclusions>
</dependency>
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-consul-discovery</artifactId>
</dependency>
```

这印证了 Sidecar 框架的设计：**注册中心是可插拔的**，sidecar 只做
"注册代理 + 健康哨兵"，具体注册到哪由 Spring Cloud Commons 抽象决定。

## 二、需要学习的知识点

1. **Consul 基础**
   - 安装启动（`consul agent -dev`）、Web 控制台（localhost:8500）；
   - 服务/实例/KV 三大核心概念，与 Nacos 的功能对比（Nacos 带配置中心，Consul 强在 KV/多数据中心）。
2. **Spring Cloud 服务注册抽象**
   - `spring-cloud-starter-consul-discovery` 如何替代 nacos-discovery；
   - Maven `exclusions` 排除传递依赖的技巧——换组件时的通用手法。
3. **Sidecar 与注册中心解耦的原理**
   - Sidecar starter 的自动装配如何兼容任意 `DiscoveryClient` 实现；
   - 对比两个模块 pom/yml 的差异，理解"可插拔注册中心"的含义。
4. **健康检查配置**
   - 本模块 `health-check-url` 是**显式配置**的（nacos 示例中被注释掉了），值得对比体会；
   - Consul 对健康检查的敏感性：检查失败实例会被标记 critical 并拒绝服务。
5. **Web vs Gateway 的取舍**
   - 本模块只有 `spring-boot-starter-web`，说明 sidecar 本身不需要网关也能工作；
   - 思考：什么场景只需要"被发现"（本模块），什么场景还需要"被网关统一路由"（nacos 版）。

## 三、学习目的

- **打破"Spring Cloud Alibaba = 只能配 Nacos"的误解**：掌握在同一套 SCA 框架下按公司基建自由选择注册中心的能力；
- **学习依赖治理**：通过 exclusion 替换默认实现，这是阅读/改造开源框架源码和 starter 的必备技巧；
- **建立横向对比思维**：同一个需求在 Nacos/Consul（乃至 Eureka/Zookeeper）下的实现差异，为技术选型打基础。

## 四、以后怎么用（实战场景）

1. **存量 Consul 体系的公司**：团队注册中心本来就是 Consul（常见于从 Spring Cloud Netflix 迁移过来的公司），老异构服务接入直接套用本模块模板；
2. **多云/多机房**：Consul 的多数据中心能力 + Sidecar 接入异构语言服务，可搭建跨机房的服务发现体系；
3. **接入姿势（三步）**：
   - Step1：引入 `sidecar`（exclude 掉 nacos-discovery）+ `consul-discovery`；
   - Step2：yml 配置 `spring.cloud.consul.host/port` + `sidecar.ip/port/health-check-url`；
   - Step3：启动 Node 等异构服务和 `DemoApplication`，到 Consul 控制台确认 `node-service` 已注册且健康。
4. **生产建议**：
   - Consul 健康检查失败会直接摘除实例，health-check-url 指向的接口务必轻量、无外部强依赖；
   - 需要被网关统一入口访问时，参照 nacos 版补上 gateway 依赖与 `discovery.locator` 配置即可。

## 五、动手验证清单

- [ ] 启动 Consul：`consul agent -dev`，打开 localhost:8500 控制台；
- [ ] `node node-service.js` 启动异构服务（8060）；
- [ ] 启动本模块 `DemoApplication`（8070）；
- [ ] Consul 控制台 services 中看到 `node-service`，健康检查为 passing；
- [ ] `kill` 掉 node 进程，观察 Consul 中健康检查变为 critical；
- [ ] 重启 node 进程，观察实例自动恢复 passing；
- [ ] 进阶：给本模块加上 `spring-cloud-starter-gateway`，实现与 nacos 版一样的 `http://127.0.0.1:8070/node-service/**` 路由访问。
