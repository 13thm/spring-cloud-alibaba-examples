# Spring Cloud Bus RocketMQ Example 学习分析 — 给微服务集群装一根"广播总线"

> 前面学过的 rocketmq-example 是**业务消息**(应用自己收发);本模块是**框架级消息**:
> Spring Cloud Bus 借 RocketMQ 当传输层,把"事件"一键广播给**所有实例**。
> 一个工程、两个实例、自定义事件 `UserRemoteApplicationEvent`,演示"发布/订阅"如何跨进程玩转 Spring 事件机制。
> 顺带藏着一个值得深挖的**目的地(destination)疑点**,是全篇最有嚼头的地方。

## 1. 一句话理解这个示例

> 同一个应用**起两份**(8080/8081),向 8080 发一次 HTTP 请求发布一个"用户事件",
> 两个实例的控制台都打印出收到——事件像广播一样穿过 RocketMQ 到达每个实例。
> 这就是 Bus 的全部魔法:**把 Spring 的 ApplicationEvent 从"单机"扩容到"集群"**。

```
        curl /bus/event/publish/user?name=jack
              │
              ▼
        实例 A(8080) ──发布 UserRemoteApplicationEvent──► RocketMQ Topic(springCloudBus)
                                                          │  广播
                              ┌───────────────────────────┴───────────────┐
                              ▼                                           ▼
                        实例 A 自己(本地事件直达)                  实例 B(8081)收到并打印
```

与业务消息的本质区别:**Bus 是框架在用 MQ,应用一行 MQ 代码都没写**——你只管发 Spring 事件。

## 3. Spring Cloud Bus 是什么:解决什么问题

**问题**:配置中心里一份配置变了,集群 50 个实例怎么知道?逐个 curl `/actuator/refresh`?
——需要一根"广播喇叭":**一个实例喊话,全员听见**。

```
没有 Bus:                          有 Bus:
配置变更 → 手动刷 50 台              配置变更 → 刷 1 台 → Bus 广播 → 49 台自动刷
新事件 → 自己写 MQ 生产/消费         发个 Spring 事件 → 全员 @EventListener
```

Bus 的经典三板斧(actuator 端点):

| 端点 | 作用 |
|---|---|
| `/actuator/busrefresh` | 广播触发所有实例的配置刷新(**Bus 的招牌场景**) |
| `/actuator/busrefresh/服务名:端口` | 定向刷新(destination 定位) |
| 自定义 RemoteApplicationEvent | 广播**任意**事件(本 demo 玩的就是这个) |

传输层可插拔:RabbitMQ / Kafka / **RocketMQ(SCA 提供)**——本模块即 RocketMQ 版,
由 `spring-cloud-stream-rocketmq` binder 承载,收发细节全部透明。

## 4. 核心三件套:RemoteApplicationEvent / Scan / Publisher

```java
public class UserRemoteApplicationEvent extends RemoteApplicationEvent {
    private User user;                                    // ① 业务载荷
    public UserRemoteApplicationEvent(Object source, User user, String originService,
            String destinationService) {
        super(source, originService, DEFAULT_DESTINATION_FACTORY.getDestination(originService)); // ← 疑点!见第 7 节
        this.user = user;
    }
}
```

| 件 | 干什么 | 本例中 |
|---|---|---|
| **RemoteApplicationEvent** | 可跨进程传输的事件基类,携带 originService(来源)+ destination(目的地模式) | UserRemoteApplicationEvent |
| **@RemoteApplicationEventScan** | 告诉 Bus 扫描哪个包的事件类型(**跨进程序列化必需**,不配则收到变 Map) | basePackages = 本包 |
| **ApplicationEventPublisher** | 老朋友:普通 Spring 发布器,Bus 在旁"截胡"转发 | publisher.publishEvent(...) |

事件元数据三问:

- **谁发的?** `originService` = 本实例的 bus id(`${spring.application.name}:${server.port}`)
- **发给谁?** `destination` = 通配模式:`**` 全员;`app:8081` 精确;`app:**` 整个应用(见第 7 节,本例有蹊跷)
- **带什么?** `User` POJO,JSON 序列化走 topic

## 5. 核心代码精读:发布与监听

```java
@RestController
@EnableAutoConfiguration
@RemoteApplicationEventScan(basePackages = "com.alibaba.cloud.examples.rocketmq")
public class RocketMQBusApplication {

    public static void main(String[] args) {
        new SpringApplicationBuilder(RocketMQBusApplication.class)
                .properties("server.port=0")                        // ← 想随机端口,但会被配置文件压住(坑 2)
                .properties("management.endpoints.web.exposure.include=*")
                .properties("spring.cloud.bus.trace.enabled=true")  // 打开事件追踪(可在 /actuator 里观察)
                .run(args);
    }

    @Autowired private ApplicationEventPublisher publisher;
    @Value("${spring.cloud.bus.id}") private String originService;  // app:port,广播时的"署名"

    @GetMapping("/bus/event/publish/user")
    public boolean publish(@RequestParam String name,
            @RequestParam(required = false) String destination) {
        User user = new User();
        user.setId(System.currentTimeMillis());
        user.setName(name);
        publisher.publishEvent(
                new UserRemoteApplicationEvent(this, user, originService, destination));
        return true;
    }

    @EventListener
    public void onEvent(UserRemoteApplicationEvent event) {          // 收到广播:打印载荷
        System.out.printf("Server [port : %d] listeners on %s\n", localServerPort, event.getUser());
    }

    @EventListener
    public void onAckEvent(AckRemoteApplicationEvent event) {        // 收到"回执"事件
        System.out.printf("Server [port : %d] listeners on %s\n", localServerPort,
                objectMapper.writeValueAsString(event));
    }
}
```

值得咀嚼的细节:

1. **发布用的就是最普通的 `publisher.publishEvent()`**——本地 Spring 事件机制,零 Bus API。
   Bus 的 `BusAutoConfiguration` 监听着所有 RemoteApplicationEvent,发现"是我发的"就转发上 MQ。
2. **两个监听器**:一个听业务事件,一个听 `AckRemoteApplicationEvent`(回执)——
   实例处理完事件后会自动回 Ack(可配),发布方因此知道"谁收到了",这就是 `trace.enabled` 的追踪闭环。
3. `destination` 参数 `required=false`:不传 = 意图广播全员(但见第 7 节的偷梁换柱)。

## 6. 消息的一生:本地事件 → RocketMQ → 各实例(原理)

```
实例 A publishEvent(UserRemoteApplicationEvent)
  │
  ├─► 【本地立即触发】A 自己的 @EventListener 直接收到(普通 Spring 语义,不经 MQ!)
  │
  └─► BusAutoConfiguration.acceptLocal:isFromSelf? 是 → 序列化 → 发往 RocketMQ topic: springCloudBus
                                              │
        ┌─────────────────────────────────────┴───────────────┐
        ▼                                                     ▼
   实例 B 收到 MQ 消息                                  实例 A 也收到(自己发的回声)
   acceptRemote:                                       acceptRemote:
     destination 匹配我 && origin≠我                     origin=我 → 丢弃(防回环)
     → 重新 publish 到本地上下文
     → B 的 @EventListener 触发 → 打印
     → B 回发 AckRemoteApplicationEvent(定向给 origin)
                                              │
                              实例 A 的 onAckEvent 收到回执
```

三条铁律(对照源码行为):

- **本地监听器在 publish 那一刻就触发**,与 Bus/MQ 无关——"自己一定收到"不是 MQ 的功劳
- **对端要收到,必须 destination 匹配** 且 origin ≠ 自己
- **Ack 是定向回执**(目的地=原事件 origin),所以发布方控制台会多出 Ack 打印

## 7. destination 疑点:构造器里的"偷梁换柱"(必看)

再看一眼事件构造器:

```java
public UserRemoteApplicationEvent(Object source, User user, String originService,
        String destinationService) {
    super(source, originService,
          DEFAULT_DESTINATION_FACTORY.getDestination(originService));   // ★ 用的是 originService!
    this.user = user;
}
```

**`destinationService` 参数被完全忽略了!** 目的地恒被替换成"发布者自己的 bus id 模式"(如 `app:8080`)。后果推演:

| 实例 | destination 匹配? | 结果 |
|---|---|---|
| A(发布者,8080) | 匹配(就是它自己),但 origin=自己 | 本地 @EventListener 在 publish 时已触发 → **打印一次**;MQ 回声被防回环丢弃 |
| B(8081) | `app:8080` ≠ `app:8081` → **不匹配** | **永远收不到,一声不吭** |

也就是说:**按当前代码,这个"广播 demo"实际只演示了"自己发自己收"**;调用时传不传 destination 都毫无作用。

修复方案(一行):

```java
super(source, originService, destinationService);   // null → Bus 自动变 "**",全网广播
// 或显式:destinationService != null ? Destination.Factory.getDestination(destinationService) : null
```

修好后:`destination=null` 全员收到;`destination=app:8081` 只有 B 收到——广播/单播随意切换。

> 这是把"事件的发布语义"讲透的绝佳素材:**origin 决定署名,destination 决定收件人,两者一混,广播就哑了。**

## 8. 环境搭建与运行

1. **RocketMQ**:启动 NameServer(9876)与 Broker(broker.conf 记得 `brokerIP1=127.0.0.1`,本机自通)
2. **起两个实例**(端口靠命令行区分):
   ```bash
   mvn spring-boot:run -Dspring-boot.run.arguments=--server.port=8080
   mvn spring-boot:run -Dspring-boot.run.arguments=--server.port=8081
   ```
3. **发布事件**:
   ```bash
   curl "http://localhost:8080/bus/event/publish/user?name=jack"
   ```
4. **观察**:按当前代码只有 8080 控制台打印 user 事件;修掉第 7 节的疑点后,8081 也会打印,
   且回到 8080 的还有 Ack 回执(JSON 串)。

## 9. 企业里怎么用?

- **配置广播(招牌)**:配置中心变更 → 触发一台 `/actuator/busrefresh` → 全集群 `EnvironmentChangeEvent`
  → @RefreshScope/@ConfigurationProperties 自动刷新,**Nacos 自己有推送,Bus 更多用于 Config Server(Git 后端)体系**
- **缓存失效广播**:某实例改了数据 → 广播"CacheEvictEvent" → 各实例本地缓存同步失效(高频真实用法)
- **路由/开关热更**:网关实例广播"刷新路由表"事件,秒级生效
- **注意事项**:Bus 是"全员喇叭",**别拿来当业务 MQ**——无重试语义、无顺序保证、事件模型是"通知"不是"传输"。
  业务数据流转请用 rocketmq-example 那套正经生产/消费
- 可靠性:Bus 消息默认非持久化语义的轻量通知,重要状态变更仍落库/落配置中心,Bus 只做"喊一嗓子"

## 10. ⚠️ 注意事项与坑

### 坑 0:parent 链断裂(与 nacos 家族同款)
pom 指向根 `com.alibaba.cloud:spring-cloud-alibaba-examples:${revision}`,而根 pom 已是 `com.thm.cloud` 空壳 → 编译不过。修法见 nacos-discovery 学习路线图坑 0(根 pom 补 revision + 三大 BOM)。

### 坑 1:本模块不需要 Nacos
很多人惯性先起 Nacos——其实只依赖 RocketMQ。bus.id 是手工拼的字符串,与服务发现无关。

### 坑 2:随机端口被配置文件"压"住了
main 里 `SpringApplicationBuilder.properties("server.port=0")` 设的是 **defaultProperties(优先级最低)**,
而 application.properties 里写死 `server.port=8080`(优先级更高)→ **随机端口从未生效**,实际恒 8080。
双实例必须用命令行参数覆盖。想真随机,把配置文件里的 8080 删掉即可。

### 坑 3:destination 被构造器吞掉(第 7 节)
广播 demo 变"自嗨 demo",传 destination 参数无效。修法见上。

### 坑 4:@RemoteApplicationEventScan 漏配 = 收到事件变 Map
不扫描事件类型,反序列化拿不到具体类,@EventListener 收到的是 `Map` 而非 UserRemoteApplicationEvent(类型不匹配直接不触发)。demo 已配好,自建工程最容易栽。

### 坑 5:bus.id 必须全局唯一
`app:port` 若两实例撞 id(比如都 8080),Bus 的"防回环/匹配自己"逻辑会错乱——收不到、或重复收。多实例务必端口互异。

### 坑 6:载荷 User 必须可序列化且有无参构造
JSON 反序列化需要(默认构造+getter/setter,demo 的 User 正好标准)。字段改私有又没 getter → 对端拿到空对象。

## 11. 知识点总结与动手练习

### 本模块覆盖的知识点
- ✅ Bus 的定位:框架级广播 vs 业务消息(rocketmq-example)的边界
- ✅ 三件套:RemoteApplicationEvent / @RemoteApplicationEventScan / ApplicationEventPublisher
- ✅ 消息生命周期:本地直达 → MQ 广播 → 防回环 → Ack 定向回执
- ✅ originService(署名)与 destination(收件人模式)的语义;bus.id 唯一性
- ✅ destination 被构造器吞掉的 bug 与修复;defaultProperties 优先级最低的坑

### 推荐动手练习(由浅入深)

1. **复现"自嗨"**:按当前代码起 8080/8081 双实例,publish 一次,确认只有发布方打印——用日志验证第 7 节的推演
2. **修复广播**:把构造器改为 `super(source, originService, destinationService)`,再发布(不传 destination)→ 两台都打印;传 `destination=spring-cloud-bus-rocketmq-example:8081` → 只有 8081 打印。**广播与单播一站学完**
3. **追踪 Ack**:修复后观察 8080 的控制台,AckRemoteApplicationEvent 的 JSON 里找到 originService 与 destination,画出"谁在什么时候收到了什么"
4. **验证坑 2**:删掉 application.properties 的 server.port,main 里的 port=0 生效,观察随机端口(日志里找 Tomkit started on port)
5. **招牌场景**:给工程加 `spring-cloud-starter-actuator`(已有),curl `http://localhost:8080/actuator/busrefresh`,配合 debug 日志观察广播刷新(无配置中心时刷新为空操作,重点看事件流)
6. **对照学习**:回看 rocketmq-example/STUDY.md——同一个 RocketMQ,业务消息 vs 框架总线的边界在哪,写一段自己的总结

### 一句话总结

> Bus 把 Spring 事件机制"接上了天线":本地 publishEvent 一声喊,RocketMQ 把它送到每个匹配 destination 的实例——
> 只是这个 demo 的天线线头接反了(destination 被换成 origin),修复那一行,广播才真正响起。
