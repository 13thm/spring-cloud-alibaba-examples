# 学习文档：integrated-praise-consumer（点赞消费者）

> 位置：`integrated-example/integrated-praise-consumer`（端口 8014）—— 点赞场景的
> **RocketMQ 消息消费者**，用 Spring Cloud Stream 函数式消费模型收消息，
> 并通过**拉取速率控制**完成"削峰填谷"的后半段。

---

## 一、这个模块做了什么

从 topic `PRAISE-TOPIC-01` 拉取点赞消息，把点赞数写进 `integrated_praise` 库，同时提供点赞数查询接口：

| 文件 | 作用 |
|---|---|
| `PraiseConsumerApplication` | 启动类 |
| `ListenerAutoConfiguration` | ★核心：定义 `Consumer<Message<PraiseMessage>> consumer()` 函数式 Bean |
| `PraiseController` | `GET /praise/query` 查点赞数（网关 `queryPraise` 路由） |
| `PraiseService(Impl)` / `PraiseMapper` | 点赞 +1 / 查询（item 表 praise 字段自增） |
| `PraiseMessage` | 消息体（与生产者侧同构，JSON 反序列化） |
| `application.yaml` | 本地只有 Nacos 地址，**消费绑定在 Nacos 的 integrated-consumer.yaml** |

### 函数式消费模型的接线全景（本模块精华）

```
Nacos 配置:
  spring.cloud.stream.function.definition: consumer;   ← 声明消费函数名
  bindings.consumer-in-0.destination: PRAISE-TOPIC-01  ← 输入通道(命名规则: 函数名-in-序号)
  rocketmq.bindings.consumer-in-0.consumer:
      pullInterval: 4000   ← 每 4 秒拉一次
      pullBatchSize: 4     ← 每次最多 4 条  ⇒ 消费速率 ≈ 1条/秒

代码:
  @Bean
  Consumer<Message<PraiseMessage>> consumer(PraiseService svc) {
      return msg -> svc.praiseItem(msg.getPayload().getItemId());  ← MQ 每来一条回调一次
  }
```

**配置里的 `definition: consumer` 与 Bean 名 `consumer()` 严格对应**，通道名自动推导为 `consumer-in-0` —— 三者环环相扣，少一环就收不到消息。

### 削峰填谷的完整闭环

```
瞬时 100 赞/秒 ──► 生产者秒收(只发MQ) ──► MQ缓冲区堆积
                                              │ 消费者按 1条/秒 平滑拉取
                                              ▼
                                    数据库写入压力恒定 ≈1 QPS
```

## 二、需要学习的知识点

1. **Spring Cloud Stream 函数式消费模型**（对照老式 `@EnableBinding`+`@StreamListener`）：
   纯 `java.util.function.Consumer` 函数 Bean，无框架注解侵入；理解 `函数名-in-0` 通道命名规则。
2. **消费组的意义**：`group: praise-consumer-group-PRAISE-TOPIC-01` —— 同组多实例**分摊**消息（扩容即提速），不同组各自全量消费。
3. **拉取速率控制**：`pullInterval`/`pullBatchSize` 两个旋钮如何调节数据库压力 —— 这是"填谷"的阀门。
4. **消息反序列化**：`content-type: application/json` + 泛型 `Message<PraiseMessage>` 自动解码。
5. **最终一致性体验**：点赞后查询数字"慢半拍"属正常现象 —— 异步系统的固有特征。

## 三、学习目的

- 补齐异步链路的"另一半"：只会发不会消费等于没学 MQ；
- 掌握函数式消费模型，这是当前 Spring Cloud Stream 官方推荐、面试常考的写法；
- 理解**消费速率 = 下游保护阀**的设计思想，学会用配置而非代码保护数据库。

## 四、以后怎么用

1. **接入姿势（两步）**：引入 stream-rocketmq starter；配置中心写 `function.definition` + `bindings.消费函数-in-0` + 消费组，再提供同名的 `Consumer` Bean。
2. **典型场景**：与本模块同构——异步落库、发短信、刷新缓存、ETL 清洗。
3. **生产要点**：
   - **幂等消费**：消息可能重投，落库前按消息 ID/业务键去重（本示例简化未做，生产必须加）；
   - 异常处理：消费函数抛异常会触发重试，需配置重试次数与死信队列；
   - 扩容：同组加实例即提升消费并行度，与 pullBatchSize 配合调优。
4. **调参经验**：`pullInterval` 越小延迟越低但请求越频繁；`pullBatchSize` 越大吞吐越高但单批处理时间变长 —— 延迟与吞吐的平衡。
