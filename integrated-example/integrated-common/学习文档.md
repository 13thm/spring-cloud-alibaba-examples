# 学习文档：integrated-common（公共模块）

> 位置：`integrated-example/integrated-common` —— 整个整合示例的"地基"，
> 被 account / storage / order 三个业务服务依赖，提供**统一响应体**与**业务异常**。

---

## 一、这个模块做了什么

它不是可运行的服务（没有启动类、没有端口），而是一个被其他模块 Maven 依赖的**公共 jar**，内容只有 4 个类：

| 类 | 类型 | 职责 |
|---|---|---|
| `Result<T>` | 泛型类 | 统一响应包装：`{code, message, data}`，附一堆静态工厂方法 |
| `IResult` | 接口 | 结果码抽象（`getCode()`/`getMessage()`），供枚举实现 |
| `ResultEnum` | 枚举 | 内置两个码：`SUCCESS(2001)` / `COMMON_FAILED(2003)` |
| `BusinessException` | 运行时异常 | 业务失败信号（库存不足/余额不足），是触发 Seata 回滚的"扳机" |

### 在整体架构中的角色

```
所有服务的 Controller 出参 ──────► Result<T> 统一格式
订单服务判断 Feign 响应 code ────► ResultEnum.COMMON_FAILED(2003)
库存/账户 Service 校验失败 ──────► throw BusinessException
                                └─► 冒泡穿过 @GlobalTransactional → Seata 全局回滚
```

## 二、需要学习的知识点

1. **统一响应体设计**
   - 为什么微服务间要约定统一响应格式（Feign 调用方靠 code 判断下游业务成败）；
   - 静态工厂方法（`Result.success()/failed()`）优于构造器的写法；
   - 泛型 `Result<T>` 如何让 data 装载任意类型。
2. **接口 + 枚举的错误码扩展模式**
   - `ResultEnum implements IResult`，新错误类型只需加枚举项，`Result.failed(IResult)` 无需改动 —— 开闭原则的最小落地案例。
3. **业务异常规范**
   - 继承 `RuntimeException`（非受检）的取舍：不强制调用方 try-catch，配合 AOP/全局异常处理更顺滑；
   - **它与 Seata 的隐含契约**：必须能从全局事务方法中抛出去，TM 才会回滚。
4. **公共模块的边界感**
   - 什么该放 common（Result/异常/工具），什么不该放（DTO 各服务自留一份，避免公共模块膨胀成"垃圾场"）。

## 三、学习目的

- 掌握微服务工程里**第一块必须先写的代码**——统一响应与统一异常的姿势，任何新项目起步都离不开；
- 理解"业务码 2001/2003 与 HTTP 状态码 200 的分层"：传输层成功 ≠ 业务成功；
- 为看懂后续三个业务模块的 Controller/Service 交互打好基础。

## 四、以后怎么用

1. **直接复用模板**：新项目把本模块 4 个类抄走即可用；扩展错误码时在 `ResultEnum` 加枚举或另建枚举类实现 `IResult`。
2. **进阶方向**（本示例未做、生产常见）：
   - 加 `@RestControllerAdvice` 全局异常处理器，让 `BusinessException` 自动转 `Result`，Controller 不再手写 try-catch；
   - Result 增加时间戳/追踪 ID 字段，便于链路排查；
   - 抽成独立 `xxx-common`/`xxx-api` 模块发布私服，供多团队共享。
3. **踩坑提示**：Feign 调用方判断的是 `Result.code` 而非异常本身——下游 200 响应里藏着业务失败，调用方**必须显式判断**，这一点在 OrderServiceImpl 里看得最清楚。
