# 学习文档：integrated-account（账户服务）

> 位置：`integrated-example/integrated-account`（端口 8012）—— 下单链路的
> **Seata AT 模式分支事务参与者（RM）**，负责扣减用户余额。与库存服务结构完全对称，
> 是"第二个 RM"，用来演示**全局回滚的触发点**。

---

## 一、这个模块做了什么

标准三层微服务，操作独立的 `integrated_account` 库：

| 文件 | 作用 |
|---|---|
| `AccountServiceApplication` | 启动类 |
| `AccountController` | `POST /account/reduce-balance` 扣余额（被订单 Feign 调）；`GET /account/?userId=` 查余额 |
| `AccountDTO` | 扣减请求（userId + price） |
| `AccountService(Impl)` | 核心：`@Transactional` 分支事务 + 余额校验 |
| `AccountMapper` | 注解 SQL；**UPDATE 带 `AND money >= ${price}` 防扣成负数** |
| `application.yaml` | Nacos 双中心 + Seata 配置 |
| SQL: account 表 + undo_log | **初始余额仅 3 元**（商品 2 元/件 → 第二单必失败） |

### 它是"回滚触发点"的刻意设计

```
初始数据: 库存 100 件, 余额 3 元, 单价 2 元
第 1 单(1件): 扣库存✓ → 扣余额 2 元✓ → 订单落库✓ → 全局提交
第 2 单(1件): 扣库存✓(99→98) → 余额只剩 1 元 ✗ "no enough balance"
              → 异常冒泡到订单服务的 @GlobalTransactional
              → Seata 全局回滚 → 库存 98→99 恢复, 余额保持 1 元, 无订单
```

余额不足 = 整条链路的"事故点"，库存的自动恢复就是 AT 模式补偿的直观证据。

### 本模块独有的细节：SQL 层兜底

```sql
UPDATE account SET money = money - #{price} WHERE user_id = ? AND money >= ${price}
```
即使并发下前置校验失效（检查时有钱、更新时没钱），SQL 条件也能保证余额不为负，
此时影响行数为 0，Service 判断 `updateCount == 0` 抛异常 —— **双重防线**。

## 二、需要学习的知识点

1. **RM 分支事务标准写法**（与 storage 模块对照学习，完全同构）：
   `@Transactional` + XID 日志 + 前置校验 + 影响行数校验。
2. **业务失败如何"跨服务传染"**（本模块最重要的链路理解）：
   `BusinessException` → Controller 捕获转 `Result.failed()`（HTTP 200 + code 2003）
   → 订单服务 Feign 拿到后**手动判 code 抛异常** → AOP 触发全局回滚。
3. **数据库层并发安全**：条件 UPDATE 防超扣，对比库存模块的纯前置校验，体会两种防线取舍。
4. **`${}` 与 `#{}` 的差异**：`${price}` 是 SQL 拼接（演示写法），生产应全部用 `#{}` 预编译防注入。

## 三、学习目的

- 巩固 RM 角色写法（和 storage 对照，理解"模板化"）；
- 深刻理解**分布式事务里"失败信号"的传递路径**——为什么回滚能发生、靠什么发生；
- 学习资金类服务特有的严谨写法（余额永不透支的双保险）。

## 四、以后怎么用

1. 所有参与分布式事务的存量服务照抄本模块四步接入：依赖 → undo_log 表 → seata 配置 → `@Transactional` 保持原样。
2. **资金操作铁律**（从本模块提炼）：
   - 扣减类 UPDATE 一律带余额充足条件；
   - 判断影响行数而不是只看是否抛异常；
   - 金额字段生产用 `DECIMAL` 而非 INT（示例简化了）。
3. 回滚排查三板斧：XID 串日志 → 看 TC 全局事务状态 → 查各库 undo_log。
