# 学习文档：integrated-praise-provider（点赞生产者）

> 位置：`integrated-example/integrated-praise-provider`（端口 8015）—— 点赞场景的
> **RocketMQ 消息生产者**，用 Spring Cloud Stream 的 `StreamBridge` 发消息，践行"削峰填谷"的前半段。

---

## 一、这个模块做了什么

接收点赞 HTTP 请求后**不碰数据库**，只把消息扔进 RocketMQ 就立刻返回：

| 文件 | 作用 |
|---|---|
| `PraiseProviderApplication` | 启动类 |
| `PraiseController` | ★核心：`GET /praise/rocketmq` 与 `/praise/sentinel` 两个路径同一逻辑，`StreamBridge.send("praise-output", msg)` 发消息 |
| `PraiseMessage` | 消息体（itemId），JSON 序列化传输 |
| `application.yaml` | 本地只有 Nacos 地址；**MQ 绑定全在 Nacos 的 integrated-provider.yaml** |

Nacos 配置（integrated-provider.yaml）的映射关系：

```
代码: streamBridge.send("praise-output", message)
        │ 绑定名
        ▼
bindings.praise-output.destination = PRAISE-TOPIC-01  (RocketMQ Topic)
bindings.praise-output.content-type = application/json
rocketmq.binder.name-server = rocketmq:9876
producer.group = test
```

### 同一接口服务两个演示场景

- `/praise/sentinel`：请求先过网关，超 5 QPS 被限流拦截（到不了本服务）——"硬抗"方案；
- `/praise/rocketmq`：请求全收下转成消息 ——"软扛"方案，多余流量堆在 MQ 里等待消费。

## 二、需要学习的知识点

1. **Spring Cloud Stream 函数式模型（发送侧）**
   - 新版用 `StreamBridge` 动态发送，对比老版 `Source` 接口 + `@EnableBinding` + `MessageChannel`；
   - binder 抽象：同一套代码，换配置即可从 RocketMQ 切到 Kafka/RabbitMQ ——**屏蔽中间件差异**是 Stream 的核心价值。
2. **消息构建**：`MessageBuilder.withPayload(...).build()`，可加 header（追踪 ID、延迟级别等）。
3. **RocketMQ 基础**：NameServer(9876) vs Broker、Topic、生产者组的概念。
4. **削峰填谷 vs 限流** 的架构差异：拒绝式（用户有感）vs 缓冲式（用户无感、结果延迟）。
5. **配置外置**：MQ 地址、topic 名全部放 Nacos，换环境零代码改动。

## 三、学习目的

- 掌握**异步化改造**的第一步：把"同步写库"改成"发消息就返回"，这是高并发系统的通用降压手段；
- 学会 StreamBridge 发送的标准姿势，理解 binding/destination/binder 三层配置关系；
- 建立"上游轻、下游缓"的流量治理思维。

## 四、以后怎么用

1. **接入姿势（两步）**：引入 `spring-cloud-starter-stream-rocketmq`；在配置中心写 `bindings.输出名.destination/topic`，代码里 `streamBridge.send(输出名, message)`。
2. **典型场景**：点赞/浏览量/日志采集/订单异步处理/短信通知——一切"允许延迟、追求吞吐"的写操作。
3. **生产要点**：
   - 发送失败处理（返回值 boolean，必要时落库重发或告警）；
   - 消息体统一加消息 ID/时间戳，方便对账与幂等；
   - 大消息考虑压缩或只发引用（ID），payload 保持精简。
4. **进阶**：RocketMQ 事务消息、延迟消息、顺序消息——都在这套 Stream 体系上扩展。
