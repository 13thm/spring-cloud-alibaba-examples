# Spring Cloud Scheduling Example 学习分析 — 定时任务从"单机跑"到"集群抢锁"

> 一个只有**两个 Job** 的迷你示例,却回答了微服务时代的经典问题:
> `@Scheduled` 任务部署了 3 个实例,会不会执行 3 遍?
> 本模块用 job1/job2 一对"对照组"给出答案:裸跑的会重复,加了 `@SchedulerLock` 的全局只有一份;
> 并提供 ShedLock(开源,靠数据库)与 SchedulerX(阿里云)两条分布式路线,二选一切换 profile 即可。

## 1. 一句话理解这个示例

> 启动两个实例,每分钟第 0 秒各跑两个定时任务:
> **job1(无锁)** 两台都执行 → 重复;**job2(@SchedulerLock)** 同一时刻全局只有一台执行 → 不重复。
> 一个注解,就是"分布式调度"与"重复劳动"的分界线。

```
            每分钟第 0 秒
实例 A ──► job1 ✓ 执行     job2 ✓ 抢到锁,执行
实例 B ──► job1 ✓ 执行     job2 ✗ 抢锁失败,跳过本轮
              │                │
              ▼                ▼
          重复执行 2 次     全局恰好 1 次
```

## 3. 问题:集群下的 @Scheduled 之痛

Spring 原生 `@Scheduled` 是**纯单机语义**:

```
@SpringBootApplication + @EnableScheduling
        ↓
每个 JVM 各自维护一个 TaskScheduler(线程池)
        ↓
到点就跑——实例之间互相不知道对方的存在
```

| 场景 | 后果 |
|---|---|
| 对账/结算任务 ×3 实例 | **跑 3 遍**(重复记账,资损) |
| 缓存预热 ×3 实例 | 浪费 2/3 资源(能忍) |
| 发提醒短信 ×3 实例 | 用户收 3 条(事故) |

解决思路两派:

- **抢锁派**:任务照旧每台都触发,开跑前先抢一把**全局锁**,抢到才执行——ShedLock 是代表(**本文主线**)
- **调度派**:由中心调度器决定"谁、何时、跑什么",实例只是执行器——SchedulerX/XXL-JOB/Quartz 集群是代表

SCA 的 scheduling 模块把两条路线统一在一个 starter + 一个配置项(`distributed-mode`)下。

## 4. 核心代码精读:job1 与 job2 的一线之差

```java
@Component
public class SimpleJob {

    /**
     * 裸跑:不加锁,所有实例同一时刻都会执行。
     */
    @Scheduled(cron = "0 */1 * * * ?")                 // 每分钟第 0 秒
    public void job1() {
        logger.info("time=" + DateTime.now().toString("YYYY-MM-dd HH:mm:ss") + " do job1...");
    }

    /**
     * 加锁:同一时刻全局只有一个实例执行。
     */
    @Scheduled(cron = "0 */1 * * * ?")
    @SchedulerLock(name = "lock-job2", lockAtMostFor = "10s")   // ★ 锁名 + 兜底超时
    public void job2() throws InterruptedException {
        logger.info("time=" + ... + " do job2...");
        TimeUnit.SECONDS.sleep(1L);                    // 模拟 1 秒的活儿
    }
}
```

`@SchedulerLock` 两个参数的语义:

| 参数 | 作用 | 本例 |
|---|---|---|
| `name` | **锁的唯一标识**(落库的主键)——同名任务全局互斥 | `lock-job2` |
| `lockAtMostFor` | **兜底持锁上限**:持锁进程崩溃了,锁最多僵死这么久,之后自动可抢 | 10s |
| `lockAtLeastFor`(本例未用) | 最短持锁时间,防任务过快结束导致时钟偏差下重复执行 | - |

注意:**锁应该大于任务最长执行时间**(这里任务 1s,锁上限 10s,安全);
若任务可能跑 30s 而锁只保 10s,第 11 秒别的实例就能抢到锁 → 重复执行(见坑 4)。

## 5. ShedLock 原理:用数据库行锁当"令牌"

```
到点,实例 A、B 同时触发 job2
   │
   ├─ A:INSERT/UPDATE shedlock 表(name='lock-job2', lock_until=now+10s) 成功 → 执行任务
   └─ B:UPDATE ... WHERE name='lock-job2' AND lock_until <= now   → 影响 0 行 = 抢锁失败 → 本轮跳过
                                                              (不等待、不排队,直接弃权)
   A 任务结束(可配 lockAtLeastFor 延长)释放;下一分钟重新开抢
```

要点:

1. **锁即一行数据**:表 `shedlock` 里每个锁名一行,`lock_until` 时间戳就是"租期"
2. **抢不到就放弃**,不是排队——同一轮只可能有一个赢家,其余实例本轮静默
3. **时钟是隐形前提**:各实例 DB 服务器时钟一致(时间戳都在 DB 侧算,规避了应用时钟偏差)
4. AOP 实现:`@SchedulerLock` 由 ShedLock 的代理拦截,业务方法零改造

ShedLock ≠ 分布式任务调度:它**不负责"何时跑"**(仍由各实例自己的 cron 决定),
只负责"到点后**谁真的跑**"——一句话:**它是去重器,不是调度器**。

## 6. 两种分布式模式:shedlock vs schedulerx

`application.yaml` 里 `spring.profiles.active: shedlock` 二选一切换:

| | shedlock(默认) | schedulerx |
|---|---|---|
| 依赖 | 自己的 MySQL(建库建表) | 阿里云 SchedulerX 控制台开通(免费额度) |
| 配置 | `distributed-mode: shedlock` + datasource 四件套 | `distributed-mode: schedulerx` + endpoint/namespace/groupId/appKey |
| 本质 | 抢锁去重(任务定义还在代码 cron) | 中心调度(控制台可视化管理任务、可动态改触发) |
| 适合 | 已有 MySQL、任务简单、想全开源自托管 | 要可视控制台/告警/重试/工作流,可接受云依赖 |

schedulerx 模式的配置(从控制台拿四要素):

```yaml
spring.cloud.scheduling:
  distributed-mode: schedulerx
  schedulerx:
    endpoint: acm.aliyun.com
    namespace: aad167f6-xxxx-...
    groupId: xxxxx
    appKey: PZm1XXXXXXXXXXXX
    # task-sync: true   # 可选:把代码里的 @Scheduled 任务同步上云管理
```

## 7. 环境搭建与运行(shedlock 模式,默认)

1. **MySQL 建库**:`CREATE DATABASE testdb;`(名字对应 application-shedlock.yaml 里的 url)
2. **建 shedlock 表**(README 没给 DDL,标准 schema 如下):
   ```sql
   CREATE TABLE shedlock (
       name       VARCHAR(64)  NOT NULL,
       lock_until TIMESTAMP(3) NOT NULL,
       locked_at  TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
       locked_by  VARCHAR(255) NOT NULL,
       PRIMARY KEY (name)
   );
   ```
3. 改 `application-shedlock.yaml` 的 url/username/password
4. **单实例**:直接跑 `ScheduleApplication`,每分钟看两条日志
5. **双实例(核心实验)**:IDEA 建两个启动项,分别加 `--server.port=18080` / `--server.port=18081`:
   - job1:两台**都**打印(重复)
   - job2:**只有一台**打印,另一台静默;`SELECT * FROM shedlock` 能看到 `lock-job2` 的租期在滚动

## 8. 企业里怎么用?

- **选型经验法则**:
  ```
  任务少、有 DB、不想加组件       → ShedLock(本文)+ @Scheduled,10 分钟接入
  任务多、要可视/告警/重试/手动触发 → XXL-JOB / SchedulerX / PowerJob 等调度平台
  秒级大规模、依赖大数据生态      → 自研 or 云调度
  ```
- ShedLock 常见生产形态:对账兜底重跑、报表预生成、缓存预热、证书续期——"偶尔跑、跑重复了会出事"的任务
- **lockAtMostFor 估算法**:任务 P99 耗时 × 3 起步,宁可锁久点也别提前放人
- **优雅停机**:本例 `task.scheduling.shutdown.await-termination: true`(最多等 60s)——
  发布重启时让正在跑的任务收尾,这是容易被忽略的生产细节
- 调度平台化后,@Scheduled 仍会保留在工具类/单体服务里——**这个知识点永远不过时**

## 9. ⚠️ 注意事项与坑

### 坑 0:parent 链断裂(与 nacos 家族同款)
pom 指向根 `com.alibaba.cloud:...:${revision}`,根 pom 已是 `com.thm.cloud` 空壳 → 编译不过。修法见 nacos-discovery 学习路线图坑 0。

### 坑 1:application-shedlock.yaml 里 driver 拼错了
```yaml
spring.datasource:
  driver-class: com.mysql.cj.jdbc.Driver     # ✗ 应为 driver-class-name
```
`driver-class` 不是合法属性(被静默忽略)。**没炸是因为** Boot 能从 jdbc url 自动推断驱动类——
但换某些场景(无 url 推断、多数据源)就会翻车。照抄配置时改成 `driver-class-name:`。

### 坑 2:README 把两份 profile 文件写反了
README"方案一(shedlock)"却说"在 application-schedulerx.yml 中修改"——实际 shedlock 配置在
`application-shedlock.yaml`。看文档不如看文件名。

### 坑 3:shedlock 表要自己建
README 只说"创建数据实例",没给建表 DDL(见第 7 节)。没建表的报错很直白:`Table 'testdb.shedlock' doesn't exist`。

### 坑 4:lockAtMostFor 小于任务耗时 = 形同虚设
任务跑 30s、锁只保 10s → 第 11 秒其他实例抢锁成功,同一任务并发两份。**估锁时长的责任在开发者**。

### 坑 5:cron 只在"每分钟"粒度对齐
`0 */1 * * * ?` 两实例同一秒触发才会"抢";若 cron 各实例不一致(或时钟漂移到不同秒),锁的互斥窗口错开,可能出现先后各跑一次。ShedLock 的假设是**所有实例同一时刻到点**。

### 坑 6:日志时间格式用了大写 YYYY
`"YYYY-MM-dd HH:mm:ss"` 里 **`YYYY` 是 week-based year(按周年份)**,年末跨年那一周会打出下一年份(如 2024-12-29 打成 2025)。正确姿势是小写 `yyyy` 或直接用 `java.time.LocalDateTime`。

### 坑 7:joda-time 是"顺来的"
代码 import 了老牌日期库 `org.joda.time.DateTime`——它是 schedulerx starter 的传递依赖,顺手拿来格式化时间。**新代码请用 java.time,demo 别学这一笔**。

### 坑 8:不用 schedulerx 也要引它的 starter
`spring-cloud-starter-alibaba-schedulerx` 是模式入口,shedlock 的装配也在这个 starter 里——依赖不可省,但云上配置可以完全不填。

## 10. 知识点总结与动手练习

### 本模块覆盖的知识点
- ✅ @Scheduled 的单机语义与集群重复执行问题
- ✅ @SchedulerLock 的 name / lockAtMostFor / lockAtLeastFor 参数语义
- ✅ ShedLock 行锁租期原理:抢不到就弃权,是“去重器”不是“调度器”
- ✅ shedlock 与 schedulerx 两种 distributed-mode 的取舍
- ✅ 优雅停机 await-termination;driver-class-name / YYYY 等配置坑

### 推荐动手练习(由浅入深)

1. **复现对照实验**:双实例跑起来,连续观察 3 分钟,记录 job1/job2 在两台上的打印矩阵(预期 job1=2 行/分钟,job2=1 行/分钟)
2. **看锁**:轮询 `SELECT name, lock_until, locked_by FROM shedlock`,观察 `lock_until` 随执行滚动、`locked_by` 是否轮换(负载随机,谁抢到是谁)
3. **复现坑 4**:把 `lockAtMostFor` 改成 `1s`、任务 sleep 拉长到 5s,双实例下观察 job2 开始重复——亲手体会"锁租期必须盖过任务"
4. **修坑 1**:把 `driver-class` 改成 `driver-class-name`,启动对比 debug 日志里数据源属性的变化
5. **掐表验证 job1 重复**:给 job1 加个计数器输出(如静态 AtomicInteger),双实例跑 5 分钟,确认计数=2×轮数
6. **进阶**:把 job2 的 cron 改成 `*/10 * * * * ?`(每 10 秒),观察高频下抢锁的分布——哪台赢多赢少?为什么?(提示:上一轮持锁者续期近水楼台)

### 一句话总结

> 这个两 Job 的小示例讲了一个大道理:**集群里 @Scheduled 是"人人有份",@SchedulerLock 才是"一个萝卜一个坑"**——
> 分布式定时任务的第一课不是学调度平台,而是先想清楚"这个任务,到底该跑几遍"。
