## 1. 项目定位:它是什么?

这是一个 **Sentinel 基础能力演示**工程,不需要任何其他微服务配合(除了可选的 Nacos 和控制台),
单进程即可演示:

| 演示能力 | 对应代码/配置 |
|----------|---------------|
| URL 自动埋点限流 | 引 starter 即生效,`/test`、`/hello` 规则 |
| 注解埋点 + 热点参数限流 | `@SentinelResource("aa")` + param-flow.json |
| 5 种规则全配置 | flow / degrade / authority / system / param-flow |
| 文件数据源 + Nacos 数据源 | yml 的 `datasource.ds1~ds6` |
| 被拦截后跳转统一错误页 | `block-page: /errorPage` + thymeleaf 页面 |
| RestTemplate 调用防护 | `@SentinelRestTemplate(blockHandler=...)` |
| Spring Cloud 断路器抽象接 Sentinel | `CircuitBreakerFactory` + `/slow` 接口 |

> 💡 建议配合家族总览的[资源命名汇总表](../学习总览.md#4-资源命名规则汇总跨模块对照重要)阅读本篇,
> "资源名对不对"是本模块所有实验成败的关键。

## 3. 核心概念:资源的三种埋点方式

Sentinel 一切都围绕"资源"。本模块一口气演示了三种把代码变成"资源"的方式:

### 3.1 方式一:URL 自动埋点(零代码)
引入 `spring-cloud-starter-alibaba-sentinel` 后,Sentinel 的 CommonFilter 会自动把
**每个进来的 HTTP 请求**包装成资源,**资源名就是 URL 路径**,如 `/hello`、`/test`。
业务代码一行都不用改,直接在规则里用 URL 当资源名即可限流。

### 3.2 方式二:`@SentinelResource` 注解埋点(方法级)
想保护某个**业务方法**而不仅是 URL,就在方法上加注解:

```java
@GetMapping("/hello")
@SentinelResource("resource")      // 资源名叫 "resource"(不是 URL!)
public String hello() { return "Hello"; }
```

注意:`/hello` 这个 URL 同时存在**两个资源**——URL 资源 `/hello` 和注解资源 `resource`,
规则配给哪个,就管哪个。

### 3.3 方式三:`@SentinelRestTemplate`(出站调用埋点)
保护**你调用别人**的请求:给 RestTemplate Bean 加注解,Sentinel 织入拦截器,
资源名格式为 `方法:URL`(如 `GET:http://www.taobao.com`):

```java
@Bean
@SentinelRestTemplate(blockHandler = "handleException",
        blockHandlerClass = ExceptionUtil.class)
public RestTemplate restTemplate() { return new RestTemplate(); }
```

## 4. 启动类分析 SentinelCoreApplication

📄 `SentinelCoreApplication.java`(精简后):

```java
@SpringBootApplication
public class SentinelCoreApplication {

	// ① 被 Sentinel 保护的 RestTemplate:被限流时走 ExceptionUtil.handleException
	@Bean
	@SentinelRestTemplate(blockHandler = "handleException",
			blockHandlerClass = ExceptionUtil.class)
	public RestTemplate restTemplate() { return new RestTemplate(); }

	// ② 裸 RestTemplate:不受 Sentinel 保护,做对照实验用
	@Bean
	public RestTemplate restTemplate2() { return new RestTemplate(); }

	// ③ 自定义 JSON 转换器:数据源读文件时用它把文本转成 List<FlowRule>
	@Bean
	public Converter myConverter() { return new JsonFlowRuleListConverter(); }

	// ④ Spring Cloud CircuitBreaker 抽象接 Sentinel:默认规则=RT 超 100ms 熔断 10 秒
	@Bean
	public Customizer<SentinelCircuitBreakerFactory> defaultConfig() {
		return factory -> factory.configureDefault(id -> new SentinelConfigBuilder()
				.resourceName(id)
				.rules(Collections.singletonList(new DegradeRule(id)
						.setGrade(RuleConstant.DEGRADE_GRADE_RT).setCount(100)
						.setTimeWindow(10)))
				.build());
	}
}
```

**四个 Bean 的分工:**

| Bean | 教学点 |
|------|--------|
| `restTemplate` | 出站请求限流 + 自定义 blockHandler 兜底 |
| `restTemplate2` | 对照组:同样的调用没注解就完全不受控,体会"埋点"的意义 |
| `myConverter` | 数据源规则解析可插拔(默认用 fastjson 转换,这里演示自定义) |
| `defaultConfig` | `CircuitBreakerFactory` 是 Spring Cloud 的**断路器抽象**;`Customizer` 注入 Sentinel 实现,并给所有断路器配默认熔断规则(RT>100ms,熔断 10s) |

> 💡 `CircuitBreakerFactory` 这层抽象的意义:业务代码只面向
> `circuitBreakerFactory.create("name").run(调用, 兜底)`,
> 底下是 Sentinel 还是 Resilience4j 可随时替换——见 TestController 的 `/slow`。

## 5. 接口分析 TestController:5 个实验入口

📄 `TestController.java`(精简后):

```java
@RestController
public class TestController {

	@Autowired
	private RestTemplate restTemplate;              // 上面 ① 那个受保护的
	@Autowired
	private CircuitBreakerFactory circuitBreakerFactory;

	@GetMapping("/hello")
	@SentinelResource("resource")                    // 实验 1:URL 与注解双资源
	public String hello() { return "Hello"; }

	@GetMapping("/aa")
	@SentinelResource("aa")                          // 实验 2:热点参数限流
	public String aa(int b, int a) { return "Hello test"; }

	@GetMapping("/test")                             // 实验 3:URL 资源 count=0 全拦
	public String test1() { return "Hello test"; }

	@GetMapping("/template")                         // 实验 4:RestTemplate 出站限流
	public String client() {
		return restTemplate.getForObject("http://www.taobao.com/test", String.class);
	}

	@GetMapping("/slow")                             // 实验 5:断路器慢调用熔断
	public String slow() {
		return circuitBreakerFactory.create("slow").run(() -> {
			Thread.sleep(500L);                      // 故意睡 500ms > 规则的 100ms
			return "slow";
		}, throwable -> "fallback");                 // 熔断后的兜底
	}
}
```

| 接口 | 资源名(记牢!) | 预设规则 | 预期现象 |
|------|----------------|----------|----------|
| `/hello` | `/hello`(URL)和 `resource`(注解) | flow: `/hello` QPS=1 | 1 秒内第 2 次 → 跳 errorPage |
| `/aa?b=..&a=..` | `aa`(注解,参数 b、a) | param-flow: b=2 限 1QPS,其他值全拒 | b=2 刷 2 次被拦;b=3 永远被拦 |
| `/test` | `/test`(URL) | flow: `/test` QPS=**0** | 一打开就被拦 → errorPage(演示"全拒") |
| `/template` | `GET:http://www.taobao.com` | flow QPS=**0** | 请求根本发不出去,直接返回 `custom block info` |
| `/slow` | `slow`(断路器 id) | RT>100ms 熔断 10s | 熔断打开后立即返回 `fallback`,不再 sleep |

## 6. 配置文件分析 application.yml

```yaml
spring:
  application:
    name: sentinel-core-example
  cloud:
    sentinel:
      transport:
        dashboard: localhost:8080   # ① Sentinel 控制台地址(没起也能跑,只是看不到监控)
      datasource:                   # ② 规则数据源:一个 ds 一个来源
        ds1: { file: { file: classpath:flowrule.json,  data-type: json, rule-type: flow } }
        ds2: { file: { file: classpath:degraderule.json, data-type: json, rule-type: degrade } }
        ds3: { file: { file: classpath:authority.json, data-type: json, rule-type: authority } }
        ds4: { file: { file: classpath:system.json,     data-type: json, rule-type: system } }
        ds5: { file: { file: classpath:param-flow.json, data-type: json, rule-type: param_flow } }
        ds6:                        # ③ 规则从 Nacos 拉(可动态推送,生产推荐形态)
          nacos:
            server-addr: 127.0.0.1:8848
            username: nacos
            password: nacos
            data-id: flowrule.json
            data-type: json
            rule-type: flow
      block-page: /errorPage        # ④ URL 资源被拦后统一跳转的页面
      eager: true                   # ⑤ 启动即向控制台注册(而不是等第一次请求)

server:
  port: 18083
```

**三个重点:**

1. **数据源的结构**:`ds名 → 类型 → 属性 + rule-type`。`rule-type` 决定 JSON 反序列化成哪种规则
   (flow/degrade/authority/system/param_flow/gw-flow/gw-api-group)。
2. **file vs nacos**:file 数据源启动时读一次,重启重读,改文件要重启;
   nacos 数据源监听配置变化,**规则动态生效**——这是"生产规则放配置中心"的雏形。
3. **block-page 只对 URL 资源生效**:注解资源被拦不走 block-page,要靠 blockHandler(见坑 4)。

## 7. 五大规则文件逐个精读

### 7.1 flowrule.json — 流控规则

```json
[
  { "resource": "/hello",  "count": 1, "grade": 1, "controlBehavior": 0,
    "limitApp": "default", "strategy": 0 },
  { "resource": "/test",   "count": 0, "grade": 1, ... },
  { "resource": "GET:http://www.taobao.com", "count": 0, "grade": 1, ... }
]
```

- `/hello`:QPS=1,1 秒内第 2 个请求被拦(快速失败)
- `/test`:QPS=**0 = 全部拒绝**(演示 block-page 的固定戏码)
- `GET:http://www.taobao.com`:RestTemplate 出站资源名格式验证,同样全拒——
  **注意资源名里没有 `/test` 路径**,Sentinel 的 RestTemplate 资源默认只精确到 host(见坑 6)

### 7.2 degraderule.json — 熔断规则(慢调用比例)

```json
[
  { "resource": "aa",   "count": 20.0, "grade": 0, "passCount": 0, "timeWindow": 10 },
  { "resource": "abc1", "count": 15.0, "grade": 0, "passCount": 0, "timeWindow": 10 }
]
```

- `grade: 0` = **慢调用比例**策略:`count: 20.0` 表示 RT 阈值 20ms——
  统计窗口内请求 RT 全部超过 20ms 且达到最小请求数,就熔断 `aa` 资源 10 秒
- `passCount` 是老版本字段名(现已叫 `minRequestAmount`),fastjson 反序列化时会被忽略,走默认值 5
- `abc1` 资源在代码里**根本不存在**,是一条"死规则"(见坑 3)
- `/aa` 接口瞬间返回,RT 远小于 20ms,这条规则平时不会触发——想触发它,自己给 `/aa` 加个 `Thread.sleep(50)`

### 7.3 authority.json — 授权规则(黑白名单)

```json
[
  { "resource": "good",     "limitApp": "abc", "strategy": 0 },   // 白名单:只允许来源 abc
  { "resource": "bad",      "limitApp": "bcd", "strategy": 1 },   // 黑名单:拒绝来源 bcd
  { "resource": "terrible", "limitApp": "aaa", "strategy": 1 }
]
```

⚠️ 三个资源在代码里都没有对应接口——这份文件只是**格式演示**。
来源"abc"从哪来?需要实现 `RequestOriginParser`(如解析某个请求头)才能生效,本模块未演示,进阶练习里补。

### 7.4 system.json — 系统自适应规则

```json
[ { "highestSystemLoad": -1, "qps": 100, "avgRt": -1, "maxThread": 10 } ]
```

应用整体保护:入口总 QPS > 100 或并发线程 > 10 时**全应用拒绝新请求**;-1 表示该维度不启用。
这是 Sentinel 独有的"最后一道防线",防止系统被压垮后无法恢复(雪崩)。

### 7.5 param-flow.json — 热点参数规则(本模块最精彩的实验)

```json
[
  { "resource": "aa", "count": 0, "grade": 1, "paramIdx": 0,
    "paramFlowItemList": [ { "object": "2", "classType": "int", "count": 1 } ] }
]
```

逐字段拆解(对照 `aa(int b, int a)`,参数顺序:b 是第 0 个,a 是第 1 个):

| 字段 | 值 | 含义 |
|------|-----|------|
| `paramIdx` | 0 | 对**第 0 个参数(b)**做热点统计 |
| `count` | 0 | 默认阈值 QPS=0 → **其他所有 b 值全部拒绝** |
| `paramFlowItemList` | b=2 → 1 | 特例:b=2 时放行 1 QPS |

实验效果:`/aa?b=2&a=1` 每秒可过 1 次;`/aa?b=3&a=1` 永远被拦。
这就是"秒杀商品 ID 单独限流"的基本形态。

## 8. 辅助类:ExceptionUtil / JsonFlowRuleListConverter / WebMvcConfiguration

### 8.1 ExceptionUtil — RestTemplate 的兜底处理器

```java
public static SentinelClientHttpResponse handleException(HttpRequest request,
        byte[] body, ClientHttpRequestExecution execution, BlockException ex) {
    System.out.println("Oops: " + ex.getClass().getCanonicalName());
    return new SentinelClientHttpResponse("custom block info");
}
```

- 签名是**固定模板**:`HttpRequest, byte[], ClientHttpRequestExecution, BlockException`
- `BlockException` 是所有拦截异常的父类,子类能区分原因:
  `FlowException`(流控)/ `DegradeException`(熔断)/ `ParamFlowException`(热点)…
- 返回 `SentinelClientHttpResponse`,所以出站请求被拦时**接口最终返回字符串 "custom block info"**
- 细节:它不必是 Spring Bean,通过注解的 `blockHandlerClass` + 方法名反射调用

### 8.2 JsonFlowRuleListConverter — 自定义数据源转换器

```java
public class JsonFlowRuleListConverter implements Converter<String, List<FlowRule>> {
    @Override
    public List<FlowRule> convert(String source) {
        return JSON.parseObject(source, new TypeReference<List<FlowRule>>() {});
    }
}
```

演示"数据源的解析逻辑可插拔":文件/配置中心里是纯文本,总要有人转成规则对象。
默认就有 fastjson 实现,自己定义 Converter 后可以换成任意格式(xml、yaml、加密串都行)。
配合 `myConverter` Bean 注册生效。

### 8.3 WebMvcConfiguration + errorPage.html — 限流统一错误页

```java
@Configuration
@EnableWebMvc
public class WebMvcConfiguration implements WebMvcConfigurer {
    @Override
    public void addViewControllers(ViewControllerRegistry registry) {
        registry.addViewController("/errorPage").setViewName("errorPage");  // → templates/errorPage.html
    }
}
```

`block-page: /errorPage` 被触发时,Sentinel 会转发到这个地址,最终渲染出
"This is error page."。生产上这里一般放一个友好的"系统繁忙"页面。

## 9. 一次限流请求的完整流程图

以"1 秒内连刷两次 `GET /hello`"为例:

```
第 1 次 /hello ──────────────────────────────────► 返回 "Hello" ✅
                        │
                        │ StatisticSlot 滑动窗口计数: /hello 这一秒 QPS = 1

第 2 次 /hello
      │
      ▼
CommonFilter(自动埋点,资源名 "/hello")
      │
      ▼
Slot 责任链: 统计 → FlowSlot 查规则(资源 "/hello")
      │ QPS=1 已达阈值 → 抛 FlowException(BlockException 子类)
      ▼
SentinelWebInterceptor 捕获 BlockException
      │ 检查配置: block-page = /errorPage
      ▼
转发到 /errorPage → thymeleaf 渲染 errorPage.html
      │
      ▼
浏览器收到 "This is error page." ❌(业务方法 hello() 根本没执行!)
```

> 💡 关键认知:**被限流的请求不会进入业务代码**——这就是"流量防卫兵"的含义,
> 保护的不是某行代码,而是整个服务的容量。

## 10. 如何运行与实验设计

### 10.1 前置
1. (推荐)启动 Sentinel 控制台:`java -jar sentinel-dashboard-1.8.x.jar`(8080)
2. (可选)启动 Nacos(8848),想看 ds6 数据源效果时才必须;不起会刷连接失败日志但不阻断启动
3. 修复坑 1(parent 链)后:`mvn spring-boot:run`,端口 **18083**

### 10.2 五个实验(对照第 5 节表格逐个做)

```bash
# 实验 1:URL 限流。1 秒内连刷 2 次,第 2 次返回 errorPage
curl http://localhost:18083/hello
curl http://localhost:18083/hello        # → This is error page.

# 实验 2:热点参数限流
curl "http://localhost:18083/aa?b=2&a=1"   # 每秒 1 次内 → Hello test
curl "http://localhost:18083/aa?b=2&a=1"   # 1 秒内第 2 次 → ParamFlowException(500,见坑 4)
curl "http://localhost:18083/aa?b=3&a=1"   # b=3 无特例 → 永远 500

# 实验 3:count=0 全拒
curl http://localhost:18083/test           # → This is error page.(一打开就拦)

# 实验 4:RestTemplate 出站限流(请求不会真的发到淘宝)
curl http://localhost:18083/template       # → custom block info(控制台打印 Oops: ...FlowException)

# 实验 5:断路器慢调用熔断。用两个终端并发刷,统计窗口内凑够最小请求数(默认 5)
curl http://localhost:18083/slow           # 前 5 次: 约 500ms 返回 "slow"
curl http://localhost:18083/slow           # 熔断打开后(10 秒内): 秒回 "fallback"
```

### 10.3 控制台观察
- 打开 `http://localhost:8080`(sentinel/sentinel)→ 左侧服务列表 → `sentinel-core-example`
- **簇点链路**:能看到 `/hello`、`resource`、`aa`、`GET:http://www.taobao.com`、`slow` 等真实资源名
- **实时监控**:QPS 曲线、被拒 QPS(蓝色被拦部分)
- 试着在控制台直接给 `/test` 改 QPS=10 → 立刻放行(规则动态生效,但重启丢失,见坑 7)

## 11. ⚠️ 项目中存在的问题与坑(重要)

### 坑 1:parent 链断裂,直接编译不过 ❌
模块 parent 指向 `com.alibaba.cloud:spring-cloud-alibaba-examples:${revision}`,
根 pom 实际是 `com.thm.cloud:1.0-SNAPSHOT` 空壳。修法:改模块 parent 指向本地根 pom,
并在根 pom 补 spring-boot / spring-cloud / spring-cloud-alibaba 三大 BOM。
**这是全家族统一问题,详见[家族总览坑 0](../学习总览.md#8-️-全家族注意事项与坑)。**

### 坑 2:端口 18083 与 nacos-discovery-consumer、seata-order 撞车 ⚠️
同仓库有三个服务都用 18083。实验时先停掉另一边,或改本模块 `server.port`。

### 坑 3:大量"死资源/死文件",别被迷惑 ⚠️
- `degraderule.json` 里的 `abc1`:代码里没有这个资源,规则永远不会触发
- `authority.json` 里 `good/bad/terrible` 三个资源都不存在,且没实现 `RequestOriginParser`,
  整份文件是**纯格式展示**
- `flowrule.xml`:没有任何数据源引用它,是历史遗留死文件(想要 xml 数据源得配
  `rule-type: flow` + xml converter,本模块没配)
判断方法:控制台"簇点链路"里出现的资源名才是真资源。

### 坑 4:@SentinelResource 被拦后默认是"裸抛异常" ⚠️
`/aa` 触发热点限流时,`@SentinelResource` **没配 blockHandler**,ParamFlowException 直接抛出 →
浏览器 500。这与 URL 资源走 block-page 不同!正确姿势:

```java
@SentinelResource(value = "aa",
        blockHandler = "aaBlockHandler",          // 处理 BlockException(限流/熔断)
        fallback = "aaFallback")                  // 处理业务异常(可选,两者职责不同!)
public String aa(int b, int a) { ... }

public String aaBlockHandler(int b, int a, BlockException ex) {
    return "aa 被限流了: " + ex.getClass().getSimpleName();
}
```
注意 blockHandler 方法签名 = **原方法参数 + BlockException**,返回类型相同,且默认要在同一个类里
(或用 `blockHandlerClass` 指定外部类的 static 方法)。

### 坑 5:RestTemplate 资源名只到 host,不含 path ⚠️
`GET:http://www.taobao.com`——默认不细分路径,`/test`、`/anything` 共用同一个资源统计。
想按路径细分,要用 `@SentinelRestTemplate` 的 `urlCleaner`/`urlCleanerClass` 属性清洗
(参考 nacos-discovery-consumer 模块的 UrlCleaner 写法)。

### 坑 6:degraderule.json 的 `passCount` 是老字段 ⚠️
1.8 后叫 `minRequestAmount`,老字段反序列化时被忽略走默认值 5。
自己写规则请用新字段名,老博客里的 `passCount`/旧 grade 编号不要照抄。

### 坑 7:控制台改的规则重启即丢 ⚠️
控制台推送默认是"内存态"。本模块 file/nacos 数据源演示了持久化方向:
**规则以数据源为准**(Nacos 推送最理想),控制台仅作观察与临时调整。

## 12. 知识点总结与进阶练习

### 本模块覆盖的知识点
- ✅ Sentinel 三种埋点:URL Filter / `@SentinelResource` / `@SentinelRestTemplate`
- ✅ 五大规则(flow/degrade/authority/system/param-flow)的字段语义与文件数据源
- ✅ Nacos 数据源(ds6):规则动态推送形态
- ✅ block-page 统一限流页 + blockHandler 兜底(两者作用范围的区别)
- ✅ 热点参数限流(paramIdx / 特例参数阈值)
- ✅ Spring Cloud CircuitBreaker 抽象 + Sentinel 实现
- ✅ count=0 = 全部拒绝;grade 新旧语义差异

### 推荐动手练习(由浅入深)
1. 修好坑 1 → 跑通第 10 节 5 个实验,在控制台"簇点链路"里找到每个资源
2. 给 `/aa` 补上 blockHandler(坑 4 的代码),让热点限流返回友好文案而不是 500
3. 给 `/aa` 方法里加 `Thread.sleep(50)`,触发 degraderule 里 aa 的慢调用熔断(RT>20ms),
   观察熔断 10 秒内请求直接被拦,10 秒后半开恢复
4. 在 Nacos 建 `flowrule.json` 配置(内容抄本地 flowrule.json 但阈值改 10),启动后验证 ds6 生效,
   再在 Nacos 上把阈值改成 100,**不重启**应用,观察规则动态变化
5. 实现 `RequestOriginParser`(取请求头 `X-Origin`),激活 authority.json 的黑白名单
6. 把 `myConverter` 从 JSON 换成解析 xml(激活死文件 flowrule.xml,数据源 type 改成 xml)
7. 进阶:给 `/hello` 规则加 `controlBehavior: 1`(Warm Up),观察冷启动时阈值爬升曲线

### 一句话总结

> 本模块用 5 个接口演示了 Sentinel 的完整基本功:**一切流量皆资源,一切资源皆可配规则**;
> 规则从数据源来,拦截后有 block-page / blockHandler / fallback 三层兜底。
> 跑完 5 个实验,你就掌握了后面 5 个模块反复出现的全部底层概念。
