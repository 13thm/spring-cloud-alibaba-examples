## 1. 项目定位:它是什么?

WebFlux 是 Spring 的响应式 Web 框架(基于 Netty + Reactor,非阻塞)。在它上面用 Sentinel 有三个新问题,本模块逐一回答:

| 问题 | 本模块的答案 |
|------|--------------|
| 响应式里没有"方法返回"时刻(异步),怎么埋点? | `Mono/Flux.transform(new SentinelReactorTransformer<>("资源名"))` |
| URL 自动埋点还有吗?被拦了返回什么? | 有(SentinelWebFluxFilter),自定义 `BlockRequestHandler` 返回 **429** |
| 断路器怎么用? | `ReactiveCircuitBreakerFactory.create(id).run(Mono/Flux, 兜底)` |

模块只有 3 个类 + 1 份流控规则,是**最小可运行的响应式限流示例**,适合精读源码。

## 3. 三分钟响应式预备知识

```
传统 MVC:   一个请求占一个 Tomcat 线程,方法 return 时响应已写完(阻塞式)
WebFlux:    方法立刻返回一个"发货单"(Mono=将来最多一个值 / Flux=将来一串值),
            数据到位时由少量 EventLoop 线程回调执行(非阻塞式)
```

- `Mono.just("x")`:立即有值的 Mono(演示用)
- `.transform(...)`:给流套一层装饰器——**Sentinel 的埋点就是一种"装饰"**:
  在流开始时进入 Slot 链(记为资源),结束时记录 RT/异常,被拦则流直接"错误完成"
- WebFlux 下返回 `Mono/Flux` 的方法,执行时刻是**订阅时**而非 return 时——
  这就是为什么 MVC 的 `@SentinelResource` 注解不能直接照搬,要改用 Transformer

## 4. 配置分析 application.yml + flowrule.json

```yaml
spring:
  application:
    name: sentinel-webflux-example
  cloud:
    sentinel:
      transport:
        dashboard: localhost:8080     # 控制台
      eager: true                     # 启动即注册
      datasource:
        ds1:
          file:
            file: classpath:flowrule.json
            data-type: json
            rule-type: flow           # 文件流控规则

server:
  port: 18084

management:
  endpoints:
    web:
      exposure:
        include=-:                    # ⚠️ 写错了!应为 include: "*" (见坑 2)
```

`flowrule.json`:

```json
[
  { "resource": "/mono", "count": 0, "grade": 1, "limitApp": "default",
    "strategy": 0, "controlBehavior": 0 },
  { "resource": "/flux", "count": 0, "grade": 1, "limitApp": "default",
    "strategy": 0, "controlBehavior": 0 }
]
```

- WebFlux 的 URL 自动埋点资源名同样是 **URL 路径**(`/mono`、`/flux`)
- `count: 0` = QPS 阈值 0 = **全拒**——这两个接口一打开就会被拦,返回 429(演示兜底)
- `/test` 没配规则 → 正常返回,做对照组

## 5. MyConfiguration:429 兜底 + 响应式断路器规则

📄 `MyConfiguration.java`(精简后):

```java
@Configuration
public class MyConfiguration {

	// ① URL 资源被拦时的统一响应
	@Bean
	public BlockRequestHandler blockRequestHandler() {
		return (exchange, t) -> ServerResponse.status(HttpStatus.TOO_MANY_REQUESTS)   // 429
				.contentType(MediaType.APPLICATION_JSON)
				.body(fromValue("block"));
	}

	// ② 响应式断路器规则定制
	@Bean
	public Customizer<ReactiveSentinelCircuitBreakerFactory> slowCustomizer() {
		return factory -> {
			// 给 "slow_mono" 这个断路器配: 慢调用 RT>100ms, 熔断 5 秒
			factory.configure(builder -> builder.rules(List.of(
					new DegradeRule("slow_mono").setGrade(DEGRADE_GRADE_RT)
							.setCount(100).setTimeWindow(5))), "slow_mono");
			factory.configure(builder -> builder.rules(List.of(
					new DegradeRule("slow_flux").setGrade(DEGRADE_GRADE_RT)
							.setCount(100).setTimeWindow(5))), "slow_flux");
			// 其他所有断路器的默认规则: 异常数 >= 0.5 次, 熔断 10 秒
			factory.configureDefault(id -> new SentinelConfigBuilder().resourceName(id)
					.rules(List.of(new DegradeRule(id)
							.setGrade(DEGRADE_GRADE_EXCEPTION_COUNT)
							.setCount(0.5).setTimeWindow(10))).build());
		};
	}
}
```

**逐个拆解:**

| Bean | 关键点 |
|------|--------|
| `blockRequestHandler` | WebFlux 版兜底,签名 `(ServerWebExchange, Throwable) → Mono<ServerResponse>`;不定义时默认也是 429 + 固定文案,自定义后可返回 JSON/重定向 |
| `slowCustomizer` | `configure(..., "名字")` 给**指定**断路器配规则;`configureDefault` 给**所有**断路器兜底默认规则(与 core 模块的 `Customizer<SentinelCircuitBreakerFactory>` 完全同构,只是响应式版) |

注意默认规则的 `count: 0.5`(异常数策略)语义:异常次数 ≥ 0.5 等价于 ≥ 1 次(次数向上取整)。

## 6. SentinelWebFluxController:5 个接口逐个拆解

📄 `SentinelWebFluxController.java`(精简后):

```java
@RestController
public class SentinelWebFluxController {

	@Autowired
	private ReactiveCircuitBreakerFactory circuitBreakerFactory;

	// ① 手动埋点:资源名 "mono"。但 flowrule.json 限的是 "/mono"(URL),注意双资源!
	@GetMapping("/mono")
	public Mono<String> mono() {
		return Mono.just("simple string")
				.transform(new SentinelReactorTransformer<>("mono"));
	}

	// ② 资源 "test":无任何规则 → 永远正常
	@GetMapping("/test")
	public Mono<String> test() {
		return Mono.just("simple string")
				.transform(new SentinelReactorTransformer<>("test"));
	}

	// ③ Flux 埋点:资源 "flux";URL /flux 被 flowrule count=0 全拒
	@GetMapping("/flux")
	public Flux<String> flux() {
		return Flux.fromArray(new String[] { "a", "b", "c" })
				.transform(new SentinelReactorTransformer<>("flux"));
	}

	// ④ 响应式断路器 + WebClient(响应式 HTTP 客户端):慢调用实验
	@GetMapping("/cbSlow")
	public Mono<String> cbSlow() {
		return WebClient.builder().baseUrl("http://httpbin.org/").build().get()
				.uri("/delay/2")                          // 外网延迟 2 秒
				.retrieve().bodyToMono(String.class)
				.transform(it -> circuitBreakerFactory.create("slow_mono").run(it,
						t -> Mono.just("fallback")));      // 熔断兜底
	}

	// ⑤ 响应式断路器:异常数实验(走 configureDefault 的默认规则)
	@GetMapping("/cbError")
	public Mono<String> cbError() {
		return WebClient.builder().baseUrl("http://httpbin.org/").build().get()
				.uri("/status/500")                       // 外网固定返回 500
				.retrieve().bodyToMono(String.class)
				.transform(it -> circuitBreakerFactory.create("cbError").run(it,
						t -> Mono.just("fallback")));
	}
}
```

| 接口 | 涉及资源 | 现象 |
|------|----------|------|
| `/mono` | URL `/mono`(被拦,429)+ 注解资源 `mono`(无规则) | 返回 `{"block"}` 429 |
| `/test` | `test` | 正常 `simple string` |
| `/flux` | URL `/flux`(被拦,429) | 429 |
| `/cbSlow` | 断路器 `slow_mono`(RT>100ms 熔断 5s) | 前 2 秒返回 httpbin 响应;达到条件后熔断,5 秒内秒回 `fallback` |
| `/cbError` | 断路器 `cbError`(默认规则:异常数熔断 10s) | httpbin 500 → 异常;若干次后熔断 10 秒,期间秒回 `fallback` |

> 💡 **重点体会 `/mono` 的"双资源"现象**:与 core 模块的 `/hello` 一样,
> URL 过滤器埋的资源(`/mono`)和 Transformer 埋的资源(`mono`)**是两个独立资源**,
> 规则配给谁才管谁。去控制台"簇点链路"能看到两个都在。

## 7. 一次被限流请求的流程图

```
GET /mono(第 1 次)
   │
   ▼
SentinelWebFluxFilter(自动埋点, 资源 "/mono") ──通过──► Controller 执行
   │                                                    │ Mono.just(...).transform(资源 "mono")
   │ 统计/检查(reactor 适配: 异步 entry)               │ 也通过
   ▼                                                    ▼
                                          返回 simple string ✅

GET /mono(第 2 次,1 秒内)
   │
   ▼
SentinelWebFluxFilter → FlowSlot: 资源 "/mono" QPS(0) 已达阈值
   │ 抛 BlockException
   ▼
BlockRequestHandler.handleRequest(exchange, t)
   │
   ▼
HTTP 429 + Content-Type: application/json + body "block" ❌
(Controller 的 Mono 根本不会被订阅执行)
```

## 8. 如何运行与实验设计

### 8.1 前置
1. (推荐)Sentinel 控制台 8080
2. 外网可达 httpbin.org(cbSlow/cbError 需要;不通时请参考坑 4 换成本地 mock)
3. 修坑 1 后启动:`mvn spring-boot:run`,端口 **18084**

### 8.2 实验清单

```bash
# 实验 1:URL 全拒 → 429 兜底
curl -i http://localhost:18084/mono
# HTTP/1.1 429 Too Many Requests ... "block"

# 实验 2:对照组(无规则)
curl http://localhost:18084/test
# simple string

# 实验 3:慢调用熔断(连刷几次 /cbSlow)
curl http://localhost:18084/cbSlow
# 前几次: 等 ~2 秒返回 httpbin 内容
# 熔断打开后: 立刻返回 fallback,且 5 秒内持续如此;5 秒后半开试探

# 实验 4:异常数熔断(连刷 /cbError)
curl http://localhost:18084/cbError
# httpbin 500 触发异常;达到最小请求数后熔断 10 秒,期间秒回 fallback
```

### 8.3 控制台观察
服务 `sentinel-webflux-example` → 簇点链路:同时能看到 `/mono`(被拦)和 `mono`(0 通过)两个资源,
直观理解"双资源"。

## 9. ⚠️ 项目中存在的问题与坑(重要)

### 坑 1:parent 链断裂(家族统一问题)❌
同其他 sentinel 模块,parent 指向 `com.alibaba.cloud:${revision}` 而根 pom 已改,
先修复才能编译。详见[家族总览坑 0](../学习总览.md#8-️-全家族注意事项与坑)。

### 坑 2:application.yml 的 management 配置写错 ⚠️
```yaml
management:
  endpoints:
    web:
      exposure:
        include=-:      # ← 原文件如此,应为 include: "*"
```
YAML 里 `include=-:` 是个无意义键,导致**所有 actuator 端点都没暴露**。
应改为 `include: "*"`。抄配置时别照搬。

### 坑 3:端口 18084 与 seata-account-service 撞车 ⚠️
混跑实验时先停掉另一边。

### 坑 4:cbSlow / cbError 依赖外网 httpbin.org ⚠️
国内访问不稳,超时会干扰对"熔断是否生效"的判断。
排查顺序:`curl https://httpbin.org/status/500` 先确认网络,再谈规则。
进阶练习 2 给了替换成本地接口的方案。

### 坑 5:响应式限流的统计精度 ⚠️
Reactor 埋点的 entry/exit 是异步的,快速连发请求时,偶尔会有并发统计与 MVC 不一致的观感
(边界窗口问题),不影响教学结论;但生产上判断"是否真的拦了",以返回码/兜底文案为准,
不要纠结第 1 次还是第 2 次被拦。

## 10. 知识点总结与进阶练习

### 本模块覆盖的知识点
- ✅ WebFlux 下 URL 自动埋点(资源名 = URL 路径)+ `BlockRequestHandler` 429 兜底
- ✅ `SentinelReactorTransformer` 手动埋点 Mono/Flux(资源名自定义,与 URL 资源并存)
- ✅ `ReactiveCircuitBreakerFactory` + `Customizer` 配置指定/默认断路器规则
- ✅ WebClient 响应式出站调用 + 断路器兜底
- ✅ 慢调用(RT)与异常数两种熔断策略的响应式实验

### 推荐动手练习(由浅入深)
1. 修坑 1、坑 2 后跑通 8.2 全部实验;在控制台簇点链路里找出 `/mono` 与 `mono` 两个资源
2. 把 `cbSlow` 的 baseUrl 换成 `http://localhost:18084`,uri 换成 `/test`(自己加一个
   `Thread.sleep` 的慢接口),做**完全离线**的熔断实验
3. 给 `flux` 资源(不是 `/flux` URL)在控制台配 QPS=2 规则,验证 Transformer 资源也能限流
4. 把 `blockRequestHandler` 的响应改成 JSON `{"code":429,"msg":"稍后重试"}`,
   并尝试 302 重定向到静态页
5. 对比:同样的 `/mono` count=0 规则,把 `controlBehavior` 改成 2(排队等待),观察行为差异
6. 进阶:阅读 `SentinelReactorTransformer` 源码,理解它在订阅时 entry、在信号到达时 exit 的机制

### 一句话总结

> 响应式世界里"没有方法返回时刻",Sentinel 的答案是**把埋点变成流的装饰器**
> (Transformer)——URL 层由 Filter 自动埋、方法层手动 transform、出站调用交给响应式断路器,
> 三层防线与 MVC 版一一对应,只是全部"响应式化"了。
