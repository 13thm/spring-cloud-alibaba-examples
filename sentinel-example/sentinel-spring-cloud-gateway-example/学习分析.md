# Sentinel Spring Cloud Gateway Example — 学习分析文档

> 本文档面向 Spring Cloud Alibaba 初学者。本模块演示**网关层限流**——微服务流量治理的"总闸门":
> Sentinel 的 Gateway 适配器提供两类专属规则(GatewayFlowRule / API 分组),
> 能按 **Route 维度**、**自定义 API 分组维度**、以及 **Header/URL 参数/Client IP 等热点维度**限流。
> 学完本模块,你就理解了"大促限流为什么都做在网关上"。

## 1. 项目定位:它是什么?

```
                    ┌─────────────────────────────────┐
   所有外部请求 ──► │  本模块(Gateway + Sentinel)      │ ──► aliyun_route  → www.aliyun.com
                    │  网关:路由转发 + 流量总闸门       │ ──► httpbin_route → httpbin.org
                    └─────────────────────────────────┘
```

网关是所有流量的必经之路,在这里限流有天然优势:**挡在最前面,后面所有服务都被保护**。
Sentinel 提供了专门的 `spring-cloud-alibaba-sentinel-gateway` 适配模块(比普通 Web 限流更懂网关):

| 能力 | 对应配置/代码 |
|------|---------------|
| 按 Route ID 限流 | `gateway.json` 里 `httpbin_route` 的规则 |
| 按 API 分组限流 | `api.json` 定义 `some_customized_api` 分组 + 分组规则 |
| 按参数热点限流 | `paramItem`(请求头 `Spring-Cloud-Alibaba`、URL 参数 `name`) |
| 自定义被拦响应 | `MySCGConfiguration` 的 BlockRequestHandler(444) |
| 运行时查看规则 | `RulesWebFluxController` 的 `/api` `/gateway` `/flow` |

## 3. 核心概念:网关限流与服务限流的三大不同

### 3.1 规则不同:GatewayFlowRule(而非 FlowRule)

| | 服务级 FlowRule | 网关级 GatewayFlowRule |
|---|----------------|------------------------|
| 资源 | 任意资源名 | **Route ID** 或 **API 分组名** |
| 维度 | QPS/线程数 | QPS,且支持**按参数细分**(IP/Header/URL参数/Cookie) |
| 数据源 rule-type | `flow` | **`gw-flow`** |
| 兜底 | blockHandler/block-page | BlockRequestHandler 统一响应 |

### 3.2 API 分组:把"任意几条路径"打包限流
服务级限流的资源是单一路径;网关上常需要"这几个接口算一组,共享一个额度"
(比如所有下单相关接口共 1000 QPS)。`api.json` 定义分组,`gateway.json` 对分组配规则。

### 3.3 兜底必须是"响应式"的
网关基于 WebFlux,被拦请求的兜底 `BlockRequestHandler` 返回 `Mono<ServerResponse>`,
可以自定义状态码(本例用了魔性的 444)、响应体(JSON/文案)。

## 4. 路由配置分析 application.yaml

```yaml
server:
  port: 18085

spring:
  application:
    name: sentinel-spring-cloud-gateway
  cloud:
    gateway:
      enabled: true
      routes:
      - id: aliyun_route                       # ① 路由一:/product/** → 阿里云官网
        uri: https://www.aliyun.com/
        predicates:
        - Path=/product/**
      - id: httpbin_route                      # ② 路由二:/httpbin/** → httpbin(去前缀)
        uri: https://httpbin.org
        predicates:
        - Path=/httpbin/**
        filters:
        - RewritePath=/httpbin/(?<segment>.*), /$\{segment}   # /httpbin/get → /get
    sentinel:
      transport:
        dashboard: localhost:8080
      eager: true
      filter:
        enabled: true                          # ③ 开启 Sentinel 网关过滤器
      scg:
        order: -100                            # ④ 限流过滤器的执行顺序(尽量早执行)
      scg.fallback:                            # ⑤ yml 方式配置兜底(与 Bean 方式二选一,见坑 3)
        mode: response
        response-status: 444
        response-body: 1234
      datasource:
        ds2.file: { file: "classpath: gateway.json", ruleType: gw-flow }        # ⑥ 网关流控规则
        ds1.file: { file: "classpath: api.json",   ruleType: gw-api-group }    # ⑦ API 分组定义
```

**三个细节:**
- `RewritePath` 里的 `$\{segment}`:`$` 在 Spring 的占位符体系里特殊,YAML 中写 `$\{...}` 是转义写法
- 注意 `classpath: gateway.json` 冒号后**带空格**也是合法写法
- `gw-flow` 与 `gw-api-group` 是网关专属的两种 rule-type,别写成 `flow`

## 5. 两类规则文件精读:gateway.json 与 api.json

### 5.1 api.json — 定义 API 分组(rule-type: gw-api-group)

```json
[
  {
    "apiName": "some_customized_api",
    "predicateItems": [
      { "pattern": "/product/baz" },                          // 精确匹配
      { "pattern": "/product/foo/**", "matchStrategy": 1 },   // 1=前缀匹配
      { "items": [                                            // 嵌套组合(高级用法)
          { "pattern": "/spring-cloud/**" },
          { "pattern": "/spring-cloud-alibaba/**" }
      ]}
    ]
  },
  { "apiName": "another_customized_api",
    "predicateItems": [ { "pattern": "/ahas" } ] }
]
```

`some_customized_api` 分组 = 三类路径的集合:精确的 `/product/baz`、前缀 `/product/foo/**`
以及嵌套 items 组合的 `/spring-cloud/**` 系列。**分组本身只定义"哪些路径算一类",额度在 gateway.json 里配**。

### 5.2 gateway.json — 网关流控规则(rule-type: gw-flow)

```json
[
  { "resource": "some_customized_api", "count": 1 },
  { "resource": "httpbin_route", "count": 0,
    "paramItem": { "parseStrategy": 2, "fieldName": "Spring-Cloud-Alibaba" } },
  { "resource": "httpbin_route", "count": 0,
    "paramItem": { "parseStrategy": 3, "fieldName": "name" } }
]
```

逐条翻译:

| 规则 | 资源 | 含义 |
|------|------|------|
| 1 | API 分组 `some_customized_api` | 组内所有路径**共享 QPS=1**,1 秒第 2 次被拦 |
| 2 | 路由 `httpbin_route` | 按**请求头** `Spring-Cloud-Alibaba` 限流:阈值 0 → **只要带这个头,立刻拦** |
| 3 | 路由 `httpbin_route` | 按**URL 参数** `name` 限流:阈值 0 → **只要带 name 参数,立刻拦** |

`parseStrategy` 取值速记:**0=Client IP,1=远程地址,2=请求头,3=URL 参数**(还有 Cookie 等)。
配合 `count: 0` 的"全拒"语义,实验现象非常确定:带上头/参数就 444,不带就放行。

## 6. 代码分析:兜底响应与规则查看接口

### 6.1 MySCGConfiguration — 自定义被拦响应

```java
@Configuration
public class MySCGConfiguration {

	@Bean
	public BlockRequestHandler blockRequestHandler() {
		return (exchange, t) -> ServerResponse.status(444)          // 自定义状态码 444
				.contentType(MediaType.APPLICATION_JSON)
				.body(fromValue("SCS Sentinel block"));              // 自定义响应体
	}
}
```

被网关限流的请求统一返回 **444 + "SCS Sentinel block"**,一眼可辨"是网关拦的,不是后端错的"。
生产上这里一般返回统一 JSON 错误码(如 `{"code":429,"msg":"请求太频繁"}`)。

### 6.2 RulesWebFluxController — 三个"规则体检"接口

```java
@GetMapping("/api")      // 当前所有 API 分组定义
@GetMapping("/gateway")  // 当前所有网关流控规则
@GetMapping("/flow")     // 当前所有普通流控规则
```

启动后直接 curl 这三个地址,就能确认 JSON 文件是否真的被加载——
**不用开控制台、不用猜**,是排查"规则没生效"的第一现场。

## 7. 一次网关限流的流程图

```
GET http://localhost:18085/httpbin/get?name=thm
      │
      ▼
Spring Cloud Gateway 路由匹配: httpbin_route(Path=/httpbin/**)
      │
      ▼
Sentinel 网关过滤器(scg.order=-100, 优先执行)
  ① 解析资源: 路由 ID "httpbin_route"(规则 2/3 都挂在它上面)
  ② 规则3命中: URL 参数 name 存在 → 参数热点检查
  ③ count=0 → 阈值已到 → 拦截!
      │
      ▼
BlockRequestHandler(MySCGConfiguration 的 Bean)
      │
      ▼
HTTP 444 + "SCS Sentinel block" ❌(请求根本不会转发到 httpbin.org)

同一路径不带 name 参数:
  ③ 规则3不命中(无该参数)→ 无规则1(非分组路径)→ 放行
      │
      ▼
RewritePath /get → 转发 https://httpbin.org/get ✅
```

## 8. 如何运行与实验设计

### 8.1 前置
1. (推荐)Sentinel 控制台 8080(网关接入后控制台会出现"网关流控规则"专属菜单)
2. 外网可达 httpbin.org / www.aliyun.com
3. 修坑 1 后启动,端口 **18085**

### 8.2 实验清单

```bash
# 体检:先确认规则已加载
curl http://localhost:18085/api       # 应返回 api.json 的分组定义
curl http://localhost:18085/gateway   # 应返回 gateway.json 的 3 条规则

# 实验 1:API 分组共享限流(QPS=1)—— /product/baz 与 /product/foo/** 共享额度
curl -i http://localhost:18085/product/baz
curl -i http://localhost:18085/product/baz         # 1 秒内第 2 次 → 444
curl -i http://localhost:18085/product/foo/xx      # 换路径也没用,同组共享 → 444

# 实验 2:请求头参数限流(count=0,带就拦)
curl -i http://localhost:18085/httpbin/get                        # 放行(httpbin 响应)
curl -i -H "Spring-Cloud-Alibaba: any" http://localhost:18085/httpbin/get   # → 444

# 实验 3:URL 参数限流(count=0,带就拦)
curl -i "http://localhost:18085/httpbin/get?name=thm"             # → 444
curl -i "http://localhost:18085/httpbin/get"                      # 放行
```

### 8.3 控制台观察
服务列表里 `sentinel-spring-cloud-gateway` → 菜单多了**"网关流控规则/API 分组管理"**两个专属页,
可以可视化地加规则(默认内存态,重启丢)。

## 9. ⚠️ 项目中存在的问题与坑(重要)

### 坑 1:parent 链断裂(家族统一问题)❌
同其他模块,先修 parent 才能编译。详见[家族总览坑 0](../学习总览.md#8-️-全家族注意事项与坑)。

### 坑 2:规则资源名必须与路由 ID / 分组名严格一致 ⚠️
`gateway.json` 的 resource 写的是 `httpbin_route`——**就是 application.yaml 里 routes 的 id**。
改名不同步是"规则永不生效"的头号原因。改路由 id 时记得同步规则文件。

### 坑 3:两种兜底配置并存,Bean 优先 ⚠️
本模块同时演示了两种定制兜底:
1. **Bean 方式**:`MySCGConfiguration` 里的 `BlockRequestHandler`(返回 444 + "SCS Sentinel block")
2. **yml 方式**:`scg.fallback.mode: response`(444 + "1234")

两者并存时,**自定义 Bean 优先生效**(自动配置的兜底是 `@ConditionalOnMissingBean`,
检测到你已有 Bean 就让位)。所以本例实际返回的是 Bean 里的 `"SCS Sentinel block"`,
yml 里的 `response-body: 1234` 处于闲置状态。验证方法:注释掉 Bean,
被拦响应体会变成 "1234"。**保留一个即可,别两套都配(虽然不报错,但维护混乱)。**

### 坑 4:嵌套 items 的 api.json 格式较新 ⚠️
`predicateItems` 里再嵌一层 `items` 是较新版本的"组合匹配"写法,老版本适配器不认识会解析失败。
若启动报 api.json 解析错误,把嵌套 items 那条删掉即可(其余功能不受影响)。

### 坑 5:444 不是标准状态码 ⚠️
444 是 nginx 的"Connection Closed Without Response"魔改用法,浏览器/curl 显示可能各异。
教学上它"一眼可辨";生产上建议用标准 429 并附 JSON 错误体。

### 坑 6:外网依赖 ⚠️
两条路由都指向外网(aliyun/httpbin)。被拦的请求不会出网,但**放行的请求**需要外网可达;
httpbin 慢会拖长实验耗时,不代表限流没生效。

### 坑 7:配置文件是 .yaml 不是 .yml ⚠️
本模块用的是 `application.yaml`——Spring Boot 两种扩展名都认,但找文件时别只搜 `.yml` 找不着。

## 10. 知识点总结与进阶练习

### 本模块覆盖的知识点
- ✅ Sentinel 网关适配:`spring-cloud-alibaba-sentinel-gateway` + `filter.enabled` + `scg.order`
- ✅ 两类专属规则:`gw-flow`(网关流控)与 `gw-api-group`(API 分组)
- ✅ 网关参数热点限流:`paramItem.parseStrategy`(0=IP/1=RemoteAddr/2=Header/3=URL参数)
- ✅ API 分组:精确/前缀/嵌套组合三种 pattern 匹配,组内共享额度
- ✅ 两种兜底定制方式(Bean vs yml scg.fallback)及优先级
- ✅ RewritePath 正则去前缀、`$\{...}` 转义
- ✅ 运行时规则体检接口(/api /gateway /flow)

### 推荐动手练习(由浅入深)
1. 修坑 1 → 先 curl 三个体检接口确认规则加载,再做 8.2 全部实验
2. 给 `httpbin_route` 加一条 `parseStrategy: 0`(Client IP)的规则,count=2,
   同机快速刷 3 次观察按 IP 限流(换手机热点 IP 立刻放行,体验"按调用方限流")
3. 把 Bean 方式兜底注释掉,启用 yml 方式,对比响应体差异(坑 3 的验证)
4. 自建一个 API 分组 `order_api`(如 `/httpbin/post/**` + `/httpbin/put/**`),配 QPS=2 分组规则
5. 把 `api.json`/`gateway.json` 迁移到 Nacos 数据源(放开 pom 注释 + yml 加 nacos datasource),
   实现规则动态推送(参考 core 模块 ds6 写法)
6. 进阶:对比"网关限流"与"服务限流"(core 模块)的兜底机制差异(BlockRequestHandler vs block-page),
   思考生产上为什么两层都要配
7. 进阶:阅读 `SentinelGatewayFilter` 源码,理解"网关为什么没有 @SentinelResource 注解"
   (过滤器统一埋点,资源=Route ID/分组名)

### 一句话总结

> 网关限流是 Sentinel 家族的"毕业篇":**资源从"接口"升维成"路由/分组",规则多了参数热点维度,
> 兜底统一成响应式 JSON**——所有外部流量在这一层先过筛,后端服务才有喘息的余地。
> 排查口诀:规则名=路由ID,体检接口先 curl,兜底只留一套。
